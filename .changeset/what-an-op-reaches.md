What an operation reaches, and the three numbers that were written for every op.

`placement` said where an operation ANSWERS and nothing said where its work GOES.
`EffectiveOperation.reach` names the fronds its handler crosses to and counts those a process
away. It is read from the HANDLER: a dependency is declared on the constructor, so every op of
one handler reaches the same fronds, and saying otherwise would dress a structural fact as a
precise effect. A new required field, like `declared`.

Three constants were a function of that one number, and each is answered differently now.

A SAMPLING rate is a budget, which no reading of the code answers — so it is the operator's
(`observability({ sample })`, default 1), and the code answers only what a budget may not touch:
an operation with hops is always kept, since the gap between the caller's span and the callee's
IS the wire cost and neither measures it alone.

A LOAD threshold is per operation and derived — `BUDGET.base + op.hops * BUDGET.perHop`, two
numbers in the generated file instead of one, read against a k6 threshold per tag.

Histogram BOUNDS are deliberately NOT derived per operation, though `reach` could: an
explicit-bucket histogram aggregates only across series sharing its bounds, so per-op bounds
would silently break the panel asking for the p95 of the whole service. They left the library
instead — `observability({ bounds })` — because a list of bounds is an operator's decision, not
a literal a package holds.

And `fougere load` finally exists. `loadScript` was exported, tested, called by one script by
hand, and the file it writes said it was generated by a command that did not exist. It reads the
scan rather than a boot, because describing a project may not migrate it.
