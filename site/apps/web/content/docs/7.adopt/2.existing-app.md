You keep your app as it is: routing, pages, components, styling and server routes stay in
place. Fougere only adds its own paths: `/_fougere/call`, the one endpoint your pages call —
who is signed in included, `session.get`; `/auth/**`, which answers once you turn auth on; and
`/api/{frond}/…` and `/graphql` if you turn [REST or GraphQL](/docs/serve/rest-graphql) on.

## The three pieces

**1. The module** — in your existing `nuxt.config.ts`:

```ts
export default defineNuxtConfig({
  modules: [/* your modules */, '@fougere/nuxt'],
});
```

**2. The config** — `fougere.config.ts` at the root ([every key](/reference/config)):

```ts
import '@fougere/adapter-sql';
import { defineFougere } from '@fougere/core';

export default defineFougere({
  sources: { main: { type: 'sqlite', path: '.data/app.db' } },
});
```

**3. A first frond** — one entity and one handler, under `fronds/` in the app you already have:

```
fronds/todo/entities/Todo.ts
fronds/todo/handlers/TodoHandler.ts
```

Fougere knows what each file is from the folder it sits in. A page imports the entity with
`import Todo from '@fronds/todo/entities/Todo.js'`: the alias exists on its own, so you add
no `package.json` and no workspace entry. A second domain later goes in `fronds/billing/`,
next to this one.

Run `npm run dev` and check the [boot log](/docs/adopt/new-project#create-it).

## Migrate feature by feature

Move one feature at a time, while your old routes keep serving the rest. Here is what
each thing you maintain today becomes:

| You maintain today | It becomes |
|---|---|
| a Zod/Yup schema | the entity's fields — [shape axis](/docs/concepts/entity) |
| a table definition or additive migration | derived — `fougere migrate` writes it from the same fields; destructive changes stay explicit |
| `server/api/todos.post.ts` + validation call | a [handler](/docs/concepts/handler) operation, validated before your code runs |
| form state + client-side rules | [`useFormFor(Todo)`](/docs/serve/forms) — same validation as the server |
| `useFetch('/api/todos')` + refresh bookkeeping | [`useQuery(todo, 'list')`](/docs/serve/pages) — typed by the handler, revalidated by commands |

Delete the old files as each feature moves over: the goal is fewer files to keep in sync,
not a second copy.

## Untangle a monolith

A monolith is hard to split because you decide everything at once: the boundary, the new
service and the network. Here you draw the boundary first, and the network can wait.

Say `OrderService` calls `PricingService` directly, and pricing should be able to leave.

**1. Give pricing its own frond.** Move the service and its entities to `fronds/pricing/`,
then write a handler for what other fronds may call. It is a handler like any other: it says
what goes out, and it checks what it has to check.

```ts
// fronds/pricing/handlers/PricingHandler.ts
import PricingService from '../services/PricingService.js';

export default class PricingHandler {
  constructor(private pricing: PricingService) {}

  /** What this cart comes to. */
  async total(cartId: string): Promise<number> {
    return this.pricing.total(cartId);
  }
}
```

**2. Call it through its [facade](/docs/concepts/facade).** The caller asks for the type and
adds an `await`. Everything still runs in one process, with no network.

```ts
// fronds/order/services/OrderService.ts
import type { Facade } from '@fougere/core';
import type PricingHandler from '@fronds/pricing/handlers/PricingHandler.js';

export default class OrderService {
  constructor(private pricing: Facade<PricingHandler>) {}

  async checkout(cartId: string): Promise<number> {
    return this.pricing.total(cartId);
  }
}
```

**3. Move it when it is worth it.** One line in `fronds:` is the whole [move](/docs/run/deploy),
and the code above does not change:

```ts
fronds: { pricing: { remote: 'http://pricing:4610' } },
```

From then on, each call costs a network call. If you never take this step, you still have a
monolith with cleaner boundaries, and it cost you almost nothing. `demos/crossing-cost` runs
the same code with 0 hops or 2.

Three things show you where a boundary does not hold:

- **What crosses must be plain data.** A class instance with methods does not survive the
  trip, so pass an id or plain fields.
- **A join between two fronds' tables** stops working once the rows leave. Read through the
  facade, or keep a [copy](/docs/data/mirror).
- **Two writes that must stand or fall as one** stay in one process. [`Together`](/docs/data/together)
  holds them across two fronds, and refuses a frond placed elsewhere, so those two move
  together or not at all.

## What stays yours

- **Pages and components** — Fougere adds composables, not components: no layout, no widgets.
- **Other server routes** — anything outside the paths above is left alone.
- **Auth** — optional. Keep your own system if you have one; `useCurrentUser` and the
  session-to-handler flow need [Fougere auth](/docs/access/authentication) to be enabled.

## What Fougere owns

Fougere owns an entity's rows: their table is written by `fougere migrate` (SQLite, Postgres, MySQL,
SQL Server, D1), or they are files or memory. Move a feature over when you can hand its table to
Fougere, and keep your existing database code for the rest.
