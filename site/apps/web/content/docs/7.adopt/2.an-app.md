You keep your app as it is: routing, pages, components, styling and server routes stay in
place. Fougere only adds its own paths: `/_fougere/call`, the one endpoint your pages call —
who is signed in included, `session.get`; `/auth/**`, which answers once you turn auth on; and
`/api/{frond}/…` and `/graphql` if you turn [REST or GraphQL](/docs/serve/rest-graphql) on.

## Add Fougere to a Nuxt app

**1. The module** — in your existing `nuxt.config.ts`:

```ts
export default defineNuxtConfig({
  modules: [/* your modules */, '@fougere/nuxt'],
});
```

**2. The config** — `fougere.config.ts` at the root ([every key](/reference/config)):

```ts
import '@fougere/adapter-sql';
import { defineFougere } from '@fougere/core';

export default defineFougere({
  sources: { main: { type: 'sqlite', path: '.data/app.db' } },
});
```

**3. A first frond** — one entity and one handler, under `fronds/` in the app you already have:

```
fronds/todo/entities/Todo.ts
fronds/todo/handlers/TodoHandler.ts
```

Fougere knows what each file is from the folder it sits in. A page imports the entity with
`import Todo from '@fronds/todo/entities/Todo.js'`: the alias exists on its own, so you add
no `package.json` and no workspace entry. A second domain later goes in `fronds/billing/`,
next to this one.

Run `npm run dev` and check the [boot log](/docs/adopt/new-project#create-it).

## Other frameworks

| Host | Package | What you write |
|---|---|---|
| Nuxt | `@fougere/nuxt` | one line in `nuxt.config` |
| Next | `@fougere/next` | two one-line route files + `withFougere()` |
| TanStack Start | *none* | two route files + the Vite plugin |
| React Router | *none* | three resource routes + the Vite plugin |
| SvelteKit | *none* | two `+server.ts` + the Vite plugin |
| Express | *none* | `app.use(fougere())` |
| Hono, a Worker, any engine | *none* | one line — [`answer`](#serve-on-any-engine) |

`fougere new` writes these lines into the shell the host's own tool made, so a new app starts from
what `create-nuxt`, `create-next-app`, `create-vite` or `sv create` writes today — see
[`fougere new`](/reference/cli). A host finds the fronds on its own — the nearest directory, up from the app, that holds
`fronds/` — so `root` is written only when they sit elsewhere, the same option for every host.

Three hosts need no package of their own, and that is not an accident: they serve
Web-standard `Request`/`Response`, so the facades go in unchanged. `@fougere/next` exists
because Next has `next/headers` — one import — and Nuxt's module is larger because an h3
event is not a `Request`.

## Mount Fougere in your framework

Mounting a facade is not the same as publishing an adapter: what you write below puts
the facade in place, and `protocols:` decides whether it serves anything.

**A Web-standard host** — Next, TanStack Start, React Router, SvelteKit — mounts the
handlers directly:

```ts
// SvelteKit — src/routes/_fougere/call/+server.ts
import { fougere } from '@fougere/app/web';
export const POST = ({ request }: { request: Request }) => fougere(request);
```

`fougere` takes a `Request` and returns a `Response`, and reads the door off the path, so every
route file hands it the same function. The file you create *is* the consent: no file, no facade.

**Express** adds them as one middleware, like `express.json()` or `cors()`:

```ts
import { fougere } from '@fougere/app/express';

app.use(fougere());   // every door; what each one serves is `protocols:` in fougere.config.ts
```

A path Fougere does not serve calls `next()`, so an app's own routes keep answering
whether they were registered before or after.

**Nuxt** mounts them itself — its module has an API for that, and adds the composables
at the same time.

## Several apps

A project can hold several apps: a Nuxt site and a terminal, for example (`--app "nuxt:web,oclif:ops"`).
Each app runs every frond in its own process. That works for what is the same everywhere: the
code, the rules, and a database the apps share.

It does not work for what must exist once:

- **Memory.** With no `sources:`, each app keeps its own data, and the other never sees it.
- **SQLite and files.** One writer at a time. A source with no transaction (memory, files, D1)
  arbitrates inside one process only.
- **Facts.** An announcement reaches the listeners of its own process only.
- **Seeds.** Two apps starting on an empty database both plant them.

When something must exist once, run its frond in one place and let the other apps call it:
`fronds: { mail: { remote: 'http://mail:4100' } }`. See [Deploy](/docs/run/deploy).

To split an app you already have into fronds, see [Split an existing app](/docs/run/split-an-existing-app).

## Migrate feature by feature

Move one feature at a time, while your old routes keep serving the rest. Here is what
each thing you maintain today becomes:

| You maintain today | It becomes |
|---|---|
| a Zod/Yup schema | the entity's fields — [shape axis](/docs/concepts/entity) |
| a table definition or additive migration | derived — `fougere migrate` writes it from the same fields; destructive changes stay explicit |
| `server/api/todos.post.ts` + validation call | a [handler](/docs/concepts/handler) operation, validated before your code runs |
| form state + client-side rules | [`useFormFor(Todo)`](/docs/serve/forms) — same validation as the server |
| `useFetch('/api/todos')` + refresh bookkeeping | [`useQuery(todo, 'list')`](/docs/serve/pages) — typed by the handler, revalidated by commands |

Delete the old files as each feature moves over: the goal is fewer files to keep in sync,
not a second copy.

## What stays yours

- **Pages and components** — Fougere adds composables, not components: no layout, no widgets.
- **Other server routes** — anything outside the paths above is left alone.
- **Auth** — optional. Keep your own system if you have one; `useCurrentUser` and the
  session-to-handler flow need [Fougere auth](/docs/access/authentication) to be enabled.

## What Fougere owns

Fougere owns an entity's rows: their table is written by `fougere migrate` (SQLite, Postgres, MySQL,
SQL Server, D1), or they are files or memory. Move a feature over when you can hand its table to
Fougere, and keep your existing database code for the rest.

## Serve on any engine

Every host above ends in the same function. When you already hold the app, call it yourself:

```ts
import { answer } from '@fougere/app/answer';

hono.all('*', async (c) => (await answer(app, c.req.raw)) ?? c.notFound());
```

`answer(app, request)` reads the door off the path — `/_fougere/call`, REST under its prefix,
`/graphql` (GraphQL over `GET` too, a mutation refused there) — and answers `undefined` when none
of them is the request's, so the engine's own routes keep answering. It loads no boot, which is
what lets a Worker import it (`demos/cloudflare-d1`). There is no router of ours to adapt: the
engine is one, and its middleware is how you stand around the app — leaving a route out is a
middleware answering before `answer` does. `fougere(request)` from `@fougere/app/web` is the same
function for a host that has only the request: it boots the app at the first one.

`fougere serve` answers this way too, beside the envelope it serves its peers, and `server: { use }`
in the config stands around that half ([config](/docs/concepts/configuration#add-middlewares-to-fougere-serve)).
The envelope is read off the Node stream rather than through a `Request`: it is the wire between two
processes, and the same call answered 29 % less the other way.

## Keep class names in production builds

A call through a facade names its address as a literal (`{ address: 'post' }`), so nothing a
minifier renames reaches it. What still reads a class name is the form — `useFormFor(Post)`
submits to the address named after the entity — and `invoke(Post, 'list')` on the server. A
minifier renames classes, so a production build would designate an entity nobody hosts:

```
Entity 'j' is not hosted here. Hosted here: post.
```

You do not have to declare anything for this. `@fougere/nuxt` and `@fougere/vite` reserve
the entity names for you — the first from the scan it just ran, the second by reading
`fronds/<frond>/entities/`. On Next, `withFougere()` does the same through webpack:

```ts
// next.config.ts
import { withFougere } from '@fougere/next/config';
export default withFougere(nextConfig);
```

```ts
// vite.config.ts — TanStack Start, React Router, SvelteKit
import { fougere } from '@fougere/vite';
export default defineConfig({ plugins: [fougere(), sveltekit()] });
```

Express needs none of this: it runs your sources, nothing is minified.

::callout
An app that minifies without one of these will build cleanly and fail on the first call.
The failure is loud — the server says which entity it does host — but it happens in
production, not at build time.
::
