Your code says what a thing is: its data, what it does. It names no process, no provider, no
database and no protocol. Those choices live in one file at the root of the project,
`fougere.config.ts`, and changing them changes no line under `fronds/`. That separation is
**the gradient**: since nothing in a frond says where it runs, moving it is a line of config.

```ts
// fougere.config.ts
import '@fougere/adapter-sql';
import '@fougere/adapter-rest';
import { defineFougere } from '@fougere/core';

export default defineFougere({
  ports: { Payment: 'StripePayment' },
  sources: { main: { type: 'sqlite', path: '.data/shop.db' } },
  protocols: { rest: {} },
});
```

Leave a key out and you get the default: every frond in the app's process, the only realization of
each port, rows in memory (the boot warns), no REST and no GraphQL. The imports at the top make a
source type or a protocol exist; naming one that is not imported refuses the boot, naming the import.
Every key, and the package that answers it: [fougere.config.ts](/reference/config).

## Where each frond runs

With no `processes:`, the whole project runs in one process: the app. To move a frond out of it,
give it a process of its own:

```ts
processes: {
  catalog: { url: 'http://127.0.0.1:4620', fronds: ['catalog'] },
},
```

Start that process by its name; the app needs none:

```bash
fougere dev catalog      # in production: fougere build, then fougere serve catalog
nuxt dev                 # the app: every frond processes: places nowhere, catalog reached at its url
```

`catalog` listens on the port of its `url`, and the app reaches it there. The code that calls the
catalog does not change; the call now crosses the network. Delete the line and the catalog runs in the
app again. The [tutorial](/tutorial/8-split) does it step by step.

A frond another extends is code, not a place: it is loaded beside its children wherever they run.
A name can also come from `FOUGERE_PROCESS`, for a host that takes no argument.

The scheme of a process `url` names what carries the call: `http://` and `https://`, or `binding://CATALOG`
for a Cloudflare service binding, all three registered by `@fougere/transport-http`. Another scheme is
a package's to register — see [extension points](/docs/extending/extension-points#replace-the-transport-or-wrap-http).

## What each process carries

An extension belongs to the process, not to a frond: the lines every call writes, a trace, a dev
panel. `platform:` lists them, imported from their package:

```ts
import { log } from '@fougere/log';
import { calls } from '@fougere/calls';

const base = [log()];

platform: base,
processes: {
  blog: { url: 'http://127.0.0.1:4100', fronds: ['blog'], platform: [...base, calls({ panel: 4400 })] },
},
```

`@fougere/log` brings two of them: `log()`, the two lines every call writes, and `file(path)`, a
file every line of the process goes to — handlers' own lines included, the call lines only when
`log()` is carried too.

A process that states no `platform` carries the config's; one that states it carries exactly that
list, nothing of the default added. To keep the default and add to it, spread it: `[...base, …]`. An
extension written under `fronds:` refuses the boot, naming the line to write instead.

An app is named by its directory under `apps/`, and carries its own list the same way:

```ts
apps: {
  web: { platform: [...base, calls({ panel: 4402 })] },   // apps/web
},
```

`apps/web` reads its name off its directory: Nuxt off its own, any other host off the directory it
runs from, and a terminal started from elsewhere passes `appNameOf(root, import.meta.dirname)` to
`bootApp`. An entry naming no directory under `apps/` refuses
the boot.

## The programs the app needs

A search engine, an object store, a cache: programs the app talks to and Fougere does not write.
`services:` says how each one is started, by its type — a command, or a Docker image:

```ts
import '@fougere/services';

services: {
  meili: { type: 'process', command: 'meilisearch --http-addr 127.0.0.1:7700', port: 7700, health: '/health' },
  cache: { type: 'docker', image: 'redis:7-alpine', port: 6379, scheme: 'redis' },
},
```

`fougere up` starts each one, waits until it answers — on its `health` path, or on its port —
then every process of `processes:` and every app under `apps/` that has a `dev` script, in one
terminal. A service is told to the rest by its address, `MEILI_URL=http://127.0.0.1:7700`, which is
the variable the `env` source reads the url of a `Meili` value off: the address is written once.
When the environment already gives `MEILI_URL` — a shared staging instance, production — that
service is not started, and its address is the one given.

`fougere env <process>` prints what a process is told — its name, where it listens, where its
neighbours answer, every service's address — for a deployment to hand over when it starts one.

## Choose what answers a port

When two classes extend `Payment`, the boot stops until `ports:` says which one answers. The same
key orders the links that stand in front of it, outside in:

```ts
ports: { Payment: process.env.NODE_ENV === 'production' ? 'StripePayment' : 'FakePayment' },
ports: { Payment: ['AuditPayment', 'StripePayment'] },
```

The handler asks for `Payment` and never learns which one it got. See [Port](/docs/concepts/port).

## Where data is stored

`sources:` names each place rows live. The entry with no `rows:` holds every entity the others do
not list:

```ts
sources: {
  main: { type: 'sqlite', path: '.data/shop.db' },
  archive: { type: 'file', path: './archive', rows: ['Order'] },   // import '@fougere/adapter-file'
},
```

`Order` is now kept as files under `archive/`; everything else stays in `main`. The repository a
handler asks for is the same either way. An entity with one instance — a search engine's address,
some settings — is listed in `values:` and injected as that value: `env: { type: 'env', values:
['Meili'] }` reads `MEILI_URL` into the `Meili` a constructor asks for. See
[Store your data](/docs/data/storage) and [Values](/docs/data/values).

## Which APIs the app serves

`protocols:` says which APIs the app answers on, beside the calls its own pages make:

```ts
import '@fougere/adapter-rest';
import '@fougere/adapter-graphql';

protocols: { rest: {}, graphql: {} },
```

Importing an adapter makes a protocol available; naming it here is what serves it. See
[REST, OpenAPI, GraphQL](/docs/serve/rest-graphql).

## Add middlewares to fougere serve

`fougere serve` is the one host where Fougere *is* the server, so what you would put around a server
of your own goes in `server:` — srvx middlewares, outside in:

```ts
server: { use: [cors({ origin: 'https://app.example.com' })] },
```

They stand around what the process answers browsers — REST, GraphQL, and any request none of them
claims, such as a `/healthz`. Under Nuxt, Next, Express or Hono the key is not read: the server and
its middlewares are yours. See [Any engine](/docs/adopt/an-app#serve-on-any-engine).

## Inherit a frond, or bring one from a package

An entry of `fronds:` says two things — which frond inherits from which, and which package brings a
frond of its own:

```ts
fronds: {
  shop: {},
  cart:    { extends: 'shop' },                  // cart and pricing inherit shop's code
  pricing: { extends: 'shop' },
},
```

Fronds under `fronds/` need no entry; the scan finds them. `extends` says one thing: `cart` takes the
code `shop` declares. It serves `shop`'s handlers under its own name, and builds `shop`'s services in
its own scope, so a class `cart` states in their place — `class StripePayment extends Payment` — is the
one they are handed, even through a service of `shop`. It grants no right to call — `cart` still
reaches `pricing` through a facade or a fact, like any neighbour. A frond others inherit from serves
nothing itself, so nothing can call it or move it, and it stands in every process that holds one of
its children.

A frond a package brings is named by its key — `'@acme/mail': {}` answers as `@acme/mail` — so it is
extended the same way, to put a class of your own in it:

```ts
fronds: {
  '@acme/mail': {},
  mail: { extends: '@acme/mail' },   // fronds/mail/services/ResendMailer.ts extends the package's Mailer
},
```

## From one process to many: what each step costs

Going up a rung never rewrites what you wrote. What each one costs:

| | The step | What it buys | What it costs |
|---|---|---|---|
| 0 | one frond, one process | a running app — no network, no HTTP | nothing |
| 1 | a second frond, in `fronds/billing/` | a boundary of ownership, before any network | no reaching into another frond's files (`fougere check` reports `cross-frond-import`); a [collector](/docs/access/authentication#get-the-current-user-in-an-operation) lives in the frond that uses it |
| 2 | a process of its own under `processes:` | the frond runs elsewhere, same code | the hop and its JSON; beyond one machine the receiver must [know who calls](/docs/run/secure); a named surface answers nothing for a remote frond; one address per frond, so a frond cannot be deployed twice |
| 3 | the frond moves to its own repository | its own team, release cycle and deployment | its **contract** is copied (`fougere sync`), the carrier under facts is yours, and readers of a fact deploy before its sender — see [A frond from another repository](/docs/adopt/another-repository) |
| 4 | the frond is not TypeScript | a Rust or Python process answering the same calls | you honour [the card and the wire](/docs/extending/card-and-wire) yourself |

## What changes after a split

| | |
|---|---|
| results | the same shapes on both sides, lists included |
| errors | the same `FougereError` — `code`, `message`, `details` — rebuilt on arrival |
| an optional input | absent is `undefined`; JSON omits the key; an explicit `null` stays `null` |
| state | the calling app's session reaches the other process, in the signed envelope |
| caller | `invocation.caller` names the frond that signed — absent when nothing was established |
| an unreachable process | `SERVICE_UNAVAILABLE` — 503 on REST — and calls resume once it is back |
| the transport | a timeout and retries on the envelope, never an automatic retry of a command |

The split adds a hop: one HTTP request and its JSON, framed and unframed by the transport, after
which the receiving side runs the same checks as a local call. What that costs depends on your
network and payloads; [crossing-cost](https://github.com/chok/fougere/tree/main/demos/crossing-cost)
measures it on a chain of three fronds, and [Observe](/docs/run/observe) shows it per call.

## Each call has one recipient

Every call has one recipient: `fronds:` gives each frond one address, and `Facade<T>` resolves to one
facade. A device behind a firewall still names one gateway; that it opens the connection itself is a
property of the deployment, not another kind of call.

A send with several recipients comes in two kinds, and only one is here:

| | Who decides the recipients | |
|---|---|---|
| a fact — a post was published | nobody: whoever accepts it | [Fact](/docs/concepts/fact) |
| a fleet | the sender, naming the set | not here — address it in the data, as [emit-fleet](https://github.com/chok/fougere/tree/main/demos/emit-fleet) does |

A remote frond adds latency and failure modes; Fougere reports them as typed errors and hides
neither. One process stays the reference; `fronds:` moves a frond when the need is real.
