# Collect and present

A handler states what it takes and what it answers. Two steps stand on either side of it, and both are
classes built on an entity, the way a [repository](/docs/business/repositories) is: `Collect<User>` fills a
parameter before the handler runs, `Present<Post>` adds fields to what it answered. TypeScript erases
`<User>` and `<Post>`, so the scan reads them; a `fronds.ts` written by hand says them —
`{ ctor: CurrentUserCollector, collects: User }`, `{ ctor: PostPresenter, presents: Post }`.

## Collect — a parameter filled by its type

A collector resolves a handler parameter **by its type** from the invocation context.
Operations declaring that parameter receive the value automatically.

```ts
import { Collect } from '@fougere/core';
import type { InvocationContext } from '@fougere/core';
import User from '../../user/entities/User.js';

/**
 * The auth middleware puts the session user on ctx.state.user —
 * this surfaces it to any handler that declares `user?: User`.
 */
export default class CurrentUserCollector extends Collect<User> {
  async collect(ctx: InvocationContext) {
    return ctx.state.user as User | undefined;
  }
}
```

From then on, in any handler of the Frond:

```ts
async mine(user?: User): Promise<Post[]> { … }           // nobody signed in: user is undefined
async publish(id: Post['id'], user: User): Promise<Post> { … }  // nobody signed in: refused
```

### A required parameter nothing filled

Without `?`, the absence is a refusal, and the handler is never called. The collector says it in
its own words with `missing()`, which throws:

```ts
export default class CurrentUserCollector extends Collect<User> {
  async collect(ctx: InvocationContext) {
    return ctx.state.user as User | undefined;
  }

  missing(ctx: InvocationContext): never {
    throw new FougereError({ code: ErrorCode.UNAUTHORIZED, message: 'Sign in first' });
  }
}
```

`missing()` is handed the call, so it can tell one absence from another — nobody signed in, a
session expired. A collector with no `missing()` refuses with `400 user: Required`, like a path
parameter left out. What `missing()` throws is read by the scan, through the helpers it calls, and
joins the [refusals](/docs/business/errors) of every operation that requires the collector: the
handler no longer writes `if (!user) throw …`, and the contract still promises the `401`.

### Resolution rules

- The match is **by checked type**: `Collect<User>` resolves `user?: User`,
  `user: User | undefined`, and aliases with the same meaning. The class answers the key
  `Collect<User>`, spelled as the type is.
- The target needs no schema. Nothing reads its fields, so an ordinary class works —
  `Collect<Ability>` for a value you build from state at every call.
- It runs for a call that comes **through a door** — the page, REST, GraphQL. Code calling
  another Frond's [`Facade<T>`](/docs/business/handlers#reaching-another-frond) already holds
  the value and passes it: `publish(id, user)`. A value left out is not collected.
- **Absence is `undefined` when the parameter says it may be** — `user?: User`, or an alias such
  as `type CurrentUser = User | undefined`, which the type checker resolves. Without it, the
  absence is refused (above).
- Collectors are DI-injectable classes — declare constructor dependencies as usual.

### State and the gradient

`ctx.state` is the request state built by the consuming application, for example from the
session. During a remote call, this state is sent with the invocation, so the collector
receives the same `ctx.state.user` as it would locally.

What it may hold is **declared**, by the extensions of the process, with fields:

```ts
extensions: [{ name: 'tenancy', state: { tenant: text() } }]
```

`betterAuth()` declares `user` and `session` — the session without its `token`: a process
trusts the one that called it, never the cookie of whoever is behind it.

The state is judged **where it entered** — in the process whose host filled it, or whose
middleware wrote a member — and nowhere after:

- **a member nobody declares there is refused** — `state.tenant: Unknown field — this process
  declares user, session`;
- **two extensions declaring one member refuse the boot**, naming both;
- **a process that receives the call declares nothing.** What crossed was judged where it
  entered, and the envelope proves which process wrote it.

What a handler READS is read by the type it asks for: a collector written `Collect<User>`
hands on what it collected as a `User`, judged and rebuilt. `state.user.since` is a `Date` in
process and across the wire, where it used to arrive as the string JSON made of it.

### A collector does not cross a Frond boundary

Keep the collector in each Frond that consumes it, or in the Frond they all extend. The binding is
decided at boot, from the collectors *of that Frond and of the one it extends* — the same reach its
scope has — not at the split, and not per call:

- **a collector for that type in another Frond is not used**: the parameter is read from the
  request, and the boot warns `collector-in-another-frond`, with both ways out — move the
  collector into this Frond, or say the request is meant;
- **no collector for that type anywhere** makes it an ordinary input: it falls into the fourth
  binding rule, `body`.

Saying the request is meant is a binding in `frond.config.ts`, and it names that parameter only —
the others keep what Fougere derives:

```ts
// fronds/admin/frond.config.ts — the invited user comes from the request
export default {
  operations: { 'invite.inviteUser': { binding: [{ name: 'user', source: { kind: 'input' } }] } },
};
```

Put plainly: `user?: User` in a project that declares no `Collect<User>` at all receives
whatever the client sent. A handler validating on `user.role` validates a caller-supplied value.

## Present — fields computed over the page

A presenter adds **computed fields** to an entity's output. Each method defines one field.
It receives every row in the response and returns one value per row.

```ts
import { Present, type Repository } from '@fougere/core';
import Post from '../entities/Post.js';
import Author from '../entities/Author.js';

export default class PostPresenter extends Present<Post> {
  constructor(private authors: Repository<Author>) { super(); }

  excerpt(posts: Post[]): string[] {
    return posts.map((post) => post.body.slice(0, 200));
  }

  /** One read for the page, not one per row — which is why the page is the argument. */
  async authorName(posts: Post[]): Promise<string[]> {
    const authors = await this.authors.findByKeys(posts.map((post) => post.authorId));
    return posts.map((post) => authors.get(post.authorId)?.name ?? 'Anonymous');
  }
}
```

Place the class in the Frond's `services/` directory, where `extends Present<Post>` says what it
is. It answers `Present<Post>`. Methods may be synchronous or asynchronous, and constructor dependencies
are resolved by type.

### Why it is not a field on the entity

`excerpt` is computed from `body` and does not need to be stored. `authorName` comes from
another entity; computing it at read time avoids duplicating the value when an author is
renamed.

Use a presenter when the calculation needs I/O, another entity, or both. It is a class so
that dependencies such as a repository can be injected. Direct `Storage` injection is
refused at boot, just as it is for handlers and collectors.

### Application across surfaces

A computed field is added to the entity's output on every facade: the envelope
(`useQuery`, `useCommand`, `invoke`), REST — mounted as the catch-all or as a standalone
host — and GraphQL. No additional configuration is required.

A handler calling another Frond through [`Facade<T>`](/docs/business/handlers#reaching-another-frond)
does not get it: code receives the rows the handler returned, and a computed field is for
whoever reads through a door.

```ts
const { items } = await useQuery(post, 'list');
items[0].excerpt;      // ← present, exactly as in a GraphQL query
```

> Enrichment is now applied in the shared façade. Earlier versions applied it separately
> in the REST and GraphQL projections, and not in `useQuery`.

### Where it stops: a named view

When an operation names an output view, only fields in that view are returned. A computed
field not listed there is excluded:

```ts
async cards(): Promise<Page<PostCard>>   // emits PostCard, and only PostCard
```

Without a named view, computed fields are added to the entity's output. The [boundary
axis](/docs/schema/entities) still applies to the entity's own fields.

### What it is not

- **Not a serializer.** What may leave at all is the `boundary` axis; what a given
  audience sees is a [view](/docs/schema/views). A presenter only **adds**.
- **Not a place for business rules.** A computed field is a read. A transition
  (`publish`) is [an operation, not a field
  write](/docs/business/handlers#a-state-changes-through-an-operation-never-through-a-field-write).
- **Not automatically optimized.** A method receives the whole page, which allows reads
  to be batched. Calling `findById` in each iteration still produces N reads.
- **No silent failures.** An error in a computed field produces `INTERNAL_ERROR` and names
  the affected field.
