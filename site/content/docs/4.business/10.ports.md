# Ports

A handler that writes `constructor(private payment: StripePayment)` has named its provider.
Everything downstream of that line — the tests, the sandbox, the day you change PSP — pays
for it.

Declare the capability instead, and extend it:

```ts
// services/Payment.ts — the port. It names no provider.
export default abstract class Payment {
  abstract charge(amountCents: number): Charge;
}

// services/StripePayment.ts — the realization.
export default class StripePayment extends Payment {
  charge(amountCents: number) { return { provider: 'stripe', amountCents }; }
}

// handlers/CheckoutHandler.ts — asks for the port.
export default class CheckoutHandler {
  constructor(private payment: Payment) {}

  /** Charge the cart. */
  async pay() { return this.payment.charge(4990); }
}
```

`this.payment` is a `StripePayment`. **Nothing declares that** — `extends` is the whole
registration, and the boot reads the prototype chain.

## Port, realization, link

Three words, and the rest of these pages use no other:

```ts
abstract class Payment { … }                                   // the PORT — what a class asks for
class StripePayment extends Payment { … }                      // the REALIZATION — what answers it
class Auditing implements Partial<Payment> {                   // a LINK — what stands in front of it
  constructor(private inner: Payment) {}
}
```

- **A port** is what is asked for: `Payment`, and the ports Fougere itself opens — `Dispatcher` around
  every call and `Dispatcher<PostHandler>` around one handler's, `Rest` and `Rest<PostHandler>` around a
  REST request, `Env<Meili>` where a value is read, `Repository<Post>`. Its subject says what it is about:
  an entity for what a thing IS (`Repository<Post>`, `Env<Meili>`), a handler for what RUNS
  (`Dispatcher<PostHandler>`, `Rest<PostHandler>`).
- **The realization** is what answers it — one, written with `extends`, or put there by Fougere when
  nothing is: the rest of the call, the rest of the request, the source, the rows.
- **A link** stands in front of it — none, one or several, written `implements Partial<X>` with an
  `inner`, or `extends X` handing its `inner` to `super` when the port's own code should run through its
  methods. Two are ordered by `ports:`, outside in.

A port with a subject is keyed as it is written, `Rest<PostHandler>`, so no class name can take it.
`fougere ports` prints each one the same way: its links in order, then the realization they reach.

## A port is not a kind of file

There is no `ports/` directory and no `Port(...)` factory. A port is a provider class that
another provider extends: `services/` is scanned as before, and the
relation between two of their classes is what makes one a port. Write the base alone and it
is an ordinary service; write a class extending it and the base becomes the key the
implementation answers under.

This is the same reading the rest of the framework already applies — the type on the
parameter names the **subject**, the container holds the realization. It is how
`Repository<Post>`, `Emit<PostPublished>` and `Facade<PostHandler>` resolve. Providers were
the one case where the type named the realization instead.

## A port under a port

A class that something extends is a port, however deep it sits. With
`StripePayment extends CardPayment extends Payment`, a handler asking for `Payment` and one
asking for `CardPayment` both receive `StripePayment` — and `CardPayment` does not even need
its own file entry to count.

What answers is a class you can build. An `abstract` class in between is never picked: the
scan reads the keyword TypeScript erases, so it stays a port and nothing else. A concrete
class in between is a second candidate for `Payment`, and the boot refuses the pair the same
way it refuses [two implementations](#two-implementations) — `ports:` picks one.

## A framework class is a port too

The condition is one line: **something already answers under that name**. Providers are
registered into the Frond's scope, and Fougere's own builtins sit in its parent — so
`Logger` is a port like `Payment` is, and extending it takes the key over:

```ts
// services/RedactingLogger.ts
export default class RedactingLogger extends Logger {
  constructor(inner: Logger) { super(inner); }

  info(message: string, ...args: unknown[]) {
    super.info(message.replace(/token=\S+/g, 'token=***'), ...args);
  }
}

// any handler, unchanged
constructor(private logger: Logger) {}   // receives RedactingLogger
```

`super(inner)` is what keeps the line whole: `inner` is the logger the app built, and handing it to
`Logger` makes the wrapper write with its name, its [log destinations](/docs/infra/observability#sending-it-somewhere)
and the operation it was written in — so `warn`, which it leaves out, still arrives everywhere. What
the wrapper leaves out runs `Logger`'s own code through its methods: a level `Logger` writes through
`info` would be redacted too. `child()` hands back a child of the real logger, which skips the wrapper.

```ts
// looks like it adds something, and silently drops every destination
export default class AuditLogger extends Logger {
  info(message: string, ...args: unknown[]) {
    audit(message);
    super.info(message, ...args);   // terminal only
  }
}
```

::warning
A subclass that asks for nothing is a second logger, built by the container with no arguments: `super`
runs on that one, which still prints to the terminal but sends nothing to your destinations and no
longer knows the operation. Nothing fails — the lines simply stop arriving elsewhere.

Ask for `inner` and hand it to `super`.
::

The default stays for every Frond that declares no subclass — the override is per Frond,
because a Frond's services are its own. With the default, each class gets a logger named after
it: a line written in `PricingService` reads `app:blog:PricingService`.

A logger built before a level change still obeys it, and so does a child: the level is
consulted rather than copied into each instance, so nothing is rebuilt when it moves. That
belongs to the [lifecycle](/docs/infra/lifecycle), not here.

A repository is not a port by this condition: nothing answers under core's `Repository`. Extending
`Repository<Post>` seats the class on Post's rows, and it answers `Repository<Post>` through that seat —
[repositories](/docs/business/repositories) says how.

## Two implementations

Which realization a deployment uses is not a fact about the code — it changes between dev
and production. So the boot refuses to guess:

```
[claim] StripePayment and OgonePayment both extend Payment, and nothing says which one
answers it. Which realization a deployment uses is not a fact about the code — state it:
ports: { Payment: 'StripePayment' } in fougere.config.ts.
```

Refusing rather than keeping one is deliberate: whichever won would depend on scan order,
and the handler would charge the wrong provider without a word.

```ts
// fougere.config.ts
export default defineFougere({
  fronds: { blog: 'http://127.0.0.1:4100' },
  ports: { Payment: process.env.PSP === 'ogone' ? 'OgonePayment' : 'StripePayment' },
});
```

`ports:` sits beside `fronds:` for the same reason `sources:` does. `fronds:` says where
a **call** goes, `sources:` says where a **row** is, `ports:` says who performs an
**action**. None of the three belongs inside the Frond, which describes itself and not its
deployment — a `billing` Frond naming Stripe would be the one thing Fougere refuses.

Delete `OgonePayment.ts` and the `ports:` line disappears with it: one implementation is
resolved by convention. **The key only exists for the exception.** A key that matches no
port anywhere is reported at boot rather than silently obeyed.

## A chain, not just a choice

The same key says what stands IN FRONT of the realization. A link is recognized by its
form — it extends the port **and** asks for it:

```ts
// services/AuditingPayment.ts
export default class AuditingPayment extends Payment {
  constructor(private inner: Payment, private ledger: Ledger) { super(); }

  charge(amountCents: number) {
    const charge = this.inner.charge(amountCents);
    this.ledger.record(`${charge.reference} ${charge.amountCents}`);

    return charge;
  }
}
```

```ts
ports: { Payment: ['AuditingPayment', 'StripePayment'] }   // outside in
```

`this.payment` is now an `AuditingPayment` holding a `StripePayment`. The handler is
unchanged, and so is the port. Add a third — the order is the list:

```ts
ports: { Payment: ['AuditingPayment', 'TimingPayment', 'StripePayment'] }
//       → auditing(timing(stripe))
```

A link reads what the port says, so what it decides is said in the port's words: a charge
written down, a charge timed, a charge sent to another realization when the first one refused.
A **retry** is not one of them. Whether a failure is worth asking again is in the status the
crossing failed with, and whether asking again is safe is in the idempotency key it carries —
neither of which reaches `charge`. It stands on the crossing: the transport between two fronds
([transport-chain](https://github.com/chok/fougere/tree/main/demos/transport-chain)), or the HTTP client inside `StripePayment`.

`inner` is not `super`. Both classes extend `Payment`, so they are siblings: `super.charge()`
would reach the abstract base, which has no body. The inheritance says only **which key the
class answers under**; the work goes through `this.inner`, which is why the chain can be any
length.

One link needs no declaration — its own signature says it. **Two refuse**, the same way two
realizations do: which one stands in front is an order, and scan order is not one.

A link need not BE a `Payment` to stand in front of one. Written `implements Partial<Payment>`, it
writes only what it changes, and every method it leaves out is the `inner` it was given:

```ts
// services/AuditPayment.ts
export default class AuditPayment implements Partial<Payment> {
  constructor(private inner: Payment) {}

  charge(amountCents: number) { return audit(this.inner.charge(amountCents)); }
  // refund() is not written: it is the inner's
}
```

`extends` says *this is a Payment* — a key, and a realization it may replace. `implements Partial`
says *this stands in front of a Payment* and nothing else. TypeScript erases `implements`, so the scan
reads the clause; a `frond()` written by hand states it — `{ ctor: AuditPayment, deps: ['Payment'],
implements: ['Payment'] }`. Without the clause, a class asking for a `Payment` is an ordinary service,
whatever its methods are called: a link is declared, never guessed.

The two forms differ on what you leave out. Extended, the port's own code runs through your methods:
a `chargeTwice()` the port writes over `this.charge` retries both charges. Implemented, what you leave
out goes to the inner whole, and `chargeTwice()` would reach the realization without passing through
you. A base with state of its own — `Logger` — takes the inner in its constructor, `super(inner)`, so
extending it loses nothing.

## Extending Fougere itself

The framework declares a few ports of its own, and they are extended with the same two
lines. They differ from yours in one way, which decides the rest: **their realization is
handed in, not scanned** — `storageFactory` builds one storage per entity, and no class
declares it. So a class extending one can only stand in front of it.

| | what it is | what a link sees |
|---|---|---|
| `Storage` | where an entity's rows live | every read and write, per entity |

`Storage` is the only one today. `Transport` is **not** extendable this way: a link is
recognized by its prototype chain, so a host port has to be a class, and `Transport` is a
function type. It has its own way in, one section down, and so does HTTP.

```ts
// services/Auditing.ts — in front of EVERY entity's storage
import { Storage } from '@fougere/core';

export default class Auditing extends Storage {
  constructor(private inner: Storage) { super(inner); }

  override async create(row: Record<string, unknown>) {
    await ship(row);

    return this.inner.create(row);
  }
}
```

[Every gesture](/docs/business/storage#the-gestures) is the port's, and this one writes one. What a link does not override reaches the next
one through the base — so a link is as small as what it changes.

It names no entity: `Storage` is the host port, so one class is in front of every entity of **its
own Frond**. `ports: { Storage: ['Auditing'] }` states the chain when there are two, exactly
as above.

The scope is the Frond and no key widens it, because the scope **is** the location: a link
sits beside the code it changes, and goes where that code goes. That is what keeps the
[gradient](/docs/infra/gradient) true — a Frond moved behind `fronds:` would otherwise
silently leave the reach of a link its own code never mentions. A link that must be
everywhere is a **Frond** that is everywhere, which an extension already brings.

::note
The judge stays outside the chain. A row the entity refuses never reaches a link at all —
it is refused at the facade, and what a link receives is the value the schema already parsed.
::

### Reaching a transport, and an HTTP router

Neither is a host port, and neither leaves you without a way in.

A **transport** is swapped whole, by the host that boots the app — the same place `fronds:`
is read, because how a call travels is a deployment fact:

```ts
boot({ root, createContainer, remoteTransport: (url) => mySocketTransport(url) });
```

And an outgoing call to a Frond behind `fronds:` already runs through the app's
middlewares before it reaches the wire, so retrying, timing or logging one is a
[middleware](/docs/business/handlers), not a transport:

```ts
app.use(async (ctx, next) => { /* ctx.address, ctx.operation */ return next(); });
```

What that does **not** reach is the envelope itself — the encoding, the headers, the
connection. For those you are the transport, and you swap it.

**HTTP** is the engine's from start to finish: the app mounts on it with `answer(app, request)`,
and the engine's own middleware stands around it. Leaving a route out is a middleware answering
before `answer` does:

```ts
hono.delete('/api/*', (c) => c.text('Method Not Allowed', 405));
hono.all('/api/*', async (c) => (await answer(app, c.req.raw)) ?? c.notFound());
```

Where an op answers is the Frond's to say, in its `frond.config.ts` — see
[surfaces](/docs/infra/surfaces) for the three parts of a URL and who sets each one.

## Port or Frond?

A remote [Frond](/docs/concepts/frond) also lets you swap what answers, and it swaps the
process too. The line between them is checkable:

- The collaborator **owns data** — entities, tables, seeds → it is a Frond, and `fronds:`
  is its statement.
- It only **acts on the outside world** — a PSP, a mailer, a file store → it is a port,
  and `ports:` is its statement.

Fougere's own ports follow the same rule from the other side: `Storage` is declared by the
framework because it **derives** things from its shape (`Repository`, the DDL, the identity card).
Nothing is derived from `Payment`, so `Payment` is yours.

## What it does not do

A port lets you express a seam. It does not tell you where the seams are — cutting a domain
into collaborators is still your call, and nothing here decides it for you.
