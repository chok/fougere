# Surfaces

A **surface** adapts a protocol to Frond operations in three steps: parse the request, call
*[invoke](/docs/client/invoke)*, then format the response. Business logic remains in the
handlers.

## The framework is not the process

Fougere opens no socket. `@fougere/core` depends on the container and the schema — on
no server. An operation is a function; HTTP is one projection among
several, not the place it lives.

`@fougere/http` declares an interface, `HttpRouter`, and has **no dependencies**, not even
peer ones. You build your Hono or your Fastify, hand it to `createHonoRouter(app)` or
`createFastifyRouter(app)`, and the surfaces program against the interface.
`RequestContext.request` is a Web Standard `Request`.

| What you bring | What Fougere plugs into it |
|---|---|
| Hono, Fastify | `createHonoRouter` / `createFastifyRouter`, then REST |
| your GraphQL server (Apollo, Yoga…) | `registerAll(builder, app)` returns a Pothos schema |
| Nuxt / Nitro | the module mounts the envelope and the REST catch-all |
| nothing at all | `fougere serve` exposes the Frond over JSON-RPC, `fougere call` invokes it from a shell |
| your own loop | [`invoke`](/docs/client/invoke) — a call is a value, not a request |

Two practical consequences. Changing HTTP server moves your routes, not your handlers. And
a test calls the operation directly, without opening a port.

### And the validator goes wherever JavaScript goes

The same declaration runs on both sides of the network. The validation engine
(`@cfworker/json-schema`) was chosen to run in edge environments, and
`@fougere/core/contract` ships as a subpath with no Node builtin in its import graph. The
validator refusing a form in the browser is therefore *the same object* as the one refusing the
body at the façade — not a rule copied faithfully, the class itself.

One caveat, because the nuance matters: it is the **contract** that is ubiquitous, not the
app. Boot reads a Frond's sources with the TypeScript compiler API and jiti, from
`process.cwd()` — that requires Node. What travels to a browser or a worker is the
declaration, its validation and the call format.

The [envelope](/docs/client/queries-commands#the-wire--and-ssr) transmits the call value
directly. REST translates verbs and paths; GraphQL translates a query. These surfaces then
call the same façade.

## REST — mounted

With `protocols: { rest: {} }` in `fougere.config.ts` (and `import '@fougere/adapter-rest'`), every
address gets its routes, entity or not. A URL has three parts, and each one is derived:

| Part | Read from | To change it |
|---|---|---|
| `/api` — where the app mounts REST | the convention | `protocols: { rest: { prefix: '/v1' } }` in `fougere.config.ts` |
| `/blog` — the frond | the frond's name | `protocols: { rest: { path: '/journal' } }` in its `frond.config.ts` |
| `/posts/{id}/publish` — the operation | the class and the signature | `operations: { 'post.publish': { rest: { path, method, status } } }` in its `frond.config.ts` |

The plural is derived from the address (`post → posts`, `category → categories`), so
`checkout.pay` answers `POST /api/shop/checkouts/pay`:

| Route | Operation |
|---|---|
| `GET /api/blog/posts` | `post.list` |
| `POST /api/blog/posts` | `post.create` |
| `GET /api/blog/posts/{id}` | `post.findById` |
| `PATCH /api/blog/posts/{id}` | `post.update` |
| `DELETE /api/blog/posts/{id}` | `post.delete` |
| `GET /api/blog/posts/by-slug` | `post.findBySlug` — explicit query kind below; a named operation wins over `{id}` |
| `POST /api/blog/posts/{id}/publish` | `post.publish(id: Post['id'])` |

The path is read off the signature, never off the operation's name. A parameter typed by the
entity's primary — `publish(id: Post['id'])` — points at one row, so it comes before the
operation: `/posts/{id}/publish`. Another required value comes after it — `byTag(tag: string)`
answers `/posts/by-tag/{tag}` — and an optional one is read from the query string. Typing the
id as `Post['id']` also means its rules are declared once, in the entity, and the value is
judged against them before the method runs.

The method is read off the contract too:

| The operation | Method |
|---|---|
| reads (its kind is `query`) | `GET` |
| its name starts with `delete` or `remove` | `DELETE` |
| points at one row and takes `Partial<Post>` | `PATCH` |
| points at one row and takes only fields of it — `retitle(id: Post['id'], title: Post['title'])` | `PATCH`, the fields in the body |
| points at one row and takes a whole `Post` | `PUT` |
| anything else | `POST` |

The path points at the row, and the body carries what changes:
`retitle` answers `PATCH /api/blog/posts/{id}/retitle` with `{ "title": "…" }`. A parameter that is
not a field of the row — `retitle(id, title, reason: string)` — makes it an action, so `POST`.
`update` merges what it is sent, so it answers `PATCH`; a `PUT` there answers `405`.

The kind comes first. Core reads a finite, whole-word convention (`list…`, `find…`, `get…` are
queries; `create…`, `publish…`, `delete…` are commands). A name with no evidence, or contradictory
evidence such as `getOrCreate…`, is refused by `fougere check` and at boot, with the line to write
— see [business logic](/docs/guides/business-logic). The key is the operation's address and name,
`'post.findBySlug'`, so two handlers of one frond that both have a `findBySlug` are told apart.

The verb is not decorative: the routes above are the canonical table `@fougere/adapter-rest`
derives, and every host matches against it rather than deriving a second one. A path served
under another verb answers `405` with an `Allow` list — it never falls through to a different
operation.

`fougere.config.ts` may also name the route of an operation, for a frond it cannot edit — one a
package brings, like `betterAuth()`:

```ts
protocols: { rest: { overrides: { 'session.get': { path: '/me' } } } },
```

For a frond of the project, the boot refuses it and gives the line to write in that frond's
`frond.config.ts` instead. A host that routes by file — SvelteKit, TanStack Start, React Router,
Next — mounts REST where its route file sits; when that file is not under the prefix, the answer
is a `404` that says so.

Three properties worth knowing:

- **Same façade.** A REST body uses the same validation, unknown-key rejection, and
  collectors as the envelope.
- **Same errors.** Failures project through `toHttpError`: the real HTTP status from the
  [code table](/docs/business/errors), the full typed value in `data`.
- **List shape.** `list` results serialize as `{ items, total, hasMore, endCursor }`.

## GraphQL — a standalone projection

`@fougere/adapter-graphql` derives Pothos types, inputs and CRUD operations from the same
`getFields()` metadata every other adapter reads. Under Nuxt, `protocols: { graphql: {} }`
mounts it on `/graphql`; anywhere else it is a projection you hand to the GraphQL server of
your choice.

### `registerAll` — the whole schema, one call

```ts
import SchemaBuilder from '@pothos/core';
import { registerAll, registerGraphQL } from '@fougere/adapter-graphql';

const builder = new SchemaBuilder({});
builder.queryType({});
builder.mutationType({});

registerAll(builder, app);          // ← every address, every op, every relation

registerGraphQL(router, builder.toSchema());   // mount it on /graphql
```

`registerAll` walks the scanned Fronds. For each address a handler serves, it registers one
field per exposed operation, and a type for each schema those operations return — an
entity's type once, whichever address answers it. `ref` and `many` relations connect the
registered types; computed fields from a [Presenter](/docs/business/presenters) become
resolvers.

Each generated resolver calls the handler façade and therefore keeps its validation,
unknown-key rejection, and collectors. A custom resolver that calls the storage directly must
apply those rules itself. Use `registerType` and `registerOperations` for fields the
projection cannot derive.

Two options, both rarely needed:

```ts
registerAll(builder, app, { surface: 'graphql' });   // honour frond.config.ts surfaces
registerAll(builder, app, { filter: (address) => address !== 'auditLog' });
```

`demos/schema-ecommerce` runs exactly this under Apollo Server on `:4000`.
