Your code names no process, no provider, no database and no protocol. Those
choices live in one file at the root of the project, `fougere.config.ts`, and none of them
changes a line under `fronds/`.

```ts
// fougere.config.ts
import '@fougere/adapter-sql';
import '@fougere/adapter-rest';
import { defineFougere } from '@fougere/core';

export default defineFougere({
  fronds: { catalog: { remote: 'http://127.0.0.1:4620' } },
  ports: { Payment: 'StripePayment' },
  sources: { main: { type: 'sqlite', path: '.data/shop.db' } },
  protocols: { rest: {} },
});
```

Each section below is one of these keys. Leave a key out and you get the default: every
frond in the app's process, the only implementation of each port, rows kept in memory (a
warning says so), and no REST or GraphQL. The imports at the top are what make a source type
or a protocol available: nothing is imported for you, and naming one that is not imported
refuses the boot, naming the import.

## Where each frond runs

`fronds:` gives a frond an address. Start the catalog alone:

```bash
fougere dev catalog --port 4620       # in production: fougere build, then fougere serve
```

and name that address:

```ts
fronds: { catalog: { remote: 'http://127.0.0.1:4620' } },
```

`PriceHandler` keeps calling `this.catalog.list()`; the call now crosses the network.
Remove the line and the catalog runs in the app's process again.

→ [Shape your topology](/tutorial/6-split) · [The gradient](/docs/concepts/configuration)

## What answers a port

When two classes extend `Payment`, the app stops at boot until `ports:` says which one
answers:

```ts
ports: { Payment: process.env.NODE_ENV === 'production' ? 'StripePayment' : 'FakePayment' },
```

The same key stacks classes in front of it, from the outside in. `AuditingPayment` extends
`Payment` and asks for one, so it wraps whatever comes after it in the list:

```ts
ports: { Payment: ['AuditingPayment', 'StripePayment'] },
```

`CheckoutHandler` still asks for `Payment`, and never learns which one it got.

→ [Ports](/docs/concepts/port)

## Where rows live

`sources:` names each place rows live. The one entry with no `rows:` list holds every
entity the others do not; an entry whose `rows:` lists some moves them elsewhere: another database, a
directory of JSON files, or memory.

```ts
sources: {
  main: { type: 'sqlite', path: '.data/shop.db' },
  archive: { type: 'file', path: './archive', rows: ['Order'] },
},
```

`Order` is now read and written as files under `archive/` (with `import '@fougere/adapter-file'`
at the top); every other entity stays in `main`. The repository a handler asks for is the same
either way.

An entity with one instance — a search engine's address, a set of settings — is listed in
`values:` instead, and injected as that value: `env: { type: 'env', values: ['Meili'] }` reads
`MEILI_URL` into the `Meili` a constructor asks for.

→ [Sources](/docs/data/sql) · [Values](/docs/data/values)

## What the app serves

`protocols:` says which APIs the app answers on, beside the calls its own pages make. The
operations are served on each one:

```ts
import '@fougere/adapter-rest';
import '@fougere/adapter-graphql';

protocols: { rest: {}, graphql: {} },
```

Importing the adapter makes a protocol available; naming it here is what serves it — a helper
imported from the package anywhere else opens nothing.

→ [Surfaces](/docs/serve/rest-graphql)

## What stands around `fougere serve`

`fougere serve` is the one host where Fougere *is* the server, so what you would put around a
server of your own goes in `server:` — srvx middlewares, outside in:

```ts
server: { use: [cors({ origin: 'https://app.example.com' })] },
```

They stand around what the process answers browsers — REST, GraphQL, and a request none of them
claims, which a middleware may answer itself (a `/healthz`). The envelope its peers call is not among
them. Under Nuxt, Next, Express or Hono the key is not read: the server is yours, and so are its
middlewares.

→ [Any engine](/docs/adopt/hosts#any-engine)

## The gradient

The gradient is not a feature the framework adds. It is what follows from a Frond naming
no address: since nothing in it says which process it runs in, moving it to another one
changes no business code and no page that calls it.

## Five rungs, and the price of each

Fougere is progressive in one precise sense, and it is the one you can check: **going up a
rung never rewrites what you wrote.** What a rung *does* cost is stated here rather than
left for you to discover.

| | The step | What it buys | What it costs |
|---|---|---|---|
| 0 | one Frond, one process | a running app — no network, no HTTP required | nothing |
| 1 | a second domain, in `fronds/billing/` | an ownership boundary, before any network | no reaching into another Frond's files (`fougere check` reports `cross-frond-import`), and a [collector](/docs/access/authentication#who-calls-collect) has to live in the Frond that consumes it ([why](/docs/access/authentication#a-collector-does-not-cross-a-frond-boundary)) |
| 2 | `fronds: { blog: { remote: '…' } }` | the Frond runs elsewhere, same code | the hop and its JSON; beyond loopback the receiver must be able to [establish its caller](/docs/run/secure), which is two commands at deployment; and two capabilities go missing — a [named surface](/docs/serve/rest-graphql) answers nothing for a remote Frond, and one address per Frond means the same Frond cannot be deployed twice |
| 3 | the Frond moves to its own repo | its own team, release cycle, deployment | the scan no longer reads it: the **contract** must be copied (`fougere sync`), the [carrier](/docs/adopt/another-repository) under fact dispatch is yours to write, and a fact is validated strictly — so its readers deploy before its sender |
| 4 | the Frond is not TypeScript | a Rust or Python host answering the same calls | you honour [the card](/docs/extending/card-and-wire) and the wire yourself |

Rung 0 costs nothing, and it is where every demo in this repository starts. Rung 1 is reversible — a second domain goes beside the first under `fronds/`, and
nothing moves — but it is not free: it is where a collector has to sit with what consumes it,
and the boot says so when it does not. Rung 2 buys the hop and pays two capabilities for
it. Rung 3 is the real border, because it removes the colocation the scan was reading: see
[where the code lives](#where-the-code-lives).

## What the app is made of

An address says where one Frond answers. `fronds:` says what the app is made of, and the
address is one of the four things it can say about an entry:

```ts
// fougere.config.ts
export default defineFougere({
  fronds: {
    shop: {},
    cart:    { extends: 'shop' },      // cart and pricing inherit shop's code
    pricing: { extends: 'shop' },
    blog: { remote: 'http://127.0.0.1:4100' },   // answers elsewhere
    '@fougere/log': {},                // a package: every process logs its calls
  },
});
```

The Fronds under `fronds/` are still found by the scan and need no entry. The tree adds two
things a flat list could not: what a package brings, and **who inherits whose code**.

Nesting says that one thing and nothing else. `cart` resolves the services, repositories,
ports and middlewares `shop` declared — its scope hangs off shop's — and it still reaches
`pricing` through a façade or an announced fact, exactly as a neighbour would. Nesting grants
no right to call.

A Frond a family inherits from serves nothing, and the boot refuses it if it does. With no
façade, nothing can call it and nothing can place it elsewhere: it stands in every process
that carries one of its children, which is what makes inheriting from it safe at every rung
of the gradient.

## Behaviour after a split

| Element | Behaviour |
|---|---|
| results | identical shapes both sides, list results included |
| errors | same `FougereError` with `code`, `message`, and `details`, rebuilt on arrival |
| optional input | absence is `undefined`; JSON omits the property; explicit `null` is preserved |
| state | the consuming app's session reaches remote collectors, carried in the signed envelope |
| caller | `invocation.caller` names the Frond that signed — absent when nothing was established |
| unreachable host | typed `SERVICE_UNAVAILABLE` — status 503 on REST, the error of the JSON-RPC answer on `/_fougere/call`; calls resume after the host restarts |
| transport | timeout and retry on the envelope, without automatic command retries |

## The price of the split

The split adds an HTTP hop and the JSON encoding and decoding it entails. A call remains
a value `(address, operation, invocation)`; the transport frames it and unframes it, then
the receiving side runs the same façade as the local path. The cost therefore depends on
the network, payload size and runtime: Fougere does not claim to make it zero.

No figure is quoted here: this repository ships no benchmark harness, and a number you
cannot re-run is not a measurement.

## One recipient per call

`fronds:` names an address per Frond, and `Facade<T>` resolves to exactly one façade —
`facadeKeyOf` produces one key, the container returns one object. Every call in Fougere
has a single recipient, by construction.

That covers more than it sounds like. A device behind NAT that cannot be called still
declares `fronds:` and sends to a gateway it names: one recipient, and the fact that the
device must open the connection is a deployment property, not a different kind of call.

**Several recipients for one send** comes in two kinds, and only one is here:

| | who determines the recipients | |
|---|---|---|
| a fact — a post was published | nobody: whoever declared an interest | [`Emit<T>` and `Fact<T>`](/docs/concepts/fact) |
| a fleet | the sender names the set | not shipped — `fronds:` names a kind of Frond, never an instance |

A fact names a subject rather than a recipient, so the emitter carries no list of what
follows from its action, and a third reader reopens nothing. A fleet is addressed in the
data instead, the way [emit-fleet](https://github.com/chok/fougere/tree/main/demos/emit-fleet)
reaches one device.

## Limits

Moving a Frond to a remote process adds network latency and failure modes. Fougere exposes
them as typed errors but does not hide them. Local mode remains the reference mode;
`fronds:` changes the topology when the need arises.
