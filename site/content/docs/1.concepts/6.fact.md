A fact says that something happened. Whoever accepts it receives it, and the one who announces it names nobody.

Every other call names **one** recipient: `fronds:` one address per Frond,
[`Facade<T>`](/docs/concepts/facade) one facade. `Emit<T>` names a
**subject** instead, and the number of readers is not the emitter's business.

## Announcing a fact

A fact is an entity, usually derived from the one it is about:

```ts
// fronds/blog/entities/PostPublished.ts
export default class PostPublished extends Post.pick('id', 'title').extend({ at: created() }) {}
```

```ts
// fronds/blog/handlers/PostHandler.ts — the emitter
constructor(private published: Emit<PostPublished>) {}

async publish(id: string, title: string) {
  await this.published({ id, title, at: new Date() });
}
```

```ts
// fronds/search/handlers/IndexHandler.ts — another Frond entirely
async reindex(fact: Fact<PostPublished>): Promise<void> { … }
```

There is no topic, no subscribe call, no listener list. **Accepting a `Fact<T>` IS the
subscription** — the scan reads the signature, and that is the whole mechanism. A fourth
listener does not reopen `PostHandler`.

Nothing marks `PostPublished` as a fact either: it becomes one because somebody writes
`Emit<PostPublished>` or `Fact<PostPublished>` about it. Either end alone is enough, so
removing the emitter does not quietly unsubscribe anybody.

### What `Fact<T>` promises

Not merely "I subscribe". Push is the **strict** mode and pull is a special case of it: an
op written for push is correct when called directly, the reverse is false. So the wrapper
commits the operation to three things no type can check:

| | pull | push |
|---|---|---|
| its return | somebody reads it | nobody |
| an exception | reaches the client | reaches a log |
| how many times | once per request | at least once — **replayable** |

A subscriber is an ordinary operation. It keeps its facade, its validator and its middlewares,
because an emission and a direct call **are the same call**. What it does not have is a caller:
no door open to one names it — REST serves no route to it, GraphQL no field, and the envelope a
page calls refuses it. What enters from outside is a command, which announces. A peer delivering
the fact from another process still reaches it, and so does the terminal, whose caller is the
operator replaying a fact by hand.

### It is a resolver, not a channel

A bus moves messages: a queue, an envelope, a delivery semantic. This has none of that. It
answers *who*, then hands over to the facade that already exists — `resolve` returning N
things instead of one. Consequences, stated rather than discovered:

- **Dispatch is not delivery.** `await this.published(...)` returns once every subscriber
  has been handed the fact, never once any of them is done. A subscriber's failure reaches
  a log; a publication is never hostage to its own indexer.
- **A fact cannot cause itself.** A ring (`A → B → A`) is refused and the message names it;
  a diamond (`A → B → D`, `A → C → D`) stays legal.
- **Nothing is durable, and nothing here will be.** Kill the listener's process and the
  fact is lost. At-least-once means putting a real channel *under* the dispatch — a log, a
  cursor per subscriber, an ack — and none of that belongs to a resolver.

  What Fougere owes such a channel is the ability to answer *did it land?*, and that is
  `app.deliver()`: it waits for every local listener and **rejects** if one refused, so a
  carrier can ack, retry or dead-letter. It is the exact opposite of announcing, on
  purpose — "dispatch is not delivery" protects the emitter, and a carrier is not the
  emitter. See [emit-multirepo](https://github.com/chok/fougere/tree/main/demos/emit-multirepo),
  where a broker of under a hundred lines holds the queue and the Frond holds none of it.

### Waiting for the answers — `Emit<T, A>`

The second type makes an announcement wait. `Emit<T>` hands the fact over and returns nothing;
`Emit<T, A>` waits for every subscriber and gives back what each one answered.

```ts
// fronds/booking/handlers/BookingHandler.ts — asks, and decides with the answers
constructor(private mayBook: Emit<CanBook, Verdict>) {}

async reserve(room: string) {
  const verdicts = await this.mayBook({ room });

  return { room, booked: verdicts.length > 0 && verdicts.every((one) => one.ok) };
}
```

```ts
// fronds/rooms/handlers/RoomsHandler.ts — its return type IS its answer
async check(question: Fact<CanBook>): Promise<Verdict> { … }
```

A subscriber answering `Promise<void>` has no opinion; any other return is one. The law —
unanimity here, a majority or the first refusal elsewhere — is the announcer's, written in its
own code. A subscriber that fails to answer refuses the announcement rather than shrinking it:
handed the survivors, the announcer could not tell them from a complete answer, and silence
would read as consent. And a fact that a carrier would take is refused at boot: a carrier
reaches whoever subscribed elsewhere and brings nothing back.

See [ask-quorum](https://github.com/chok/fougere/tree/main/demos/ask-quorum) — three
processes, and what a missing answer costs.

### Finishing a fact — `Pipe<T>`

An operation taking `Pipe<T>` transforms the fact before any subscriber reads it — a hash, a lookup the announcer should not hold. See [Finish a fact](/docs/behaviour/finish-a-fact).

### Across processes

`fronds:` is the only line that changes. When the listener's Frond is on this disk, it is
scanned, so the emitter knows its signature; declaring it remote only says it is not hosted
here, and its facade resolves to a stand-in that sends the call.

When it is not read here — `fougere serve blog` reads `blog` alone — the listener says it
itself. Each op on a Frond's card states the fact it listens to (`listens`), and the emitter
reads the cards of the Fronds `fronds:` places elsewhere. Either way the fact reaches the
listener as a call, so an `Emit<T, A>` gets its answers back.

A process with no address in `fronds:` cannot be called, so it cannot be reached either: a
listener hosted by a Nuxt app is not reached from a Frond served on its own.

See [emit-split](https://github.com/chok/fougere/tree/main/demos/emit-split) — the same
`PostHandler`, published twice, and the pid in the output says which process indexed.

::demo{name="emit-split"}
::

Beyond two processes, [emit-fleet](https://github.com/chok/fougere/tree/main/demos/emit-fleet)
is a hub and N devices over one socket: facts travel in both directions, a device that
starts before the hub reconnects on its own, and addressing **one** device is done in the
data — because `fronds:` names a kind of Frond, never an instance of one.

### Across repositories

When the listener lives in another repository, finding it is `fronds:`, and carrying the fact across is a carrier you write. See [A frond from another repository](/docs/adopt/another-repository#facts-across-repositories).

### Changing a fact

A fact meets the **same validator** as any other input: a key outside the contract is
`Unknown field`, and that is deliberate. Tolerating it would mean a reader silently
ignoring a field it was meant to handle — the failure you find six months later.

So **adding a field to a fact breaks every reader still carrying the older copy**. The
refusal reaches the reader's log and never the sender, because dispatch is not delivery —
so that line is the whole of the evidence, and it says what to do:

```
ERR [blog] postPublished → index.reindex refused the shape — author: Unknown field.
    If 'postPublished' gained a field, this copy is older than the sender's:
    re-run `fougere sync`.
```

The order is therefore part of the change:

```
1. sender declares the new field
2. every reader: `fougere sync`, then deploy      ← first
3. sender deploys                                 ← last
```

Removing a field is breaking in the same way, and no amount of tolerance would have
helped: the data a reader needs is simply not there.

When you do not control step 2 — another team, a fleet, anything you cannot deploy in
order — **announce a second fact instead of changing the first**. It costs one class and
one `Emit<T>`, both facts run in parallel, and readers move when they move:

```ts
constructor(
  private published: Emit<PostPublished>,        // the old readers, untouched
  private publishedV2: Emit<PostPublishedFull>,  // the new shape
) {}
```

Nothing registers a fact, so a second one adds nothing to unregister later. Delete the
first `Emit` when its last reader is gone.

::note
There is no event bus and no event name. A subscriber is found by the TYPE it accepts, so a
misspelled fact does not compile, the payload is typed, and a listener that fails does not
fail the one who announced.
::
