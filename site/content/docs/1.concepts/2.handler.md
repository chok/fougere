A handler is what your app does: its public methods are the operations, and their signatures are the contract.

A handler groups the operations of one entity. It extends that entity's repository —
`Repository<Post>`, or a `PostRepository` that names its queries — and exposes what it extends: the
five CRUD operations, beside each public method it writes.

```ts
import { Repository, FougereError, ErrorCode } from '@fougere/core';
import Post from '../entities/Post.js';
import User from '../../user/entities/User.js';

export default class PostHandler extends Repository<Post> {
  /** The draft→published transition. */
  async publish(id: Post['id'], user: User): Promise<Post> {
    const post = await super.findById(id);
    if (!post) throw new FougereError({ code: ErrorCode.NOT_FOUND, message: `Post '${id}' not found` });
    if (post.authorId !== user.id) throw new FougereError({ code: ErrorCode.FORBIDDEN, message: 'Only the author can publish' });
    if (post.status === 'published') throw new FougereError({ code: ErrorCode.CONFLICT, message: 'Already published' });

    return super.update(id, { status: 'published', publishedAt: new Date() });
  }
}
```

It serves `list`, `findById`, `create`, `update`, `delete` and `publish`. The rest of what the rows
can do — `findBy`, `findAllBy`, `findByKeys`, `upsert` — is the class's to call and never served.
TypeScript erases `<Post>`, so the scan reads it, and a frond written by hand says it:
`{ ctor: PostHandler, repository: Post }`. The boot hands the rows over once the class is built, after
what its constructor asks for — so a constructor of its own takes its own dependencies only.

Fougere does not require a service layer. A handler can contain an operation's logic
directly or delegate to a service when the domain needs it.

A handler extending `PostRepository` exposes what that one adds as well. To share a query without
exposing it, a handler asks for the repository instead: `constructor(private posts: PostRepository)`.
A handler that wants the five DIFFERENT — published only, a draft visible to its author — does not
extend a repository: it would redefine every one, and TypeScript refuses an inherited method a
different signature. It asks for its repository and writes the ones it serves. No handler ever holds a
`Storage`. The repository's gestures — reads: `list(options?)`, `findById(id)`, `findBy(criteria)`,
`findAllBy(criteria)`. Writes: `create(input)`, `update(id, input)`, `delete(id)`. `output(view)`
returns the same port scoped to a view's fields.

```ts
await this.posts.findBy({ slug });                    // the one row matching
await this.posts.findAllBy({ authorId: user.id });    // every row matching
await this.posts.list({ where: { status: 'published' }, limit: 20, orderBy: 'createdAt' });
```

The façade validates input before calling the method. The storage then applies lifecycle rules
such as automatic values and defaults. The handler's return value is projected and
validated before leaving the façade.

## Where a named query lives

`Storage` is a port: [generic gestures](/docs/extending/source-adapter#the-gestures), no flavour of domain. "The loud readings" is
not one of them, so that query ends up spelled at the call site, in the middle of the
calculation it feeds. `Repository<Entity>` gives it a home:

```ts
// services/ReadingRepository.ts
export default class ReadingRepository extends Repository<Reading> {
  loud(): Promise<Reading[]> {
    return this.findAllBy({ loud: true });
  }
}
```

```ts
// handlers/ReadingHandler.ts — asks the question, never spells the storage
export default class ReadingHandler {
  constructor(private readings: ReadingRepository) {}
  async loud() { return this.readings.loud(); }
}
```

Every entity has one whether or not you wrote the file, and it is **not a facade** — so the
validator stays here, in the handler. See [Repositories](/docs/concepts/repository).

## The four binding rules

Fougere reads your method signature in the project's TypeScript program at boot and binds each parameter from the
invocation — in this order:

| # | Parameter looks like | Bound from |
|---|---|---|
| 1 | a type with a [Collector](/docs/access/authentication#who-calls-collect) **declared in this Frond** (`user?: User`) | the collector's `collect(ctx)` |
| 2 | `ctx: InvocationContext` | the whole invocation |
| 3 | a primitive (`id: string`, `page: number`) | `params[name]`, then `query[name]` — coerced to number/boolean; absent (unless optional) or not a number/boolean → `VALIDATION_FAILED` |
| 4 | anything else (`input: PostDraft`) | the request `body` |

The scanner keeps the AST for what you declared and uses the type checker for what the
declaration means. In particular:

- **A collector binds only inside its own Frond.** Rule 1 reads that Frond's own
  collectors, so a type it cannot resolve falls to rule 4 and the parameter carries the
  request body — see
  [A collector does not cross a Frond boundary](/docs/access/authentication#a-collector-does-not-cross-a-frond-boundary).
- **Aliases resolve.** `user?: User` binds directly, and
  `type CurrentUser = User | undefined; user: CurrentUser` binds to the same collector.
- **The facade is what you declare public.** A `private` or `protected` method is not an
  operation: the scan skips it, because TypeScript already has the word for it. A helper
  the handler names by intent (`mustOwn`, `refuse`) therefore stays a helper, inside the
  class. `#name` works too.

### Canonical absence

The façade normalizes every facade before calling the handler. Absence follows TypeScript,
not the transport:

```ts
foo?: T          // omitted → undefined
foo: T | null    // null is an explicit domain value and stays null
foo?: T | null   // omitted → undefined; explicit null → null
```

JSON cannot carry an `undefined` property, so a remote or browser call omits it. The local
path applies the same rule: `{ foo: undefined }` is canonicalized to `{}`, and reading
`foo` still returns `undefined`. No adapter may translate an explicit `null` to
`undefined`. This applies to primitive bindings and to optional fields inside a body.

## Input validation

When a parameter's type is a schema class (entity or view), the façade validates the body
before calling the method. Invalid input produces `VALIDATION_FAILED` with per-field
details. A `partial()` view uses patch mode.

A primitive typed by a field of an entity obeys that field. The rules stay where they are
declared, in the entity, and the query string is judged against them:

```ts
class Sample extends entity({
  id: primary(text({ format: 'uuid' })),
  age: number({ integer: true, min: 1 }),
}) {}

async match(sampleId: Sample['id'], age: Sample['age']) { … }
// ?age=21  → age is the number 21
// ?age=0   → VALIDATION_FAILED, age: 0 is less than 1.
```

### Unknown keys are refused

A key outside the contract produces an error instead of being silently dropped: a body
`{ …, status: 'published' }` against a view that does not declare `status` comes back as
`VALIDATION_FAILED` (`status: Unknown field`) before the method runs. Accepted input can
therefore be passed to the storage without another projection. `useFormFor` applies the same
validation in the browser before the network request.

## A state changes through an operation, never through a field write

`publish()` illustrates an explicit state transition for an order, subscription, or
ticket. It combines the following rules:

```ts
// the entity — the set of values, and the one it is born with
status: readOnly(oneOf('draft', 'published', { default: 'draft' })),
```

```ts
// the handler — the passage, and the refusal
async publish(id: Post['id']): Promise<Post> {
  const post = await super.findById(id);
  if (post.status === 'published') {
    throw new FougereError({ code: ErrorCode.CONFLICT, message: 'Already published' });
  }
  return super.update(id, { status: 'published' });
}
```

- **`oneOf`** limits the values. A form can render a `<select>`, the DDL emits
  `CHECK status in (…)`, and GraphQL declares an enum type.
- **`{ default: 'draft' }`** is the initial state — a create rule on the
  [lifecycle axis](/docs/concepts/entity), so nobody supplies it.
- **`readOnly`** prevents clients from writing the field: `boundary.in` is `closed`, so `status` is
  absent from every input view. A body carrying it is refused as an unknown key.
- **The named operation** owns the transition and returns `CONFLICT`, projected as
  [409](/docs/concepts/handler), when the current state prevents it.

The method alone controls the transition order. A direct SQL update, or a handler writing
`posts.update(id, { status })` through the repository, can bypass it as long as the value satisfies the
`CHECK`. Fougere does not provide a state graph: the field declares possible values and
the operation controls transitions between them.

## Output view

An operation answering a view — a derivation such as `Post.pick('id', 'title')` — names what leaves:
the façade projects onto it, and a field it leaves out stays home, a computed one included.

```ts
async cards(): Promise<Page<PostCard>> { return Page.of(await this.list()); }  // one op, one view
class PostHandler extends Repository<PostPublic> {}                            // the whole handler
```

The first keeps the full row in the storage, so a validator still reads every field. The second
reads through the view itself, and its rows are those of the entity it was cut from. A second handler
file can therefore define another audience: `handlers/PostHandler.ts` (full) and
`handlers/public/PostHandler.ts` (restricted).

## Refusing

`FougereError` represents a domain error with a typed code. Handlers throw it, and the
following layers retain its code, message, and details. The facade it crosses adds
`address` and `operation` — where the call was refused — so a handler never writes them.

```ts
throw new FougereError({
  code: ErrorCode.CONFLICT,
  message: `Slug '${slug}' is already taken`,
  // details?: [{ path, message }]   — per-field, used by VALIDATION_FAILED
  // cause?: unknown
});
```

Every code and its HTTP status: [Error codes](/reference/errors).

### Error propagation

1. **Handler throws** `FougereError` — the same object whether the Frond is local or remote.
2. **Local call** — the error propagates in memory, untouched.
3. **Remote call** — the transport frames it as a JSON-RPC error (`code: -32000`,
   `data: { code, message, address, operation, details? }`) and the client side
   rebuilds a `FougereError`, including its `details`.
4. **In a page** — `useQuery`/`useCommand` expose it as `error` (a real `FougereError`);
   `useFormFor` maps `VALIDATION_FAILED.details` onto per-field errors automatically.
5. **On the REST surface** — `toHttpError` projects the code to the real HTTP status
   (table above), the full typed value in `data`.

The browser receives the same code, message, and per-field errors whether the Frond is
local or remote. An unreachable host produces a typed `SERVICE_UNAVAILABLE` error.

### Check order

The site's blog checks in this order:

```ts
author: User               // UNAUTHORIZED — a required parameter, refused before the method runs
→ requireOwn(id, author)   // NOT_FOUND, then FORBIDDEN
→ state checks             // CONFLICT (already published, empty draft)
→ realize                  // this.posts.update(…)
```

## Query or command

A handler is a class in `handlers/`. Its public methods are what the rest of the app can
call.

```ts
// fronds/shop/handlers/CartHandler.ts
export default class CartHandler {
  async getTotal(): Promise<number> {
    return 4990;
  }
}
```

Nothing else to write: no route, no registration. The file being in `handlers/` is the
declaration.

The name tells Fougere whether the method reads or writes. A method reads when its name uses
only read verbs — `get`, `list`, `find`, `count`, `search`, `has`, `is`… — and every other
method writes: `create`, `pay`, `publish`, and also `total` or `getOrCreate`. A write is a
command: it answers over `POST` and is never cached. A read taken for a write still works,
which is why the rule leans that way; ASP.NET Web API settles a method with no known verb
the same way.

To make a read of a method whose name does not say so, state it for that one operation,
naming it the way a call does — its address, then its name:

```ts
// fronds/shop/frond.config.ts
export default { operations: { 'cart.total': { kind: 'query' } } };
```

When a read verb of your domain starts many operations, teach it once instead.
A file in the frond's `vocabulary/` exports it, and the process lists it beside its fronds:

```ts
// fronds/shop/vocabulary/verbs.ts
import { Verbs } from '@fougere/core';

export const total = Verbs.term('total', 'query');

// fronds.ts — written by the scan, or by hand
export const vocabulary = [total];
```
