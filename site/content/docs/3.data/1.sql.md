Rows stay in memory until you name a database. One entry in `sources:` puts them in SQLite or Postgres, and `fougere migrate` writes the tables.

An app usually has one database, and declares nothing. When it has several — a legacy
archive, a partner's replica, a warehouse — `sources:` says which entities live where, and
`reads:` says which Fronds may query across them.

## Where rows live

`sources:` names every place rows live. The one entry with no `rows:` list holds every
entity the others do not, so an app with one database writes one line:

```ts
// fougere.config.ts
import '@fougere/adapter-sql';

export default defineFougere({
  sources: {
    main: { type: 'sqlite', path: '.data/app.db' },
    archive: { type: 'sqlite', path: '/mnt/legacy/catalog.db', rows: ['Book'] },
  },
});
```

`Book` now reads and writes in `archive`; everything else stays in `main`. Two entries with no
`rows:` refuse the boot, naming both: nothing would say which one holds the rest. When every entry
lists its rows, none holds the rest, and an entity left out of all of them refuses the boot by
name. No source holding rows at all keeps them in memory, and the boot says so. The
[storage](/docs/extending/source-adapter) a handler receives is unchanged — placement is a fact about the
app, not about the code that uses it. A source may also be an engine the caller built, so a
pool Fougere did not open is still a place rows can live.

Beside `rows:`, an entry lists `values:` — the entities it holds as ONE value each, injected
into the constructor that asks for one: see [Values](/docs/data/values). A source nothing
is written to, such as `env`, never holds the rest.

A [derivation](/docs/concepts/entity) makes no table of its own unless it says `.anchor()`. That
is the entity's own word, never a key of this file: a frond stays mountable without its host
knowing that one of its schemas holds rows.

## The type of a source

`type:` names the engine, and what sits beside it belongs to that engine. Every entry writes
it: an entry with none is refused, naming the types this process answers.

| `type` | Says | Imported from |
|---|---|---|
| `sqlite` | `path` | `@fougere/adapter-sql` |
| `pg`, `mysql`, `mssql` | `url` | `@fougere/adapter-sql` |
| `d1` | `binding` — the Worker's D1 binding | `@fougere/adapter-sql` |
| `file` | `path`, `format` — one JSON or YAML file per row, a directory per entity, one file per value | `@fougere/adapter-file` |
| `memory` | nothing — a Map | `@fougere/adapter-memory` |
| `env` | nothing — the process environment, read-only | `@fougere/adapter-env` |

```ts
import '@fougere/adapter-sql';
import '@fougere/adapter-file';

export default defineFougere({
  sources: {
    main:    { type: 'sqlite', path: '.data/app.db' },
    archive: { type: 'file', path: './rows', rows: ['Snapshot'] },
    legacy:  { type: 'pg', url: process.env.DATABASE_URL, rows: ['Book'] },   // pnpm add pg
  },
});
```

**Nothing is imported for you.** The import is what registers a type and what makes it a word
the config may write: with none, the editor refuses every entry, and the boot refuses
`Unknown source type … To add one, import the adapter that provides it`. Each type declares its entry once,
as a format: the editor reads it as a type, and the boot judges the entry by it — `pathh` is
refused in both, by name, and `{ type: 'pg' }` without a `url` too.

Under Bun, `type: 'sqlite'` opens with `bun:sqlite`, since the native `better-sqlite3` binding does not load there.

`@fougere/adapter-sql` loads on any runtime — Node, Bun, Deno, a Worker. An engine reads what it
needs when it OPENS: SQLite its native driver and `node:fs`, a server its driver from the app
(`better-sqlite3`, `pg`, `mysql2`, or `tedious` and `tarn`), so an app that opens none installs
nothing native, and a missing one is refused with the command that adds it. On a Worker,
`type: 'd1'` reads its binding from `cloudflare:workers` at the first query.

Any other Kysely dialect — libSQL, PGlite, Neon — is built in code and handed in with
`createKyselySource(dialect, 'sqlite')`.

A source states five gestures and only the first is required:

| | |
|---|---|
| `storageFactory` | build the storage of an entity that lives here |
| `pending?` | what the entities ask for and this source does not hold yet — read, never written. The boot refuses when it is not empty |
| `migrate?` | bring the shape of what lives here up to date — run by `fougere migrate --apply`, never by a boot |
| `transacted?` | run one unit of work |
| `close?` | release |

**The absence answers too.** A source that hands out no transaction makes a
[frame](/docs/data/together) compensate instead of transacting, and the boot says which of
the two it built:

```
Together<[RateCard, Ledger], [RateMirror]> — compensated: rateCard in 'archive', ledger in 'main' — no isolation
Together<[Account, Ledger]>                 — transaction, source 'main'
```

Two frames, one app, two guarantees — and the handlers are the same either way.

### Writing one

An adapter supplies a `Store`, four gestures over a keyed collection, and `storageOver` derives
every gesture of the [storage port](/docs/extending/source-adapter#the-gestures) from them. Pages, criteria and
lifecycle stamps are not written twice:

```ts
import { Sources, storageOver, type Store, type Source } from '@fougere/core';

const mapRows = (): Store => {
  const store = new Map();
  return {
    client: store,
    get: async (key) => store.get(key),
    has: async (key) => store.has(key),
    set: async (key, row) => { store.set(key, row); },
    delete: async (key) => store.delete(key),
    all: async () => [...store.values()],
  };
};

Sources.register('memory', (): Source => ({ storageFactory: storageOver(mapRows), name: 'memory' }));
```

That is `@fougere/adapter-memory` in full. The `register` runs when the package is imported, and an
app imports it for that alone (`import '@fougere/adapter-memory'`), so the package says so in its
`package.json` — `"sideEffects": ["./dist/index.js"]` — or a bundler drops the import as unused and the
type answers nothing in a built app. List the entry the app imports and the file that registers.

`all()` reading everything is what bounds a
file-backed source: `list` with a `where` or an `orderBy` filters in memory, which is right
for rows held for their durability and wrong on a hot read path.

## Migrations

The table does not exist yet, and the app does not create it for you: it refuses to start,
and says what is missing.

```
Fougere boot refused: the database is missing 1 change(s) from the entities:
  products — no table
  On your machine: fougere migrate --latest --apply
  On a shared database: fougere freeze, then fougere migrate --apply
```

`npm run migrate` — `fougere migrate --latest --apply` — creates it on your database. Run it each
time an entity gains a field; the boot tells you when.

A rename is declared on the entity, and the rows follow:

```ts
export default class Product extends entity(
  { id: primary(), name: text(), cents: number({ min: 0 }) },
  { previous: { name: 'title' } },
) {}
```

`npm run migrate` renames the column on your database. Before the change leaves it, freeze it:

```bash
fougere freeze v2
```

A deployment runs `fougere migrate --apply`, which applies only what was frozen — a change
nobody froze is refused there, by name. A field that left with no `previous:` is a drop:
`fougere freeze` warns that its column goes at the next `migrate`, and its data with it.
