# La CLI

`@fougere/cli` compose un workspace, héberge une Frond dans son propre process, et appelle
une opération depuis un shell. C'est elle-même une app Fougere — ses commandes sont des
entités avec des handlers sous `fronds/`, ce qui explique que chaque flag ci-dessous soit
un champ de schéma, jugé comme n'importe quelle entrée.

> **Pré-release.** Pas encore sur npm : aujourd'hui elle tourne depuis le workspace
> (`node packages/cli/dist/bin.js …`). Les commandes et flags ci-dessous sont ce qui existe.

## `fougere new` — composer un workspace

```bash
fougere new shop --frond blog --app nuxt
```

Deux phases dans l'ordre des dépendances : les Fronds (tes domaines), puis les apps qui
les consomment. Elle produit un workspace pnpm :

```
shop/
  fougere.config.ts          ← db, auth, topologie
  pnpm-workspace.yaml        ← packages: [fronds/*, apps/*]
  fronds/blog/               ← le domaine
    entities/Post.ts
    handlers/PostHandler.ts
  apps/nuxt/                 ← le consommateur
    nuxt.config.ts
    app/pages/index.vue
```

| Flag | Ce qu'il fait |
|---|---|
| `--frond blog,api:catalog` | les Fronds à ajouter — `template:nom` renomme ; le nom du template est le nom par défaut |
| `--app nuxt:web` | pareil, pour les apps |
| `--bare` | la coquille vide, rien de composé |
| `--flat` | un seul domaine : pas de `fronds/`, pas de workspace — la racine de l'app est la Frond |
| `--local` | lie `@fougere/*` à un checkout local de Fougere (développement) |
| `--force` | écrase un dossier existant |

**Énoncé ou guidé.** Avec `--frond`/`--app`, rien n'est demandé — la seule forme qu'un
script, un job de CI ou un agent puisse piloter. Sans l'un ni l'autre, et avec un TTY,
elle demande template par template. Le flux guidé exige ce TTY et pendrait sans lui :
c'est pourquoi l'énoncé gagne.

**`--flat` choisit une forme, pas une composition.** `fougere new shop --flat --frond blog`
écrit une app Nuxt dont la racine porte le domaine — pas de segment `fronds/`, pas de
`pnpm-workspace.yaml`, un seul `pnpm install` ([la forme à
plat](/fr/docs/getting-started#un-seul-domaine-pas-de-fronds-du-tout)). `--app` est refusé
avec lui : l'app *est* la racine. Un deuxième domaine ira plus tard dans `fronds/billing/`
et la Frond racine ne bouge pas. Le projet généré porte aussi un `tsconfig.frond.json`
dont le `include` nomme les dossiers de la convention, donc `pnpm typecheck` juge le
domaine seul, sans Nuxt.

Ce que la Frond générée enseigne est le point : une entité qui possède sa donnée, deux
vues qui en dérivent (`NewPost` pour ce qu'un client peut proposer, `PostCard` pour ce
qu'une liste émet), et une vraie opération métier à côté du CRUD :

```ts
export class NewPost extends Post.pick('title', 'body') {}

export default class PostHandler extends Crud(Post) {
  async create(input: NewPost): Promise<Post> { … }

  /** La transition draft→published — une opération, pas une écriture de champ. */
  async publish(id: string): Promise<Post> { … }
}
```

Le contrat d'abord, la projection ensuite — pas du CRUD avec un formulaire vissé dessus.

## `fougere serve` — une Frond, son propre process

```bash
fougere serve blog --port 4100
```

Boote cette Frond seule et l'expose en JSON-RPC sur `POST /_fougere/call`. L'app qui la
consomme la nomme dans `remotes:` et rien d'autre ne change — c'est le
[gradient](/fr/docs/infra/gradient), depuis le shell.

Elle ne suit **pas** `remotes:` elle-même : un hôte *est* la Frond, il ne route pas vers
l'extérieur.

> `serve()` écoute `127.0.0.1` par défaut, et c'est ce défaut qui la protège : un
> récepteur en split lit l'identité sur le fil. Ne l'expose pas sur une interface publique.

## `fougere call` — appeler une opération

```bash
fougere call post.list
fougere call post.create --title "Bonjour" --body "…"
```

Elle emprunte le même contrat d'appel que tous les autres consommateurs — l'enveloppe,
les juges, les erreurs typées. Un `VALIDATION_FAILED` dans un shell est la même valeur
qu'une page reçoit.

## `fougere sync` — consommer une Frond distante

```bash
fougere sync blog --from http://blog-service:4100
```

Demande `rpc.discover` à l'hôte et écrit localement les entités reconstruites depuis les
[cartes](/fr/docs/schema/card) qu'il renvoie :

```ts
// .fougere/remotes/blog/entities/Post.ts — généré
import { reconstruct } from '@fougere/schema';
const Post = reconstruct({ /* la carte, telle quelle */ });
export default Post;
```

La classe reconstruite valide localement : le jugement n'est jamais un aller-retour
réseau. Elle écrit aussi `.fougere/remotes.json`, que le module Nuxt lit pour aliaser
`@frond/blog` — les pages importent donc l'entité d'une Frond distante exactement comme
celle d'une locale.

Seules reviennent les entités que l'hôte **sert** vraiment : une entité sans façade ne
déclare aucune opération, et publier sa forme reviendrait à donner à un appelant la
structure de tables qu'il ne pourra jamais atteindre.

## `fougere graph` — lire le modèle

```bash
fougere graph
```

Affiche le graphe des entités — chacune, ce qu'elle référence, combien la référencent —
et, passé six entités, les regroupements de domaine naturels qu'elle trouve :

```
  Post → Author, Category (2 incoming)
  Author
```

C'est l'instrument que décrit la page [chemin le plus court](/fr/docs/concepts/shortest-path),
dans sa première forme : une lecture que n'importe qui rend en une minute, là où le même
jugement énoncé en termes de modèle prenait un senior et une heure.

## `fougere build-frond` — publier les entités d'une Frond

```bash
fougere build-frond blog
```

Compile `fronds/blog/entities/**` vers `dist/` avec les déclarations de types, et pointe
le `package.json` de la Frond dessus. C'est ce qu'un consommateur d'un autre dépôt
installe quand la Frond déménage — la
[dimension organisationnelle](/fr/docs/infra/gradient#où-le-code-vit) du gradient.
