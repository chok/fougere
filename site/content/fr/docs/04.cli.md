# La CLI

`@fougere/cli` crée un workspace, héberge une Frond dans un processus séparé et appelle
une opération depuis un shell. La CLI utilise elle-même des entités et des handlers ; ses
options sont donc validées à partir de leurs schémas.

> **Alpha.** Sur npm sous le tag `alpha` — `npx fougere@alpha` la lance sans installer,
> `npm create fougere` l'entre directement sur `new`. Les commandes et flags ci-dessous
> sont ce qui existe.

## `fougere new` — composer un workspace

```bash
fougere new shop --frond blog --app nuxt
```

Les apps proposées sont les hôtes dont cette CLI dépend et qui expédient un démarreur —
`nuxt`, `next`, `react`, `svelte` et `oclif` aujourd'hui. Chaque démarreur vit dans son propre
paquet, donc un `nuxt.config.ts` s'écrit là où le câblage de Nuxt est connu et nulle part
ailleurs ; `@fougere/vite` n'en expédie aucun, parce qu'il est ce avec quoi les démarreurs React
et Svelte sont *construits*, pas une app à échafauder.

```bash
fougere new shop --frond blog --app "nuxt:web,oclif:ops"
```

La commande crée d'abord les Fronds, puis les apps qui les consomment. Elle produit un
workspace pnpm :

```
shop/
  fougere.config.ts          ← db, auth, topologie
  pnpm-workspace.yaml        ← packages: [fronds/*, apps/*]
  fronds/blog/               ← le domaine
    entities/Post.ts
    handlers/PostHandler.ts
  apps/nuxt/                 ← le consommateur
    nuxt.config.ts
    app/pages/index.vue
```

| Flag | Ce qu'il fait |
|---|---|
| `--frond blog,api:catalog` | les Fronds à ajouter — `template:nom` renomme ; le nom du template est le nom par défaut |
| `--app nuxt:web` | pareil, pour les apps |
| `--bare` | la coquille vide, rien de composé |
| `--flat` | un seul domaine : pas de `fronds/`, pas de workspace — la racine de l'app est la Frond |
| `--local` | lie `@fougere/*` à un checkout local de Fougere (développement) |
| `--force` | écrase un dossier existant |

**Arguments ou mode interactif.** Avec `--frond` et `--app`, la commande n'affiche aucune
question et peut être utilisée dans un script ou en CI. Sans ces options, elle demande les
templates dans un TTY. Le mode interactif n'est pas disponible sans TTY.

**Structure à plat.** `fougere new shop --flat --frond blog`
écrit une app Nuxt dont la racine porte le domaine — pas de segment `fronds/`, pas de
`pnpm-workspace.yaml`, un seul `pnpm install` ([la forme à
plat](/fr/docs/getting-started#un-seul-domaine-pas-de-fronds-du-tout)). `--app` est refusé
avec lui : l'app *est* la racine. Un deuxième domaine ira plus tard dans `fronds/billing/`
et la Frond racine ne bouge pas. Le projet généré porte aussi un `tsconfig.frond.json`
dont le `include` nomme les dossiers de la convention. `pnpm typecheck` peut ainsi vérifier
le domaine sans charger Nuxt.

La Frond générée contient une entité, deux vues dérivées (`NewPost` pour l'entrée et
`PostCard` pour la liste) et une opération métier en plus du CRUD :

```ts
export class NewPost extends Post.pick('title', 'body') {}

export default class PostHandler extends Crud(Post) {
  async create(input: NewPost): Promise<Post> { … }

  /** La transition draft→published — une opération, pas une écriture de champ. */
  async publish(id: string): Promise<Post> { … }
}
```

Les vues définissent les contrats d'entrée et de sortie de ces opérations.

## `fougere serve` — une Frond, son propre process

```bash
fougere serve blog --port 4100
```

Démarre cette Frond seule et l'expose en JSON-RPC sur `POST /_fougere/call`. L'app qui la
consomme indique son adresse dans `fronds:` pour router les appels vers cet hôte. Voir
[le gradient](/fr/docs/infra/gradient).

Elle ne suit **pas** `fronds:` elle-même : un hôte *est* la Frond, il ne route pas vers
l'extérieur.

> `serve()` écoute `127.0.0.1` sauf si `hosts` dit autre chose : un récepteur lit
> l'identité sur le fil, donc le défaut le garde sur la machine et l'élargir est une
> décision écrite.

## `fougere call` — appeler une opération

```bash
fougere call post.list
fougere call post.create --title "Bonjour" --body "…"
```

La commande utilise la même enveloppe, la même validation et les mêmes erreurs typées que
les autres clients. Une erreur `VALIDATION_FAILED` conserve donc le format reçu par une
page.

## `fougere sync` — consommer une Frond distante

```bash
fougere sync blog --from http://blog-service:4100
```

Demande `rpc.discover` à l'hôte et écrit localement les entités reconstruites depuis les
[cartes](/fr/docs/schema/card) qu'il renvoie :

```ts
// .fougere/remotes/blog/entities/Post.ts — généré
import { Card } from '@fougere/schema';

export class Post extends Card.fromDescriptor<{
  id: string;
  title: string;
  createdAt: Date;
}>({ /* la carte, telle quelle */ }).toSchema() {}
```

Une classe, comme celle qu'on aurait écrite à la main : `Post` est la valeur — un validateur qui
valide localement, sans requête supplémentaire vers l'hôte — et le type d'une ligne qu'il
renvoie, si bien que `post.titel` ne compile pas. Les deux se lisent sur la même carte.

À côté, `handlers/PostHandler.ts` énonce ce que la frond sert, pour qu'un consommateur
écrive `Facade<PostHandler>` sans détenir le code du handler :

```ts
export interface PostHandler {
  list(invocation?: Invocation): Promise<Post[] & { total?: number; hasMore?: boolean }>;
  findById(invocation?: Invocation): Promise<Post | undefined>;
}
```

La commande écrit aussi `.fougere/remotes.json`, que le module Nuxt lit pour aliaser
`@fronds/blog`. Les pages utilisent ainsi le même chemin d'import pour une entité locale
ou distante.

La relancer **supprime ce que l'hôte ne sert plus**. Le barrel perd son export tout seul,
mais le fichier restait — et `exports` liste `'./entities/*'` en joker, si bien que
`@fronds/blog/entities/Ticket.js` résolvait encore vers une classe qui valide parfaitement
et dont plus rien ne répond derrière. Seuls les fichiers portant l'en-tête généré sont
supprimés ; ce que vous déposez vous-même dans ce dossier est laissé intact.

L'hôte renvoie les entités associées à une façade, et **les faits que ses fronds
annoncent**. Une entité qui n'est ni l'un ni l'autre n'est pas dans le résultat de
découverte — une forme que personne n'expose et que personne n'a déclarée sortante reste
chez elle.

Un fait n'a pas d'opération : il obtient une classe et aucune interface `Handler` à côté.

```ts
// .fougere/remotes/blog/entities/PostPublished.ts — généré
export class PostPublished extends Card.fromDescriptor<{ id: string; title: string; at: Date }>(…).toSchema() {}
```

Pour qu'un fait qui arrive soit validé, réexportez cette classe dans une de vos propres
fronds — le boot valide contre une entité d'une frond **scannée**, et `.fougere/remotes/`
est un paquet, pas une frond :

```ts
// fronds/search/entities/PostPublished.ts
export { default } from '../../../.fougere/remotes/blog/entities/PostPublished.js';
```

### Les règles

| code | ce que ça veut dire |
|---|---|
| `directory-unreadable`, `handler-parse-failed`, `heritage-unresolved` | ce que le scan n'a pas pu faire — une règle sur une absence n'est fondée que si l'analyse atteste avoir regardé |
| `operation-unbound` | une opération déclare des paramètres et n'a aucun plan de liaison : elle est servie, et elle n'en reçoit aucun |
| `cross-frond-import` | un import relatif qui résout dans une autre frond |

La dernière est un avertissement, pas un refus — ça résout aujourd'hui et l'app tourne. Ce
qu'elle énonce, c'est qu'une **contrainte de colocalisation tient l'application et que rien
ne la déclare** : `'../../user/entities/User.js'` dit que ces deux dossiers sont voisins,
dans une chaîne que le scan, la carte d'identité et `fronds:` ignorent tous. Ça marche
jusqu'au jour où ce dossier n'est plus là, et ça casse alors comme un chemin de fichier,
pas comme un modèle.

`'@fronds/user/entities/User.js'` énonce la même dépendance en termes que le modèle lit, et
c'est la forme qu'écrit [`fougere sync`](#fougere-sync--consommer-une-frond-distante) — elle
survit donc au déménagement de la frond. Le nom résout pareil, que la frond soit locale ou
synchronisée.

## `fougere build` — écrire ce que le scan a trouvé

```bash
fougere build                       # écrit .fougere/scan.generated.ts
fougere build --out src/scan.ts
```

Le scan lit un système de fichiers et un programme TypeScript. Ceci écrit sa réponse, pour qu'un
déploiement ne lise ni l'un ni l'autre — passez le fichier à `createApp` en `scan:` et plus rien
ne touche un disque ensuite.

C'est ce qui rend l'[edge](/fr/docs/infra/deployment) atteignable : un Worker n'a pas de système
de fichiers et ne peut pas expédier un compilateur. C'est aussi pourquoi le scan est
**optionnel** — `frond()` déclare la même chose à la main, et `createApp({ fronds })` boote sans
disque ni `tsc`.

Un fichier généré n'est pas une seconde source. Rien ne le lit que le boot, et le regénérer est la
seule façon de le changer.

## `fougere check` — ce que le scan n'a pas pu faire

```bash
fougere check                 # depuis une racine de projet ; --root en désigne une autre
```

Il **scanne sans booter**, donc il rend compte d'un projet qu'il ne sait pas démarrer.
Sept règles aujourd'hui, chacune sous un nom stable partagé avec les diagnostics du scan :

| signalement | ce que ça veut dire |
|---|---|
| `directory-unreadable`, `handler-parse-failed`, `heritage-unresolved` | ce que le scan n'a pas pu faire — un dossier illisible, un handler qui ne parse pas, un `extends` qu'il n'a pas su suivre |
| `operation-unbound` | une opération dont les paramètres n'ont aucun plan de liaison : elle est servie, et elle ne reçoit rien |
| `input-contract-ambiguous` | deux paramètres pourraient être le contrat d'entrée, la provenance ne peut pas trancher — refusé plutôt que réglé par l'ordre des paramètres |
| `cross-frond-import` | un import relatif qui tombe dans une autre Frond — une contrainte de colocalisation que rien ne déclare, et qui tient jusqu'au jour où cette Frond n'est plus sur ce disque |
| `frond-holds-several-domains` | au-delà de six entités, le même seuil que `fougere graph` |
| `unknown-adapter` | une entité qui adresse un adapter auquel aucune dépendance du projet ne répond — une faute de frappe, ou une dépendance jamais ajoutée |
| `super-linear-pattern` | un `pattern` dont la répétition imbriquée rétro-suit de façon super-linéaire : la regex est fixée à la déclaration, la chaîne testée contre elle est au choix de l'appelant |

Un signalement est **bloquant** ou **avertissement**, et seul un bloquant sort en code non
nul — c'est ce qui le rend utilisable en CI. Une classe de base non résolue sans opération
est ordinaire, et un contrôle qui crie au loup cesse d'être lu.

## `fougere explain` — le contrat sous lequel une opération est servie

```bash
fougere explain Post.publish          # depuis l'intérieur d'un projet
fougere explain Post.publish --root ../blog
fougere explain --names operations    # un nom par ligne, ce que lit la complétion
fougere explain --json
```

Affiche le contrat résolu d'une opération — le handler et la méthode qui s'exécutent, d'où vient
chaque paramètre, quels collectors le remplissent, les surfaces et adapters qui la servent, et les
deux faits sur l'endroit où elle se trouve :

```
Placement: commande / local
Reach:     stock — 1 hop(s)
```

`placement` dit où elle RÉPOND, [`reach`](/fr/docs/infra/observability) où son travail VA.
Commentez une ligne de `fronds:` et la même opération rapporte `0 hop(s)` — rien n'a changé dans
le handler.

Sans opération nommée, elle liste ce que le projet sert. `--json` émet un ordre de clés stable,
qui est le contrat que lit un agent.

## `fougere graph` — lire le modèle

```bash
fougere graph
```

Deux altitudes d'une même image. D'abord où tournent les Fronds et laquelle atteint
laquelle, lu depuis `fronds:` et depuis ce qu'un handler demande à son constructeur — donc
elle répond sans rien de démarré et sans booter :

```
  Fronds
    commande  local   → stock
    stock     remote  http://127.0.0.1:4100
```

Puis les entités, leurs références et le nombre de références entrantes. Au-delà de six
entités, la commande propose aussi des regroupements calculés depuis ce graphe :

```
  Entity Graph
    Post → Author, Category (2 incoming)
    Author
```

Un franchissement dont l'autre côté n'a jamais été scanné est laissé de côté plutôt que
deviné : nommer la Frond derrière une adresse veut dire lire sa carte, et une carte est une
découverte. Une adresse est affichée en hôte et port, jamais entière.

La page [chemin le plus court](/fr/docs/concepts/shortest-path) décrit les usages actuels
et envisagés de ce graphe.

## `fougere load` — le scénario que l'app décrit déjà

```bash
fougere load                          # écrit <racine>/load.js
fougere load --facade http://127.0.0.1:4200/_fougere/call
fougere load --out ""                 # l'affiche au lieu de l'écrire
```

Écrit un scénario [k6](https://k6.io) couvrant chaque opération que la porte par défaut répond. Ce
qu'il dérive, c'est tout ce que le code énonce déjà : les opérations, un corps pour chacune depuis
les champs de l'entité, et l'enveloppe JSON-RPC depuis la seule fonction qui cadre un appel.

Ce qu'il ne dérive **pas**, il le marque à l'endroit où ça se trouve — les poids, les paliers et
les seuils sont des faits sur vos utilisateurs, pas sur votre code :

```js
export const options = {
  // Yours: a flat rate draws flat lines and there is nothing to read in them.
  stages: [ … ],
  // Yours: what counts as too slow is a fact about your users.
  thresholds: { … },
};
```

Il lit le **scan**, jamais un boot : booter exécute les migrations et plante les semences, et une
commande qui décrit un projet n'a rien à écrire dans sa base. Une surface nommée est laissée de
côté — la charge d'une app est ce que sa porte par défaut répond, et compter une surface
compterait une opération deux fois.

Regénérez plutôt que corriger. Un scénario écrit à la main dérive du code, et vous comparez alors
deux scripts au lieu de deux déploiements — ce qui est tout l'enjeu quand le même code tourne
[en un process ou en plusieurs](/fr/docs/infra/gradient).

## `fougere devtools` — ce que les apps en marche dispatchent

```bash
fougere devtools                      # toutes les adresses que ce projet déclare
fougere devtools --url http://127.0.0.1:4100
fougere devtools --json               # une page, puis on s'arrête
```

Lit le journal d'appels qu'une app tient quand elle a monté
[`@fougere/calls`](/docs/infra/observability), via `/_fougere/call` comme n'importe quel
autre consommateur. **C'est le lecteur qui tire** : aucune app ne s'enregistre nulle part,
et une app démarrée seule ne dépend de rien. Le prix, c'est de connaître les adresses — et
le projet les énonce déjà : `fronds:` dit où part un appel, donc dit aussi où l'autre
moitié de cet appel peut être observée.

L'adresse LOCALE est l'exception : un port appartient à l'hôte et aucun projet n'en énonce,
donc `http://127.0.0.1:3000` est une convention — là où Nuxt, Next et le site se tiennent
tous. Un hôte qui sert ailleurs le dit comme il nomme un niveau de log :

```bash
FOUGERE_URL=http://127.0.0.1:4100 fougere devtools
```

`--url` l'emporte toujours sur les deux, et restreint la lecture à cette seule adresse.

Une adresse qui n'a pas répondu est rapportée comme un refus plutôt que comme un silence, et
ces refus ne sont pas un fait mais quatre : pas démarrée, répond mais ne sert aucun journal
d'appels (`Unknown rpc operation 'calls'. It serves discover.`), silencieuse — et une
étrangère, `answered HTTP 404 — not a Fougere receiver?`, ce que dit d'elle-même autre chose
qui occupe ce port.

## `fougere freeze` — enregistrer les formes du jour sous un nom

```bash
fougere freeze v2
fougere freeze v2 --json
```

Écrit deux artefacts, et les deux sont nécessaires. Un **instantané** seul perd l'intention — un
champ disparu plus un champ apparu ne se distingue pas d'un renommage, et les deux produisent des
DDL opposées. Une **étape** seule se corrompt en silence, sans rien pour la vérifier. Rejouer
l'étape par-dessus l'instantané précédent doit reproduire celui-ci, et c'est ce qui attrape une
étape manquante ou un fichier édité à la main.

**Rien n'atteint le disque tant qu'une question est ouverte.** Quand un retrait et un ajout
pourraient n'être qu'un renommage, la commande demande — cette intention est la seule chose que le
code ne détient pas, et elle est partie avec la personne qui a fait le changement.

## `fougere migrate` — réaliser les étapes que la base n'a pas rattrapées

```bash
fougere migrate           # affiche le plan, ne bouge rien
fougere migrate --apply   # l'exécute
```

Lit les versions gelées et le schéma vivant, et rapporte l'écart. Sans `--apply`, rien n'est
écrit — le plan EST la réponse, et le lire est tout l'objet.

Une table fraîche et une table migrée promettent la même chose : un `unique()` qu'une table
vivante n'a jamais porté est proposé en index, et l'instruction échoue sur les lignes qui le
violent déjà. Cet échec est la réponse, pas un accident.

## `fougere keys` — la racine qui signe les habilitations d'un déploiement éclaté

```bash
fougere keys              # une fois, au déploiement
```

Crée l'autorité et sort. Rien ne reste vivant, rien n'est rejoint au boot, et aucun Frond ne
contacte quoi que ce soit pour prouver qui il est. Un receveur finit par détenir **une clé
publique**, donc un Frond habilité demain est admis par un receveur déployé aujourd'hui sans
qu'on touche à sa config.

La clé privée est écrite et jamais affichée : elle signe les habilitations, et une habilitation
est la seule chose qui doive voyager.

## `fougere grant` — se porter garant d'un Frond

```bash
fougere grant billing
```

Lie le nom d'un Frond à une clé fraîche, signée par la racine. C'est ce qui permet à un receveur
d'[établir son appelant](/fr/docs/infra/identity) au lieu de croire une prétention — `serve()`
refuse de démarrer au-delà de la boucle locale sans moyen de vérifier, et c'est contre ceci qu'il
vérifie.

## `fougere completion` — la complétion du shell

```bash
fougere completion zsh >> ~/.zshrc
```

`zsh` et `bash` ; le shell est détecté quand l'argument est absent. Les noms complétés
sortent des mêmes entités que les commandes chevauchent : une nouvelle commande ne demande
pas une seconde liste.

## `fougere build-frond` — publier les entités d'une Frond

```bash
fougere build-frond blog
```

Compile `fronds/blog/entities/**` vers `dist/` avec les déclarations de types et configure
le `package.json` de la Frond. Un consommateur situé dans un autre dépôt peut ensuite
installer ce paquet. Voir [où le code vit](/fr/docs/infra/gradient#où-le-code-vit).
