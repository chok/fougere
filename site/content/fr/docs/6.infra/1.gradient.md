# Le gradient

Le gradient est l'affirmation qui justifie Fougere : un module métier démarre in-process
et part dans son propre process **sans rewrite** — ni du module, ni des pages qui
l'utilisent.

## L'énoncé de topologie

```ts
// fougere.config.ts
export default defineFougere({
  remotes: { blog: 'http://127.0.0.1:4100' },
});
```

La déclaration **est** l'énoncé : une Frond dans `remotes` reste scannée (ses entités
continuent de nourrir formulaires, validation et DI en metadata) mais n'est pas hébergée
localement — les appels vers elle voyagent. Commentez la ligne → les mêmes appels
redeviennent des exécutions mémoire directes. **Le code utilisateur ne change pas d'une
virgule** — vérifié sur la démo phare jusqu'au build de production :

```bash
pnpm dev:blog      # la Frond blog seule, dans son process (:4100)
pnpm dev           # l'app — la consomme via la ligne remotes
```

## Le contrat d'appel

Un appel est une valeur : `(entity, operation, invocation)` avec
`invocation = { params, query, body, state }`.

- `createLocalRunner` exécute strictement en local ;
- `createAppRunner` suit la topologie — façades locales, doublures distantes ;
- les transports déplacent la valeur, ne la remodèlent **jamais**.

## Le format du fil

Process-à-process, c'est JSON-RPC 2.0 sur `POST /_fougere/call` :

```jsonc
// → requête
{ "jsonrpc": "2.0", "id": 1, "method": "post.publish",
  "params": { "params": { "id": "…" }, "query": {}, "body": null, "state": { "user": { … } } } }

// ← succès
{ "jsonrpc": "2.0", "id": 1, "result": { "id": "…", "status": "published", … } }

// ← échec métier — ravivé en FougereError côté appelant
{ "jsonrpc": "2.0", "id": 1, "error": { "code": -32000,
    "data": { "code": "CONFLICT", "message": "Déjà publié",
              "entity": "post", "operation": "publish" } } }
```

`method` est `entity.op` ; `params` est l'invocation **intouchée**. Le navigateur parle la
même trame à Nitro — avec une asymétrie : venant de hors-topologie, son `state` est ignoré
et tamponné côté serveur.

## Ce qui est garanti sous un split

| Voyage | Garantie |
|---|---|
| résultats | formes identiques des deux côtés, listes comprises |
| erreurs | même `FougereError` code/message/`details`, ravivée à l'arrivée |
| state | la session de l'app consommatrice atteint les collectors distants |
| host mort | `SERVICE_UNAVAILABLE` typée → vrai 503 dans les pages ; host relancé → récupération, Nuxt intouché |
| sémantique transport | timeout + retry sur l'enveloppe — jamais de retry sur une command |

## Le prix mesuré

Build de production, démo phare : cœur du framework **~47 200 ops/s** (~21 µs/appel —
jugement, binding, collectors, SQLite compris) ; Nuxt in-process **~23 300 req/s** ; split
**~12 900 req/s**. Le split coûte exactement le saut HTTP — aucun impôt du framework
par-dessus.

## Où le code vit

Le gradient a une troisième dimension, organisationnelle : la frontière qui laisse une
Frond changer de process est celle qui la laisse changer de repo. Une Frond qui part dans
son propre repo emporte son équipe, son cycle de release et son déploiement — l'app la
compose via `remotes`, exactement comme ci-dessus, sans voir la différence. Le mécanisme
est le même : les appels passent par les doublures, le contrat voyage en metadata, pas en
code source. L'outillage du flux cross-repo n'est pas encore livré — aujourd'hui, le
split vérifié est celui du monorepo ci-dessus.

## Ce que ce n'est pas

La promesse n'est **pas** que le réseau soit transparent — un réseau tombe, et Fougere le
remonte en erreurs typées plutôt que de prétendre. La promesse est que le domaine et ses
contrats restent stables pendant que la topologie évolue. Le mode local est le mode de
référence ; vous choisissez quand un module mérite son process, et le code était prêt
dans les deux cas.
