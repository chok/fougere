# Surfaces

Toutes les portes d'un Frond sont des **surfaces** — des ponts minces en trois gestes :
*parser* son protocole en valeur d'appel, *[invoke](/fr/docs/client/invoke)*, *formater*
le résultat en retour. Une surface ne contient jamais de logique métier, et toutes mènent
aux mêmes opérations jugées.

L'[enveloppe](/fr/docs/client/queries-commands#le-fil--et-le-ssr) en est une, et pas une
catégorie à part : simplement celle dont **le protocole est la valeur d'appel elle-même**,
donc dont le parser et le formateur sont l'identité. Elle n'a rien à traduire — c'est ce
qui la fait paraître privilégiée. Les pages l'empruntent par défaut ; REST traduit des
verbes et des chemins, GraphQL traduit une requête.

## REST — montée

Le module Nuxt monte un catch-all REST sous `/api/{frond}/{pluriel}` — le pluriel dérive
du nom de l'entité (`post → posts`, `category → categories`) :

| Route | Opération |
|---|---|
| `GET /api/blog/posts` | `post.list` |
| `POST /api/blog/posts` | `post.create` |
| `GET /api/blog/posts/{id}` | `post.findById` |
| `PUT · PATCH /api/blog/posts/{id}` | `post.update` |
| `DELETE /api/blog/posts/{id}` | `post.delete` |
| `POST /api/blog/posts/by-slug` | `post.bySlug` — kebab-case → camelCase ; une opération connue gagne sur un id |

Trois propriétés à connaître :

- **Même façade.** Un body REST rencontre exactement les juges que l'enveloppe impose —
  validation, refus des clés inconnues, collectors. Il n'y a pas de seconde porte plus
  laxiste.
- **Mêmes erreurs.** Les échecs se projettent par `toHttpError` : le vrai statut HTTP de
  la [table des codes](/fr/docs/business/errors), la valeur typée entière dans `data`.
- **Forme des listes.** Les résultats de `list` se sérialisent en
  `{ items, total, hasMore, endCursor }`.

## GraphQL — une projection standalone

`@fougere/schema-graphql` dérive les types, inputs et opérations CRUD Pothos depuis la
même metadata `getFields()` que lisent tous les autres adapters. Il n'est **pas monté par
le module Nuxt** — il se livre comme une projection que vous tendez au serveur GraphQL de
votre choix :

### `registerAll` — tout le schéma, en un appel

```ts
import SchemaBuilder from '@pothos/core';
import { registerAll, registerGraphQL } from '@fougere/schema-graphql';

const builder = new SchemaBuilder({});
builder.queryType({});
builder.mutationType({});

registerAll(builder, app);          // ← chaque entité, chaque op, chaque relation

registerGraphQL(router, builder.toSchema());   // et on le monte sur /graphql
```

C'est tout le pont. `registerAll` parcourt les fronds scannés et, pour chaque entité qui a un
handler, enregistre son type, ses inputs, et un champ par opération que le handler expose. Les
relations déclarées par `ref`/`many` sont câblées entre les types enregistrés ; les champs
calculés d'un [Presenter](/fr/docs/business/presenters) deviennent des resolvers sur le type.

**L'écrire à la main, c'est perdre le juge.** Chaque resolver généré appelle la façade du
handler — la même porte que l'enveloppe et REST, donc la même validation, le même refus des clés
inconnues, les mêmes collectors. Un resolver que vous écrivez vous-même contre l'ORM (ou pire,
contre la base) est une seconde porte sans juge derrière : une `quantity` que votre schéma
déclare `number({ min: 1 })` est tenue sur toutes les surfaces qui passent par la façade, et sur
aucune autre. `registerType` / `registerOperations` servent à ajouter un champ que la projection
ne sait pas dériver — jamais à reconstruire ce qu'elle donne déjà.

Deux options, rarement nécessaires :

```ts
registerAll(builder, app, { surface: 'graphql' });   // respecte les surfaces de frond.config.ts
registerAll(builder, app, { filter: (entity) => entity.name !== 'auditLog' });
```

`demos/schema-ecommerce` fait exactement ça sous Apollo Server sur `:4000`.

Honnêteté pré-release : la surface GraphQL existe comme projection de schéma avec un demo
qui tourne ; un endpoint GraphQL monté par le module Nuxt comme l'est REST n'existe pas
encore.
