# Collectors

Un collector résout un paramètre de handler **par son type** à partir du contexte
d'invocation. Les opérations qui déclarent ce paramètre reçoivent la valeur automatiquement.

```ts
import { Collector } from '@fougere/core';
import type { InvocationContext } from '@fougere/core';
import User from '../../user/entities/User.js';

/**
 * Le middleware auth pose l'user de session sur ctx.state.user —
 * ceci le fait remonter à tout handler qui déclare `user?: User`.
 */
export default class CurrentUserCollector extends Collector(User) {
  async collect(ctx: InvocationContext) {
    return ctx.state.user as User | undefined;
  }
}
```

Dès lors, dans n'importe quel handler de la Frond :

```ts
async mine(user?: User): Promise<Post[]> { … }
async publish(id: string, user?: User): Promise<Post> { … }
```

## Règles de résolution

- Le match est **par type résolu** : `Collector(User)` résout `user?: User`,
  `user: User | undefined` et les alias qui ont le même sens. La classe s'enregistre
  comme `UserCollector` par convention.
- La cible n'a pas besoin de schéma. Rien ne lit ses champs, donc une classe ordinaire
  suffit — `Collector(Ability)` pour une valeur construite depuis l'état à chaque appel.
- **L'absence est `undefined`.** Préférez la forme concise `user?: User`. Le type checker
  résout aussi un alias comme `type CurrentUser = User | undefined`.
- Les collectors sont des classes injectables — déclarez des dépendances de constructeur
  comme d'habitude.

## Le state et le gradient

`ctx.state` est l'état de requête construit par l'application consommatrice, par exemple à
partir de la session. Lors d'un appel distant, cet état est transmis avec l'invocation :
le collector reçoit le même `ctx.state.user` qu'en local.

Ce qu'il peut contenir est **déclaré**, par les extensions du processus, avec des champs :

```ts
extensions: [{ name: 'tenancy', state: { tenant: text() } }]
```

`betterAuth()` déclare `user` et `session` — la session sans son `token` : un processus fait
confiance à celui qui l'appelle, jamais au cookie de la personne derrière.

Le state est jugé **là où il est entré** — dans le processus dont l'hôte l'a rempli, ou dont
un middleware a écrit un membre — et nulle part après :

- **un membre que personne n'y déclare est refusé** — `state.tenant: Unknown field — this
  process declares user, session` ;
- **deux extensions qui déclarent un même membre font refuser le démarrage**, en les nommant ;
- **un processus qui reçoit l'appel ne déclare rien.** Ce qui a traversé a été jugé à son
  entrée, et l'enveloppe prouve quel processus l'a écrit.

Ce qu'un handler LIT est relu par le type qu'il demande : un collector écrit
`Collector(User)` rend ce qu'il a collecté comme un `User`, jugé et reconstruit.
`state.user.since` est une `Date` en local comme à travers le fil, là où il arrivait sous la
forme de la chaîne que JSON en avait faite.

## Un collector ne franchit pas la frontière d'une Frond

Placez le collector dans chaque Frond qui le consomme. Ce qui arrive sinon mérite d'être
dit précisément, parce que ce n'est ni « plus tard » ni « rien » :

- **ce n'est pas au moment du split.** La liaison est décidée au démarrage, dans un seul
  processus, à partir des collectors *de la Frond elle-même* ;
- **le paramètre n'est pas vide.** Un type que la Frond ne sait pas résoudre tombe dans la
  quatrième règle de binding, `body`. Le handler reçoit donc **le corps de la requête** là
  où il attend un `User`.

Autrement dit, `user?: User` déclaré dans une Frond qui n'a pas de `UserCollector`
reçoit ce que le client a envoyé. Un handler qui valide sur `user.role` valide sur une valeur
fournie par l'appelant.
