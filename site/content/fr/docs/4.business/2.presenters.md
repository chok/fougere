# Presenters

Un presenter ajoute des **champs calculés** à ce qu'une entité émet. Chaque méthode est un
champ : le nom de la méthode est le nom du champ, et elle reçoit **toutes les lignes de la
réponse d'un coup**, en répondant une valeur par ligne.

```ts
import { Presenter } from '@fougere/core';
import type { EntityOrm } from '@fougere/core';
import Post from '../entities/Post.js';
import Author from '../entities/Author.js';

/** Alias typé — la DI résout par nom de TYPE, et `AuthorOrm` est la clé du container. */
type AuthorOrm = EntityOrm<Author>;

export default class PostPresenter extends Presenter(Post) {
  constructor(private authorOrm: AuthorOrm) { super(); }

  excerpt(posts: Post[]): string[] {
    return posts.map((post) => post.body.slice(0, 200));
  }

  /** Une lecture pour la page, pas une par ligne — c'est pourquoi la page est l'argument. */
  async authorName(posts: Post[]): Promise<string[]> {
    const ids = [...new Set(posts.map((p) => p.authorId))];
    const authors = await Promise.all(ids.map((id) => this.authorOrm.findById(id)));
    const byId = new Map(authors.filter(Boolean).map((a) => [a!.id, a!.name]));
    return posts.map((post) => byId.get(post.authorId) ?? 'Anonymous');
  }
}
```

Il vit dans le `presenters/` de la Frond, et le scan l'enregistre comme `PostPresenter`. Les
méthodes peuvent être sync ou async, et la classe est injectable comme n'importe quelle
autre — déclare ses dépendances de constructeur par type.

## Pourquoi ce n'est pas un champ de l'entité

Une entité déclare **ce qu'elle possède**. `excerpt` n'est pas une donnée possédée — il se
dérive, chaque fois, de `body`. Le stocker énoncerait deux fois le même fait, et la seconde
copie périmerait. `authorName` est pire : il appartient à une autre entité, donc le
dupliquer laisse traîner les anciennes lignes à chaque renommage d'auteur.

La règle est celle qu'énonce [la philosophie](/fr/docs/concepts/philosophy) : un fait
s'énonce une fois, tout le reste dérive. Le presenter est l'endroit où la dérivation tourne
quand elle ne peut pas être une projection du seul shape — il lui faut de l'I/O, une autre
entité, ou les deux. C'est aussi pourquoi c'est une classe et pas un callback : il prend la
DI, donc il atteint un ORM sans qu'un handler ait à lui en passer un.

## Toutes les portes, la même réponse

Un champ calculé fait partie de la sortie de l'entité, donc il voyage sur les **quatre**
surfaces — l'enveloppe (`useQuery`, `useCommand`, `invoke`), le catch-all REST, un hôte
REST standalone, et GraphQL. Rien à activer.

```ts
const { items } = await useQuery<Post>(Post, 'list');
items[0].excerpt;      // ← présent, exactement comme dans une requête GraphQL
```

> C'est récent. L'enrichissement vivait dans les seules projections REST et GraphQL,
> chacune avec sa copie, donc le même presenter répondait sur deux portes et était
> silencieusement absent de `useQuery`. Deux routes vers une destination sont un défaut du
> cadre selon [son propre critère](/fr/docs/concepts/shortest-path) — ça tourne maintenant
> une fois, à la façade.

## Où ça s'arrête : une vue nommée

Une op qui nomme sa vue de sortie est **fermée** — l'auteur a énoncé exactement ce que
cette audience reçoit, donc un champ calculé qu'il n'a pas listé reste dehors :

```ts
Crud(Post, { list: PostCard })   // list émet PostCard, et rien que PostCard
```

Ouvert est le défaut, et là un champ calculé est un ajout à la sortie de l'entité. Nommer
une audience est ce qui la ferme — la règle même que l'[axe boundary](/fr/docs/schema/entities)
applique aux champs propres de l'entité.

## Ce que ce n'est pas

- **Pas un sérialiseur.** Ce qui peut sortir du tout est l'axe `boundary` ; ce qu'une
  audience donnée voit est une [vue](/fr/docs/schema/views). Un presenter ne fait
  qu'**ajouter**.
- **Pas un endroit pour les règles métier.** Un champ calculé est une lecture. Une
  transition (`publish`) est [une opération, pas une écriture de
  champ](/fr/docs/business/handlers#un-état-change-par-une-opération-jamais-par-une-écriture-de-champ).
- **Pas gratuit, mais plus par ligne.** Une méthode reçoit la page, donc `authorName`
  ci-dessus fait une requête pour 200 posts, pas 200. La forme rend le batch possible, elle
  ne le force pas : `posts.map((p) => this.orm.findById(p.authorId))` dans un champ calculé
  fait toujours N lectures, et rien ne le dit.
- **Pas le droit d'échouer en silence.** Un champ calculé qui plante remonte en
  `INTERNAL_ERROR` en nommant le champ — le domaine l'a produit, donc c'est un bug, pas une
  mauvaise requête.
