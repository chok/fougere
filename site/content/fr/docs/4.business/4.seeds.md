# Seeds

Une seed est un fichier sous `fronds/<nom>/seeds/`, exécuté une fois au boot après la
migration. Elle reçoit `resolve` et parle aux **mêmes façades** que votre app — les seeds
passent par les opérations jugées, pas à côté.

```ts
// fronds/blog/seeds/Post.seed.ts
type Facade = Record<string, (inv?: Record<string, unknown>) => Promise<any>>;

export default async (resolve: <T>(name: string) => T) => {
  const posts = resolve<Facade>('post');

  // L'idempotence vous appartient — ici : ne seeder qu'un monde vide.
  const existing = await posts.list();
  if (existing.length > 0) return [];

  const created = await posts.create({
    params: {}, query: {},
    body: { slug: 'hello', title: 'Hello', body: '…' },
    state: { user: { id: 'seed-author' } },   // le code serveur possède l'invocation
  });

  // La transition passe par la même opération que tout le monde.
  await posts.publish({ params: { id: created.id }, query: {}, body: undefined,
                        state: { user: { id: 'seed-author' } } });

  return [];   // rien à laisser à la boucle de boot
};
```

## Le contrat

- **Export** : `default async (resolve) => rows[]`. Retourner `[]` signifie « tout est
  fait ici ».
- **`resolve('<entité>')`** rend la façade de l'entité — chaque opération prend une
  invocation complète `{ params, query, body, state }`.
- **Le `state` vous appartient** : une seed tourne côté serveur, elle possède donc
  l'invocation — tamponner `state.user` est la manière d'agir *en tant que* quelqu'un à
  travers les opérations jugées (le `publish` ci-dessus vérifie toujours author-only, et
  passe parce que la seed dit qui elle est).
- **L'idempotence** est la responsabilité de la seed ; le garde-fou est un `list()` +
  retour anticipé.

Pourquoi par la façade et pas par l'ORM ? Parce qu'ainsi les seeds exercent les mêmes
juges, tampons et erreurs que le trafic de production — une seed qui marche est une
preuve, pas un contournement.
