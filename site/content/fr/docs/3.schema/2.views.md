# Vues

Une vue est une classe de schéma dérivée. Elle se déclare **depuis** l'entité, jamais à
rebours de ce qu'une requête a sélectionné :

```ts
/** Ce qu'un auteur peut écrire. */
export class PostDraft extends Post.pick('slug', 'title', 'summary', 'body') {}

/** Ce que l'index public montre — pas de body. */
export class PostCard extends Post.pick('id', 'slug', 'title', 'summary', 'publishedAt') {}

/** L'entrée d'une opération de lecture custom. */
export class BySlugInput extends Post.pick('slug') {}
```

Une vue est une classe de schéma complète : elle a `getFields()`, `validate()`, et
s'utilise comme type TypeScript. Les vues se chaînent : `Post.pick(…).partial()`.

## Les quatre dérivations

| Dérivation | Produit |
|---|---|
| `Post.pick('a', 'b')` | ces champs seulement |
| `Post.omit('a')` | tous les champs sauf ceux-là |
| `Post.partial()` | chaque champ optionnel — **valide en patch** : un champ absent signifie « intouché », jamais « forgé » |
| `Post.extend({ extra: text() })` | l'entité plus des champs — c'est ainsi que `User` étend `AuthUser` |

Le mode de la vue voyage avec elle : une vue `partial()` utilisée comme entrée d'opération
valide automatiquement en mode patch.

## Où les vues se branchent

- **Entrées de handler** — déclarez la vue comme type du paramètre ; la façade valide le
  body du fil contre elle avant votre code ([Handlers](/fr/docs/business/handlers)).
- **Sorties de handler** — `Crud(Post, { list: PostCard })` nomme la vue d'une opération ;
  `Crud(Post, PostPublic)` restreint tout le handler ([Handlers](/fr/docs/business/handlers)).
- **Formulaires** — `useFormFor(PostDraft)` dérive ses champs de la vue ([Formulaires](/fr/docs/client/forms)).

## Les projections io

L'axe boundary dérive deux ensembles de champs que toutes les surfaces utilisent :

```ts
inputFields(Post.getFields())    // les champs qu'un client peut ÉCRIRE — readOnly exclus
outputFields(Post.getFields())   // les champs qu'un client peut LIRE  — writeOnly exclus
```

C'est pourquoi un formulaire bâti sur `Post` ne montre jamais d'inputs `status` ou
`publishedAt`, sans aucune configuration par formulaire — la projection est l'énoncé unique.

## Champ ou vue — la partition

`readOnly` / `writeOnly` retirent un champ d'une surface ; `pick` / `omit` aussi. Deux
mécaniques pour « retirer un champ » ? Non — deux **natures**, et savoir laquelle choisir
est tout l'enjeu.

- **boundary** (sur le champ) énonce un **invariant** : « ce champ ne franchit jamais
  cette direction, nulle part ». `writeOnly(password)` — le mot de passe ne sort d'**aucune**
  vue, jamais.
- **pick / omit** (en dérivation) énonce un **choix d'usage** : « pour cette surface-ci, ces
  champs-là ». `Post.pick('id', 'title')` — l'index public, pas les autres.

Ce ne sont pas des synonymes : chacun couvre ce que l'autre ne peut pas.

- **Tout mettre en dérivation** casse sur l'invariant. Sans `writeOnly` sur le champ, il
  faudrait `omit('password')` sur *chaque* sortie ; un oubli = fuite. L'invariant re-déclaré
  à chaque vue, c'est la cohérence à la main — [ce qu'une déclaration unique
  supprime](/fr/docs/concepts/philosophy).
- **Tout mettre sur le champ** casse sur le choix local. Une réponse publique (`id`, `title`)
  et une réponse admin (`+ authorEmail`) ne se marquent pas sur le champ : `authorEmail` est
  dedans ou dehors *selon la vue*. Le forcer sur le champ demanderait un axe par surface — de
  la config, partout.

Le critère, en une question : **vrai partout, ou vrai pour cet usage ?**

| Le fait est… | Il vit… | Exemple |
|---|---|---|
| vrai partout (invariant) | sur le champ — `readOnly` / `writeOnly` | un mot de passe ne sort jamais |
| vrai pour un usage (local) | en dérivation — `pick` / `omit` | cet endpoint ne renvoie que id + titre |

Un invariant porté par le champ **voyage** en prime : il part dans la
[carte](/fr/docs/schema/card) (`x-fougere.boundary`), donc un consommateur écrit dans un
autre langage sait lui aussi que le mot de passe ne sort pas. Une vue dérivée en TypeScript,
elle, ne voyage pas.
