# Comment un schéma bouge

Une entité se décrit telle qu'elle est aujourd'hui. `fougere freeze` enregistre ce qu'elle
**était**, si bien que la différence entre deux moments devient une valeur sur laquelle
quelque chose peut agir.

```bash
fougere migrate --latest --apply  # votre base, pendant que vous itérez
fougere freeze v2                 # fronds/blog/versions/v2/ — dans le changement qui fait bouger une entité
fougere migrate --apply           # toutes les autres bases : ce qui a été gelé, et rien d'autre
```

Une base que quelqu'un d'autre partage reçoit une version, jamais ce qui se trouve sur le disque :
sans `--latest`, `fougere migrate` refuse une Frond jamais gelée, ou dont les entités ont bougé
depuis sa dernière version, et la nomme.

## Un artefact, plusieurs lecteurs

```
fronds/blog/versions/
  v1/  shape.json                  ce que les formes ÉTAIENT
  v2/  shape.json  from.json       …et le pas qui mène ici
```

Les deux sont écrits, et aucun ne remplace l'autre. **Un instantané seul perd l'intention** —
un champ parti plus un champ apparu ne se distingue pas d'un renommage. **Un pas seul se
corrompt en silence** — rien ne le confronte à quoi que ce soit. Ensemble ils portent un
invariant : rejouer le pas sur l'instantané précédent doit redonner celui-ci.

Une migration lit le pas **une fois**, contre les lignes. Le second lecteur est la raison
pour laquelle le pas est un artefact et non un appel de fonction : une ancienne version d'API
encore servie rejouerait le même pas **à chaque appel**, à la porte. **Ce lecteur n'est pas
encore écrit** — et c'est pourquoi la comparaison vit à un seul endroit, car l'écrire deux
fois laisserait les deux diverger sur les deux mêmes formes.

## Un renommage se déclare, il ne se devine jamais

Fougere ne décidera pas que `body` est devenu `content`, même quand c'est la seule
possibilité. Les deux lectures produisent des DDL **opposées** — l'une garde une colonne de
données vivantes, l'autre la jette — et aucune paire de formes ne contient l'intention.

L'entité le dit, à côté du champ :

```ts
export default class Post extends entity(
  { id: primary(), title: text(), content: text() },
  { previous: { content: 'body' } },
) {}
```

`fougere freeze` le lit comme la réponse à sa question, et enregistre le renommage dans la
version. Sur votre propre base, `fougere migrate --latest` le lit contre la **table vivante** :
`body` y est et `content` non, donc la colonne est renommée et les lignes suivent. Une fois
gelée, la déclaration a fait son travail et peut partir — la version la porte jusqu'à toutes les
autres bases.

Une table qui garde une colonne qu'aucun champ ne déclare pendant qu'elle en gagne une, c'est
ce à quoi ressemble un renommage non déclaré, et `fougere migrate` le dit avant de rien
exécuter :

```
▲  posts keeps body, which no field declares, while content is added —
   if one replaces the other, declare it on the entity: previous: { content: 'body' }
```

`fougere freeze` pose la même question quand il coupe une version, et n'écrit rien tant
qu'elle n'est pas réglée :

```
◆  post.body — what happened to it?
   ❯ renamed to content    la donnée le suit
     dropped               la colonne part, et ce qu'elle tenait avec elle
```

## Ce qu'une migration réalise

`fougere migrate` fait deux choses, dans cet ordre : ce qui touche des données vivantes — un
renommage, une suppression — puis la moitié **additive**, qui crée une table manquante et
ajoute une colonne manquante. L'ordre compte : renommée d'abord, une colonne est déplacée
plutôt qu'ajoutée vide à côté de l'ancienne.

La moitié qui touche des données vivantes ne fait que ce qu'un pas — ou un `previous:` — dit :

| Le pas dit | La base fait |
|---|---|
| `renamed` | `ALTER TABLE … RENAME COLUMN` — la donnée suit |
| `removed` | `DROP COLUMN` |
| `added`, optionnel | rien ; la moitié additive s'en charge |
| un index qui apparaît | rien ; la moitié additive propose tous les index déclarés |
| une `boundary` qui bouge | rien — qui peut lire un champ n'est pas dans une colonne |

La comparaison lit les **quatre axes**, pas seulement la forme : un index, un groupe unique,
une relation, un lifecycle et une boundary sont des différences aussi, et un pas qui ne
rapportait que la forme répondait au quart de la question.

Tout le reste est refusé **en le nommant**, et en une fois plutôt qu'un à la fois :

- **un champ requis sans défaut** — les lignes existantes n'ont rien à mettre dedans.
  Déclarez `text({ default: … })`, la même réponse qu'une migration donne quand on ajoute une
  colonne `NOT NULL` à une table qui a déjà des lignes.
- **un champ devenu requis** — même raison, dans l'autre sens.
- **un type qui bouge** — aucune conversion ne se dérive de deux formes.
- **une borne resserrée** — la porte la fait respecter ; la table garde son ancien `CHECK`
  jusqu'à ce que vous la migriez vous-même.
- **un groupe unique qui bouge** — les lignes déjà stockées peuvent le contredire, donc
  ajouter la contrainte est une décision sur les lignes, pas sur le DDL.
- **une relation qui bouge** — une clé étrangère est une contrainte, et rien ici n'en altère.
- **un défaut qui bouge** — la table garde l'ancien ; rien ici n'altère un `DEFAULT`.
- **un index qui disparaît** — rien ne supprime un index aujourd'hui, la table le garde.

Un plan qui porte un seul refus n'exécute **rien**. Un renommage à moitié fait est pire que
pas fait : la donnée finit dans une colonne dont plus rien ne connaît le nom.

## Rejouer ne coûte rien

Lancez `migrate` deux fois et le second passage répond *up to date*. Il n'y a aucun registre
des migrations appliquées — un changement est sauté parce que **les colonnes elles-mêmes**
disent qu'il a eu lieu : un renommage dont l'ancien nom a disparu a été fait, et une table
qui n'existe pas encore est créée sous sa forme finale.

C'est pour ça que la chaîne est lue entière et **composée** en un seul pas plutôt que rejouée
pas à pas : un champ renommé deux fois est suivi jusqu'au nom sur lequel il finit, le seul
dont les tables puissent répondre. Un nom intermédiaire qu'elles n'ont jamais porté n'est pas
une question qu'on peut leur poser. Rien n'a besoin de
savoir à quelle version la base est assise, et une colonne que quelqu'un a renommée à la main
est vue plutôt que contredite. Un registre serait un second enregistrement d'un fait que les
colonnes portent déjà, et les deux divergeraient le jour où ils ont divergé.

## Le démarrage lit, il n'écrit jamais

**Rien ne migre au démarrage.** Un démarrage compare la base aux entités et refuse quand
elle est en retard, en nommant ce qui manque :

```
Fougere boot refused: the database is behind the entities (2):
  products — no table
  orders.total — no column
  Read the plan: fougere migrate — then write it: fougere migrate --apply
```

Toutes les autres étapes d'un démarrage vérifient et refusent ; celle qui écrivait était aussi
celle que deux répliques se disputaient, et celle qui servait une base vide à côté de la vraie
avec un démarrage au vert. Écrire le schéma est une étape que vous lancez — en développement
`pnpm migrate`, dans un déploiement [une étape de release](/fr/docs/infra/deployment) avant que
les serveurs démarrent.

Un process dont la base naît avec lui — `path: ':memory:'`, un test — n'a personne d'autre
pour la migrer, donc il dit qu'il écrit la sienne : `extensions: [migrating(storage.migrate)]`,
ou `migrates: true` pour `bootApp` et `configureFougere`.

**Un gel n'est pas un artefact de build.** Il est committé, parce qu'il enregistre un passé
qu'aucun code présent ne sait régénérer — contrairement à [la carte
d'identité](/fr/docs/schema/card), dérivée des entités d'aujourd'hui et redérivable à tout
moment. On le coupe dans chaque changement qui fait bouger une entité, parce que c'est ce
qu'un déploiement applique : une base en retard de trois versions suit toute la chaîne,
renommages et suppressions compris, longtemps après que `previous:` a quitté l'entité.

Ensuite : [La carte d'identité](/fr/docs/schema/card) — la même idée à travers les process
plutôt qu'à travers le temps.
