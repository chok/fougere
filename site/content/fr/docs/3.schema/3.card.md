# La carte d'identité

Une entité déclarée en TypeScript ne voyage pas : c'est une classe, avec des thunks et des
fermetures. Sa **carte** voyage — un document JSON qui décrit la même chose, et depuis
lequel un consommateur rebâtit un schéma vivant.

C'est la contrepartie structurelle de Standard Schema : là où `~standard` est l'interface
opaque et vivante « je sais valider », la carte est la description transparente et
sérialisable qui traverse le fil.

```ts
import { describe, reconstruct } from '@fougere/schema';

const card = describe(Post);       // schéma → document JSON
const Rebuilt = reconstruct(card); // document → schéma vivant (validate + from)
```

Les deux fonctions sont duales et **uniques** : `describe` est le seul sérialiseur
canonique (les adaptateurs l'appellent au lieu d'en recopier un), `reconstruct` le seul
reconstructeur. Ce qui traverse est reconstitué **chez le consommateur** — la validation
n'est jamais un aller-retour réseau.

## La structure

La carte est un document JSON Schema valide. L'axe `shape` **est** ce vocabulaire, donc
ses mots-clés vivent au niveau supérieur du champ ; les trois autres axes vivent sous la
clé d'extension `x-fougere`.

```jsonc
{
  "title": "post",
  "type": "object",
  "properties": {
    "id": {
      "type": "string",
      "x-fougere": {
        "role": { "primary": true },
        "lifecycle": { "create": { "generate": "cuid2" } }
      }
    },
    "title": { "type": "string", "minLength": 3, "maxLength": 120 },
    "status": { "type": "string", "enum": ["draft", "published"] },
    "publishedAt": {
      "type": ["string", "null"],
      "format": "date-time",
      "x-fougere": { "lifecycle": { "update": "forbidden" } }
    },
    "secret": { "type": "string", "x-fougere": { "boundary": { "out": "closed" } } }
  },
  "required": ["title", "status"],
  "x-fougere-version": 1,
  "x-fougere-vendor": "fougere"
}
```

Un champ nullable se replie dans l'union `type: ["T", "null"]` — la nullité est du shape,
donc du JSON Schema standard. Un objet embarqué (`json(Entity)`) porte ses `properties` et
son `required` imbriqués, eux aussi purement shape.

## Les trois axes sous `x-fougere`

Les formes normales **sont** la forme du fil : des tokens nommés, du JSON pur. Il n'y a pas
de jumeau descripteur à maintenir — elles voyagent verbatim.

| clé | valeurs | ce que ça énonce |
|---|---|---|
| `role.primary` | `true` | identité — le système la possède |
| `role.unique` / `role.index` | `true` | contraintes de stockage |
| `role.relation` | `{ to, kind: 'one'\|'many', onDelete? }` | `to` est un **nom**, pas un schéma inliné |
| `lifecycle.create` | `{ value }` \| `'now'` \| `{ generate }` \| `'optional'` | qui écrit à la création, et quand |
| `lifecycle.update` | `'now'` \| `'forbidden'` | qui écrit à la mise à jour |
| `boundary.in` | `'closed'` \| `{ decode }` | lecture seule, ou conversion entrante nommée |
| `boundary.out` | `'closed'` \| `{ encode }` | écriture seule, ou conversion sortante nommée |

Une clé absente vaut « ouvert » : pas de `lifecycle.create` signifie que l'appelant doit
fournir la valeur ; pas de `boundary` signifie identité dans les deux sens.

Seul un `boundary` **explicitement déclaré** est émis. Le défaut dérivé du shape (un champ
`format: date-time` décode en `Date`) n'est pas transporté : il est re-dérivé à la
reconstruction. Convention plutôt que configuration, jusque sur le fil.

## `required` ne veut pas dire ce que JSON Schema croit

C'est le seul endroit où la carte s'écarte de la lecture standard, et il faut le savoir
pour en produire une.

`required` liste **les noms qu'un appelant doit fournir à la création** — ceux dont aucune
règle `lifecycle.create` ne répond de l'absence, et qui ne sont pas une relation `many`
(absente → `[]`). C'est plus étroit que le `required` de JSON Schema, qui est
context-free et répond « qu'est-ce qui est toujours présent en lecture ? ».

Conséquence à ne pas manquer : un champ **nullable reste requis**. L'appelant peut fournir
`null`, il ne peut pas omettre la clé. Présence et nullité sont deux axes distincts.

## Le bundle — plusieurs entités, relations comprises

`describeSet` produit un document `$defs` auto-suffisant, chaque entité sous son nom en
minuscules — exactement le nom qu'un `relation.to` porte.

```ts
const bundle = describeSet({ post: Post, author: Author });
const { post, author } = reconstructSet(bundle);
```

Une relation est un **pointeur**, jamais un sous-schéma inliné : `Post → Author → Post`
fait deux références, pas une imbrication infinie. `reconstruct` seul laisse les relations
en simples noms ; `reconstructSet` les résout, et le `to()` reconstruit rend la vraie
entité cible — ce dont les adaptateurs ont besoin.

## Les pertes honnêtes

Une carte est de la donnée. Ce qui est vivant ne traverse pas, et le dire vaut mieux que
le laisser découvrir :

- **une relation devient un nom.** Le thunk `() => Author` n'existe plus ; `reconstructSet`
  le rétablit à l'intérieur d'un bundle, pas au-delà.
- **un générateur ou une conversion custom voyage par NOM**, re-résolu contre le registre
  du consommateur. Un nom inconnu échoue **fort et localement** (« unknown generator »)
  plutôt qu'en silence chez le voisin.

C'est la raison pour laquelle les axes n'acceptent jamais de fermeture : une fonction
disparaîtrait sans bruit à la sérialisation, et c'est le frond distant qui paierait.

## `rpc.discover` — la carte d'une app entière

Un hôte répond à l'opération réservée `rpc.discover` par ce qu'il héberge : ses fronds,
leurs entités, les opérations que chaque façade expose, et la carte de chaque schéma.

```jsonc
{
  "fronds": [{
    "name": "blog",
    "entities": [{ "name": "post", "ops": ["list", "findById", "publish"], "schema": { … } }]
  }]
}
```

C'est ce que le routeur de doublures interroge au premier appel qu'il ne sait pas placer :
la clé déclarée dans `remotes` n'est qu'une étiquette pour une adresse — **la carte décide
quelles entités vivent derrière**.

## Écrire un Frond ailleurs

Rien de tout cela ne suppose TypeScript. Un frond écrit dans un autre langage entre dans
la topologie s'il honore trois choses :

1. **le fil** — `POST /_fougere/call`, JSON-RPC 2.0, `method = "entity.op"` ;
   voir [Le gradient](/fr/docs/infra/gradient).
2. **la carte** — `rpc.discover` rend l'enveloppe ci-dessus, `x-fougere-version: 1`.
3. **le vocabulaire d'erreur** — un `FougereError` entier dans `error.data`, dont le `code`
   est un [code sémantique](/fr/docs/business/errors) ; l'entier `-32000` reste celui de la
   spec JSON-RPC.

Le consommateur reconstruit alors le schéma et **juge en local** : les mêmes règles, sans
avoir jamais vu une ligne du langage d'en face.

`demos/rust-frond/` en est un, en Rust — une entité, trois opérations, aucune classe
`entity({...})` nulle part.
