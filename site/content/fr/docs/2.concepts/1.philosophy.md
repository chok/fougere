# Philosophie

La plupart des frameworks vous tendent des moyens d'exécution : pages, routes, endpoints,
tables, caches. Fougere vous tend un **modèle applicatif** — données, opérations,
contrats, frontières — et le projette vers ces moyens. Cette page est le modèle mental
que tout le reste de la doc suppose.

> Décrire l'application comme un système de données, d'opérations, de contrats et de
> frontières — puis projeter ce modèle vers Nuxt, HTTP, SQL, cache ou un process distant.

## Les déclarations se projettent

Une [entité](/fr/docs/schema/entities) est une déclaration, pas une table. La table est
une de ses *projections* — avec la validation, le type TypeScript, le contrat de
formulaire, le type GraphQL. Vous écrivez la déclaration une fois ; tout l'aval dérive,
donc rien ne peut diverger. Quand vous vous apprêtez à énoncer le même fait à un deuxième
endroit (un validateur ici, une colonne là), arrêtez-vous : trouvez la déclaration dont
il devrait dériver.

## Des opérations, pas des écritures de champ

Le vocabulaire d'une Frond : **commands** (intentions qui changent le système),
**queries** (lectures cacheables) et, quand le système grossit, **events** (faits
produits par une command). `Crud(Post)` vous donne les cinq opérations standard pour
démarrer — puis votre domaine gagne de vrais verbes :
[`publish`](/fr/docs/business/handlers) est une opération avec un juge et une transition,
pas un client qui écrit `status: 'published'` dans un champ. Quand vous exposez une
écriture de champ brute pour quelque chose qui a un sens métier, nommez l'opération à la
place.

## La Frond possède

La logique métier vit dans des [Fronds](/fr/docs/concepts/frond) — des frontières de
propriété portant entités, opérations, policies et persistance. Une Frond ne fouille
jamais dans les entrailles d'une autre ; l'app compose des Fronds au lieu de reconstruire
le domaine à coups de pages, de fetchs et de stores. La frontière est ce qui permet à un
module de bouger plus tard sans rien déchirer.

## La topologie est de la configuration

Où tourne une Frond — in-process, son propre process, une autre machine — s'énonce dans
[une ligne de config](/fr/docs/infra/gradient), pas dans votre code. Le code métier ne
connaît jamais sa topologie ; les appels passent par la même enveloppe dans tous les cas,
et un appel local est une exécution mémoire directe, pas du RPC caché. Décidez le split
quand l'équipe ou la charge l'exige — le code était prêt de toute façon.

## Un état est perdable ou durable

Chaque état répond à une question : *que se passe-t-il si on le perd ?* Comportement
inchangé → c'est un **cache**, dérivé d'une query, et le framework peut le vider à tout
instant (il le fait : chaque redémarrage en dev, chaque deploy). Comportement changé →
c'est une **entité**, même si elle vit dix secondes : un code OAuth à usage unique est
une entité `{ code, userId, expiresAt }` à lecture destructrice, et cette phrase est déjà
l'architecture — durable, migrable, observable, sans infra dédiée. Il n'y a pas de
troisième catégorie, et c'est ce qui rend la question toujours tranchable.

## La vérité voyage, la réalisation varie

Le principe de packaging derrière tout ce qui précède :

- **Embarqué** — ce qui doit être *une seule vérité* : le juge, les projections io, la
  metadata. Livrés dans le schéma, ils voyagent avec la classe. Une implémentation de
  référence, **exécutée partout** : le même juge tourne dans le navigateur, à la façade,
  dans une Frond distante. Une vérité, N copies, zéro dérive.
- **Externalisé** — ce qui *réalise localement* : le storage, le transport, le rendu. Là,
  la variation est le but — SQLite aujourd'hui, Postgres demain, GraphQL ou REST selon la
  surface. Interchangeable précisément parce que ce n'est pas normatif.

Le juge est embarqué parce qu'un juge qui varie n'est plus un juge ; le storage est
externe parce qu'un storage qui ne peut pas varier n'est plus un adapter. C'est le
[gradient](/fr/docs/infra/gradient) appliqué au packaging : les dérivations pures de la
déclaration sont invariantes à la topologie ; les réalisations vivent là où on les
branche.

## L'ordre de conception

Quand une décision de design se présente, poser les questions dans cet ordre :

1. Quel est le concept applicatif ?
2. Quelle est sa frontière de propriété ?
3. Quels contrats doit-il exposer ?
4. Quelles opérations changent l'état ?
5. Quelles queries le lisent ?
6. Qu'est-ce qui invalide quoi ?
7. Quel adapter exécute ou projette ce modèle ?

Commencer par la route, la page, la table ou le transport, c'est laisser l'outil dicter
l'architecture.

## Position

Fougere n'est pas un Nuxt plus pratique, un Nest moins verbeux ou un générateur CRUD.
L'ambition est plus étroite et plus dure : **un modèle d'application pour produits
data-intensive, capable de se projeter vers plusieurs runtimes et topologies sans perdre
ses frontières métier.**
