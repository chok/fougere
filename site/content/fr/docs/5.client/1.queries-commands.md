# Queries & commands

Une page parle à une Frond par deux gestes duals : **query** (lit) et **command** (écrit),
liés par l'entité. La désignation est *classe + verbe* — la classe d'entité importée porte
la metadata, son nom est la clé d'enregistrement. Pas de chaîne à parser, pas de client
généré.

```ts
import Post from '@frond/blog/entities/Post';

const { items, total, hasMore, loading, error } = await useQuery<PostCard>(Post, 'list');
const publish = useCommand<Post>(Post, 'publish');
await publish.execute({ params: { id } });
// → toutes les queries montées sur Post se revalident, automatiquement
```

## useQuery

```ts
useQuery<T>(Entity, op, input?, opts?)
// input: CallInput | () => CallInput      CallInput = { params?, query?, body? }
// opts:  { immediate?: boolean }          immediate: false → ne pas tirer au montage
```

Retour (tout est réactif) :

| Clé | Type | Notes |
|---|---|---|
| `data` | `Ref<T \| null>` | le résultat brut (ops à objet unique : `findById`, `bySlug`…) |
| `items` | `ComputedRef<T[]>` | normalisation de liste : un tableau nu **ou** un `ListResult` se lisent pareil |
| `total`, `hasMore` | du `ListResult` | présents quand l'op en rend un |
| `loading` | `Ref<boolean>` | |
| `error` | `Ref<FougereError \| null>` | l'erreur typée ravivée ([Erreurs](/fr/docs/business/errors)) |
| `refresh` | `() => Promise<void>` | revalidation manuelle — rarement utile, voir le lien |

Un **input getter** rend la query réactive à ses arguments :

```ts
const { items } = await useQuery<Hit>(Post, 'searchByTitle',
  () => ({ body: { title: submitted.value } }),
  { immediate: false });
```

## useCommand

```ts
useCommand<T>(Entity, op)
// → { execute(input?): Promise<T>, loading: Ref<boolean>, error: Ref<FougereError | null> }
```

`execute` rejette avec la même `FougereError` qu'il range dans `error` — attrapez-la en
try/catch ou lisez la ref, les deux styles marchent.

## Le lien

**Une command réussie sur X revalide toutes les queries montées sur X.** La désignation
donne l'entité des deux côtés, il n'y a rien à déclarer — publiez un post, la liste qui
affiche son badge se met à jour sans reload. Ce cache est *perdable* : le vider ne change
jamais le comportement, seulement la latence.

## Le fil — et le SSR

Le navigateur POSTe la même trame JSON-RPC que le transport process-à-process
(`POST /_fougere/call`, `method: "post.list"`, `params` = l'invocation).

> **C'est ce qu'on appelle l'enveloppe** : la porte unique `POST /_fougere/call`, et le
> chemin que prennent `useQuery`, `useCommand` et `invoke`. Le reste de la doc l'emploie
> comme ça, par opposition aux [surfaces](/fr/docs/infra/surfaces) — REST sous
> `/api/{frond}/…`, GraphQL. Toutes mènent aux mêmes opérations jugées ; l'enveloppe est
> celle que les pages empruntent par défaut.

Deux propriétés :

- **En SSR**, le même appel se replie en exécution in-process — pas de réseau, pas de port.
- **Le `state` ne vient jamais du fil** : le navigateur est hors topologie, la session est
  tamponnée côté serveur depuis le contexte de requête. Une page ne peut pas forger qui
  elle est.

La sémantique transport côté client est héritée de l'enveloppe : jamais de retry sur une
command, erreurs typées toujours ([Erreurs](/fr/docs/business/errors)).
