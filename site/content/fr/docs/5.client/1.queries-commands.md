# Queries & commands

Une page appelle une Frond avec une **query** pour lire ou une **command** pour écrire.
L'appel nomme une **porte** — une adresse, et le type du handler qui y répond. La page la
nomme une fois, comme un service déclare sa dépendance une fois dans son constructeur.

```ts
import { post } from '@fronds/facade';

const { items, total, hasMore, loading, error } = await useQuery(post, 'list');
const publish = useCommand(post, 'publish');
await publish.execute({ params: { id } });
// → toutes les queries montées sur cette porte se revalident, automatiquement
```

`@fronds/facade` est écrit par le scan — un `const` par adresse, portant chacun le handler qui
y répond comme TYPE. Compilé, tout `post` vaut `{ at: 'post' }` : le handler est nommé, jamais
importé, donc aucun code serveur n'atteint le bundle.

Ce que le type apporte est le contrat de la page : quelles opérations existent, ce que chacune
répond, et ce que chacune peut refuser. **Aucune forme de ligne n'est écrite à la main**, ce
qui est tout l'objet : une page qui déclare `interface PostCard { … }` affirme une forme que
rien ne confronte au handler.

```ts
publish.error?.code   // ErrorCode.CONFLICT | ErrorCode.FORBIDDEN | ErrorCode.NOT_FOUND
```

Ce sont les codes que `PostHandler.publish` lance réellement, remontés depuis les sites de
`throw` à travers les fonctions qu'il appelle. Un `switch` dessus avec un `default` en `never`
cesse de compiler le jour où une opération apprend à refuser autre chose ; un `default:` qui
affiche le message, jamais. La page choisit lequel des deux elle veut.

Une page dont les lignes s'appellent déjà `post` aliase la porte à l'import — `import { post
as postFacade }` — comme toute autre collision de nom se règle.

L'adresse est le nom du handler, pas celui d'une entité — `PostHandler` répond à `post`,
`CheckoutHandler` à `checkout`. Les deux coïncident dès qu'un handler porte le nom d'une
entité, ce qui est le cas de tout `Crud` et de la plupart des autres ; 17 des 41 handlers
des démos de ce dépôt répondent à une adresse qu'aucune classe d'entité ne porte, et
celles-là étaient hors de portée d'une page.

## useQuery

```ts
useQuery(facade, op, input?, opts?)
// facade:  l'un des exports de `@fronds/facade`
// op:    un nom de méthode du handler derrière ; tout le reste ne compile pas
// input: CallInput | () => CallInput      CallInput = { params?, query?, body? }
// opts:  { immediate?: boolean }          immediate: false → ne pas tirer au montage
```

Retour (tout est réactif), où `Answered` est ce que `Handler[op]` rend :

| Clé | Type | Notes |
|---|---|---|
| `data` | `Ref<Answered \| null>` | le résultat brut (ops à objet unique : `findById`, `findBySlug`…) |
| `items` | `ComputedRef<Row[]>` | normalisation de liste : un tableau nu **ou** un `ListResult` se lisent pareil |
| `total`, `hasMore` | du `ListResult` | présents quand l'op en rend un |
| `loading` | `Ref<boolean>` | |
| `error` | `Ref<FougereError \| null>` | l'erreur typée ravivée ([Erreurs](/fr/docs/business/errors)) |
| `refresh` | `() => Promise<void>` | revalidation manuelle — rarement utile, voir le lien |

Un **input getter** rend la query réactive à ses arguments :

```ts
const { items } = await useQuery(post, 'searchByTitle',
  () => ({ body: { title: submitted.value } }),
  { immediate: false });
```

## useCommand

```ts
useCommand(facade, op)
// → { execute(input?): Promise<Answered>, loading: Ref<boolean>, error: Ref<FougereError | null> }
```

`execute` rejette avec la même `FougereError` qu'il range dans `error` — attrapez-la en
try/catch ou lisez la ref, les deux styles marchent.

## Le lien

Une command réussie sur une porte revalide les queries actives de cette même porte. Après la
publication d'un post, les listes de posts sont donc actualisées. Supprimer ce cache ne
change pas le résultat des opérations, mais déclenche de nouvelles lectures.

## Le fil — et le SSR

Le navigateur POSTe la même trame JSON-RPC que le transport process-à-process
(`POST /_fougere/call`, `method: "post.list"`, `params` = l'invocation).

> La documentation appelle **enveloppe** le point d'entrée `POST /_fougere/call` utilisé
> par `useQuery`, `useCommand` et `invoke`. Les [surfaces](/fr/docs/infra/surfaces) REST et
> GraphQL traduisent leurs protocoles vers les mêmes opérations.

Deux propriétés :

- **En SSR**, le même appel se replie en exécution in-process — pas de réseau, pas de port.
- **Le navigateur ne fournit pas le `state`** : le serveur le construit depuis le contexte
  de requête, notamment pour y placer la session.

Le transport client ne relance pas automatiquement une command et conserve les erreurs
typées ([Erreurs](/fr/docs/business/errors)).
