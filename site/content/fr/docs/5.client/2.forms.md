# Formulaires

`useFormFor` est le **contrat** de formulaire — état, validation, soumission, mapping
d'erreurs par champ. Il ne rend rien : la page possède les widgets, le contrat possède la
mécanique.

```vue
<script setup lang="ts">
import Post from '@frond/blog/entities/Post';

const { values, errors, submit, loading, error } = useFormFor<{ id: string }>(Post);

async function onSubmit() {
  const created = await submit();          // null quand un juge a refusé
  if (created) navigateTo(`/blog/edit/${created.id}`);
}
</script>

<template>
  <form @submit.prevent="onSubmit">
    <UFormField label="Titre" :error="errors.title">
      <UInput v-model="values.title" />
    </UFormField>
    <p v-if="error">{{ error.message }}</p>          <!-- échec non-validation -->
    <UButton type="submit" :loading="loading" />
  </form>
</template>
```

## Signature

```ts
useFormFor<T>(EntityOuVue, options?)
// options: {
//   op?: string                        la command du submit — défaut 'create'
//   initial?: Record<string, unknown>  mode édition : l'entité chargée
//   params?: Record<string, string>    désignation de la cible — mode édition : { id }
// }
```

Retour :

| Clé | Type | Notes |
|---|---|---|
| `fields` | `FormField[]` | dérivés des axes io — les champs possédés serveur n'apparaissent jamais |
| `values` | record `reactive` | initialisé depuis `initial` — voir la note sur les défauts |
| `errors` | record `reactive` | chemin de champ → message |
| `submit` | `() => Promise<T \| null>` | voir le cycle |
| `loading` | `Ref<boolean>` | |
| `error` | `Ref<FougereError \| null>` | échec **non-validation** (conflit, host mort) |
| `valid` | `ComputedRef<boolean>` | aucune erreur de champ courante |

Le mode édition se compose avec une query :

```ts
const { data: post } = await useQuery<Post>(Post, 'findById', { params: { id } });
const form = useFormFor(Post, { op: 'update', params: { id }, initial: post.value ?? undefined });
```

## Le cycle du submit

1. **Pré-jugement local** — `Entity.validate(payload)` tourne dans le navigateur avec
   exactement les règles que le handler applique (une déclaration, deux côtés). Les refus
   atterrissent dans `errors` sans aller-retour ; `submit()` rend `null`.
2. **La command** — le payload part par `useCommand(Entity, op)` : une réussite déclenche
   le lien d'entité, les queries montées se revalident.
3. **Jugement distant** — un `VALIDATION_FAILED` en retour est mappé sur `errors` par
   `path`, exactement comme le juge local. **Le formulaire ne sait jamais qui a jugé.**
4. Tout le reste (`CONFLICT`, `SERVICE_UNAVAILABLE`…) atterrit dans `error`, intouché.

## Ce que le formulaire ne fera pas

- **Rendre** — widgets et layout sont app-land, délibérément.
- **Montrer les champs possédés serveur** — les champs `readOnly` sont exclus par la
  projection io ; un statut s'affiche en badge depuis la donnée chargée, il ne s'édite pas.
- **Deviner les labels** — les labels sont l'affaire de votre i18n ; la metadata donne des
  clés stables (entité + nom de champ) où les accrocher.
- **Pré-remplir les défauts déclarés** — et c'est l'affaire des axes, pas un oubli. Un
  `default` sur un champ est une règle `lifecycle.create` : **le storage la réalise**,
  comme il tamponne `createdAt`. Donc `oneOf('draft', 'published', { default: 'draft' })`
  laisse le champ vide dans le formulaire et revient à `'draft'` après l'écriture.
  Le pré-remplir dans le navigateur ferait énoncer à l'état client un fait qu'il ne
  possède pas — et deux endroits répondraient alors à « quel est le défaut », la dérive
  même qu'une déclaration unique existe pour tuer. Le voir avant l'écriture ? Passez-le
  dans `initial` — c'est l'app qui choisit, explicitement.
