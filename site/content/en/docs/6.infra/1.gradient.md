# The gradient

The gradient is the claim that makes Fougere worth building: a business module starts
in-process and moves to its own process **without a rewrite** — not of the module, not of
the pages that use it.

## The topology statement

```ts
// fougere.config.ts
export default defineFougere({
  remotes: { blog: 'http://127.0.0.1:4100' },
});
```

The declaration **is** the statement: a Frond in `remotes` is still scanned (entities keep
feeding metadata to forms, validation, DI) but is not hosted locally — calls to it travel.
Comment the line → the same calls become direct memory execution. **User code does not
change by one comma** — verified in the flagship demo down to the production build:

```bash
pnpm dev:blog      # the blog Frond alone, in its own process (:4100)
pnpm dev           # the app — consumes it through the remotes line
```

## The call contract

A call is a value: `(entity, operation, invocation)` with
`invocation = { params, query, body, state }`.

- `createLocalRunner` executes strictly locally;
- `createAppRunner` follows the topology — local façades, remote doublures;
- transports move the value, **never** reshape it.

## The wire format

Process-to-process is JSON-RPC 2.0 on `POST /_fougere/call`:

```jsonc
// → request
{ "jsonrpc": "2.0", "id": 1, "method": "post.publish",
  "params": { "params": { "id": "…" }, "query": {}, "body": null, "state": { "user": { … } } } }

// ← success
{ "jsonrpc": "2.0", "id": 1, "result": { "id": "…", "status": "published", … } }

// ← domain failure — revived as FougereError on the calling side
{ "jsonrpc": "2.0", "id": 1, "error": { "code": -32000,
    "data": { "code": "CONFLICT", "message": "Already published",
              "entity": "post", "operation": "publish" } } }
```

`method` is `entity.op`; `params` is the invocation **untouched**. The browser speaks the
same frame to Nitro — with one asymmetry: coming from outside the topology, its `state` is
ignored and stamped server-side.

## What is guaranteed under a split

| Travels | Guarantee |
|---|---|
| results | identical shapes both sides, list results included |
| errors | same `FougereError` code/message/`details`, revived on arrival |
| state | the consuming app's session reaches remote collectors |
| dead host | typed `SERVICE_UNAVAILABLE` → real 503 in pages; host restarts → recovery, Nuxt untouched |
| transport semantics | timeout + retry on the envelope — never retry a command |

## The measured price

Production build, flagship demo: framework core **~47,200 ops/s** (~21 µs/call — judgment,
binding, collectors, SQLite included); Nuxt in-process **~23,300 req/s**; split
**~12,900 req/s**. The split costs exactly the HTTP hop — no framework tax on top.

## Where the code lives

The gradient has a third, organizational dimension: the boundary that lets a Frond change
process is the one that lets it change repository. A Frond moving to its own repo takes
its team, its release cadence and its deployment with it — the app composes it through
`remotes`, exactly as above, without seeing the difference. The mechanism is the same:
calls go through the doublures, the contract travels as metadata, not as source code. The
cross-repo workflow tooling is not shipped yet — today, the verified split is the
monorepo one above.

## What it is not

The promise is **not** that the network is transparent — networks fail, and Fougere
surfaces that as typed errors rather than pretending. The promise is that the domain and
its contracts stay stable while the topology evolves. Local mode is the reference mode;
you choose when a module earns its own process, and the code was ready either way.
