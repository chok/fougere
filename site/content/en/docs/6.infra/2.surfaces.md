# Surfaces

Pages talk to Fronds through the envelope. Everything else talks through a **surface** —
a thin bridge in three moves: *parse* its protocol into a call value, *[invoke](/docs/client/invoke)*,
*format* the result back. A surface never contains business logic; it is a door, and every
door leads to the same judged operations.

## REST — mounted

The Nuxt module mounts a REST catch-all under `/api/{frond}/{plural}` — the plural is
derived from the entity name (`post → posts`, `category → categories`):

| Route | Operation |
|---|---|
| `GET /api/blog/posts` | `post.list` |
| `POST /api/blog/posts` | `post.create` |
| `GET /api/blog/posts/{id}` | `post.findById` |
| `PUT · PATCH /api/blog/posts/{id}` | `post.update` |
| `DELETE /api/blog/posts/{id}` | `post.delete` |
| `POST /api/blog/posts/by-slug` | `post.bySlug` — kebab-case → camelCase; a known operation wins over an id |

Three properties worth knowing:

- **Same façade.** A REST body meets exactly the judges the envelope enforces —
  validation, unknown-key refusal, collectors. There is no second, laxer door.
- **Same errors.** Failures project through `toHttpError`: the real HTTP status from the
  [code table](/docs/business/errors), the full typed value in `data`.
- **List shape.** `list` results serialize as `{ items, total, hasMore, endCursor }`.

## GraphQL — a standalone projection

`@fougere/schema-graphql` derives Pothos types, inputs and CRUD operations from the same
`getFields()` metadata every other adapter reads. It is **not mounted by the Nuxt module** —
it ships as a projection you hand to the GraphQL server of your choice.

### `registerAll` — the whole schema, one call

```ts
import SchemaBuilder from '@pothos/core';
import { registerAll, registerGraphQL } from '@fougere/schema-graphql';

const builder = new SchemaBuilder({});
builder.queryType({});
builder.mutationType({});

registerAll(builder, app);          // ← every entity, every op, every relation

registerGraphQL(router, builder.toSchema());   // mount it on /graphql
```

That is the whole bridge. `registerAll` walks the scanned fronds and, for each entity that has
a handler, registers its type, its inputs, and one field per operation the handler exposes.
Relations declared with `ref`/`many` are wired between the registered types; a
[Presenter](/docs/business/presenters)'s computed fields become resolvers on the type.

**Write it by hand and you lose the judge.** Each generated resolver calls the handler façade —
the same door the envelope and REST go through, so the same validation, the same unknown-key
refusal, the same collectors. A resolver you write yourself against the ORM (or worse, against
the database) is a second door with no judge behind it: a `quantity` your schema declares as
`number({ min: 1 })` is enforced on every surface that goes through the façade, and on no
other. Reach for `registerType` / `registerOperations` only to add a field the projection
cannot derive — never to rebuild what it already gives you.

Two options, both rarely needed:

```ts
registerAll(builder, app, { surface: 'graphql' });   // honour frond.config.ts surfaces
registerAll(builder, app, { filter: (entity) => entity.name !== 'auditLog' });
```

`demos/schema-ecommerce` runs exactly this under Apollo Server on `:4000`.

Pre-release honesty: the GraphQL surface exists as a schema projection with a working
demo; a GraphQL endpoint mounted by the Nuxt module the way REST is does not exist yet.
