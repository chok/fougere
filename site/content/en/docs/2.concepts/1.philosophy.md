# Philosophy

Most frameworks hand you means of execution: pages, routes, endpoints, tables, caches.
Fougere hands you an **application model** — data, operations, contracts, boundaries —
and projects it onto those means. This page is the mental model everything else in the
docs assumes.

> Describe the application as a system of data, operations, contracts and boundaries —
> then project that model onto Nuxt, HTTP, SQL, cache or a remote process.

## Declarations project

An [entity](/docs/schema/entities) is a declaration, not a table. The table is one of its
*projections* — alongside validation, the TypeScript type, the form contract, the GraphQL
type. You write the declaration once; everything downstream derives, so nothing can
drift. When you are about to state the same fact in a second place (a validator here, a
column there), stop: find the declaration it should derive from.

## Operations, not field writes

The vocabulary of a Frond is **commands** (intentions that change the system), **queries**
(cacheable reads) and, as the system grows, **events** (facts a command produced).
`Crud(Post)` gives you the five standard operations to start with — then your domain
grows real verbs: [`publish`](/docs/business/handlers) is an operation with a judge and a
transition, not a client writing `status: 'published'` into a field. When you find
yourself exposing a raw field write for something that has business meaning, name the
operation instead.

## The Frond owns

Business logic lives in [Fronds](/docs/concepts/frond) — ownership boundaries carrying
entities, operations, policies and persistence. A Frond never reaches into another's
internals; the app composes Fronds instead of rebuilding the domain out of pages, fetches
and stores. The boundary is what lets a module move later without tearing anything.

## Topology is configuration

Where a Frond runs — in-process, its own process, another machine — is stated in
[one line of config](/docs/infra/gradient), not in your code. Business code never knows
its topology; calls ride the same envelope either way, and a local call is direct memory
execution, not hidden RPC. Decide the split when the team or the load demands it — the
code was ready either way.

The same boundary also settles where the code *lives*: a Frond can move to its own
repository, with its own team and its own release cadence — the app composing it sees no
difference. Process and repository are two sliders of the same
[gradient](/docs/infra/gradient), not two architectures.

## State is losable or durable

Every piece of state answers one question: *what happens if it is lost?* Behavior
unchanged → it is a **cache**, derived from a query, and the framework may clear it at
any instant (it does: every dev restart, every deploy). Behavior changed → it is an
**entity**, even if it lives ten seconds: a one-shot OAuth code is an entity
`{ code, userId, expiresAt }` with a destructive read, and that sentence is already the
architecture — durable, migrable, observable, no dedicated infra. There is no third
category, and that is what makes the question always answerable.

## Embedded or externalized

The packaging principle behind all of the above: what must stay identical everywhere
ships with the class; what realizes locally is plugged into it.

- **Embedded** — what must be *a single truth*: the judge, the io projections, the
  metadata. They ship inside the schema and go wherever the class is imported. One
  reference implementation, **executed everywhere**: the same judge runs in the browser,
  at the façade, in a remote Frond. One truth, N copies, zero drift.
- **Externalized** — what *realizes locally*: storage, transport, rendering. There,
  variation is the goal — SQLite today, Postgres tomorrow, GraphQL or REST per surface.
  Interchangeable precisely because it is not normative.

The judge is embedded because a judge that varies is no judge; storage is external
because a storage that cannot vary is no adapter. This is the
[gradient](/docs/infra/gradient) applied to packaging: pure derivations of the
declaration are topology-invariant; realizations live where they are plugged.

## The design order

When a design decision comes up, ask in this order:

1. What is the application concept?
2. What is its ownership boundary?
3. What contracts must it expose?
4. Which operations change state?
5. Which queries read it?
6. What invalidates what?
7. Which adapter executes or projects this model?

Starting from the route, the page, the table or the transport lets the tool dictate the
architecture.

## Why "Fougere"

*Fougère* is French for fern, and a fern is fractal: every frond has the same shape as
the whole plant. The framework is built the same way. A field is a complete declaration
at its scale (shape, role, lifecycle, boundary); an entity is complete at its own; a
Frond is a complete piece of business — entities, operations, policies, persistence; an
app composes Fronds and has the same shape as a Frond. At every scale, the same gesture:
declare once, project the rest. That repetition is what lets you grow — from "solo, one
repo, one process" to "teams, several repos, distributed" — without ever rewriting the
scale below.

## Position

Fougere is not a more convenient Nuxt, a less verbose Nest, or a CRUD generator. The
ambition is narrower and harder: **an application model for data-intensive products,
able to project itself onto several runtimes and topologies without losing its business
boundaries.**
