# The CLI

`@fougere/cli` creates a workspace, hosts a Frond in a separate process, and invokes an
operation from a shell. The CLI itself uses entities and handlers, so its options are
validated from their schemas.

> **Alpha.** On npm under the `alpha` tag — `npx fougere@alpha` runs it without
> installing, `npm create fougere` enters it at `new`. The commands and flags below are
> what ships.

## `fougere new` — compose a workspace

```bash
fougere new shop --frond blog --app nuxt
```

The command creates Fronds first, followed by the apps that consume them. It produces a
pnpm workspace:

```
shop/
  fougere.config.ts          ← db, auth, topology
  pnpm-workspace.yaml        ← packages: [fronds/*, apps/*]
  fronds/blog/               ← the domain
    entities/Post.ts
    handlers/PostHandler.ts
  apps/nuxt/                 ← the consumer
    nuxt.config.ts
    app/pages/index.vue
```

| Flag | What it does |
|---|---|
| `--frond blog,api:catalog` | Fronds to add — `template:name` renames; the template name is the default name |
| `--app nuxt:web` | same, for apps |
| `--bare` | the empty shell, nothing composed |
| `--flat` | one domain: no `fronds/`, no workspace — the app root is the Frond |
| `--local` | link `@fougere/*` to a local Fougere checkout (development) |
| `--force` | overwrite an existing directory |

**Arguments or interactive mode.** With `--frond` and `--app`, the command asks no
questions and can run in a script or CI job. Without these options, it prompts for
templates in a TTY. Interactive mode is not available without a TTY.

**Flat structure.** `fougere new shop --flat --frond blog`
writes one Nuxt app whose root carries the domain — no `fronds/` segment, no
`pnpm-workspace.yaml`, one `pnpm install` ([the flat
shape](/docs/getting-started#one-domain-no-fronds-at-all)). `--app` is refused with it:
the app *is* the root. A second domain later goes to `fronds/billing/` and the root Frond
stays where it is. The generated project also carries a `tsconfig.frond.json` whose
`include` names the convention directories. `pnpm typecheck` can therefore check the
domain without loading Nuxt.

The generated Frond contains an entity, two derived views (`NewPost` for input and
`PostCard` for list output), and a business operation in addition to CRUD:

```ts
export class NewPost extends Post.pick('title', 'body') {}

export default class PostHandler extends Crud(Post) {
  async create(input: NewPost): Promise<Post> { … }

  /** The draft→published transition — an operation, not a field write. */
  async publish(id: string): Promise<Post> { … }
}
```

The views define the input and output contracts for these operations.

## `fougere serve` — one Frond, its own process

```bash
fougere serve blog --port 4100
```

Starts that Frond alone and exposes it over JSON-RPC on `POST /_fougere/call`. The
consuming app sets its address in `remotes:` to route calls to that host. See
[the gradient](/docs/infra/gradient).

It does **not** follow `remotes:` itself: a host *is* the Frond, it does not route back
out.

> `serve()` binds `127.0.0.1` unless `hosts` says otherwise: a receiver reads identity
> off the wire, so the default keeps it on the machine and widening it is a decision
> written down.

## `fougere call` — invoke an operation

```bash
fougere call post.list
fougere call post.create --title "Hello" --body "…"
```

The command uses the same envelope, validation, and typed errors as other clients. A
`VALIDATION_FAILED` error therefore keeps the format received by a page.

## `fougere sync` — consume a remote Frond

```bash
fougere sync blog --from http://blog-service:4100
```

Asks the host `rpc.discover`, and writes local entity files rebuilt from the
[cards](/docs/schema/card) it answers with:

```ts
// .fougere/remotes/blog/entities/Post.ts — generated
import { Card } from '@fougere/schema';

export class Post extends Card.fromDescriptor<{
  id: string;
  title: string;
  createdAt: Date;
}>({ /* the card, verbatim */ }).toSchema() {}
```

One class, like the one you would have written by hand: `Post` is the value — a validator
that validates locally, without an additional request to the host — and the type of a row
it hands back, so `post.titel` does not compile. Both are read off the same card.

Next to it, `handlers/PostHandler.ts` states what the frond serves, so a consumer can
write `Facade<PostHandler>` without holding the handler's code:

```ts
export interface PostHandler {
  list(invocation?: Invocation): Promise<Post[] & { total?: number; hasMore?: boolean }>;
  findById(invocation?: Invocation): Promise<Post | undefined>;
}
```

The command also writes `.fougere/remotes.json`, which the Nuxt module reads to alias
`@fronds/blog`. Pages therefore use the same import path for a local or remote entity.

Re-running it **removes what the host no longer serves**. The barrel loses the export by
itself, but the file used to stay — and `exports` lists `'./entities/*'` as a wildcard, so
`@fronds/blog/entities/Ticket.js` kept resolving to a class that validates perfectly and
that nothing behind it answers for. Only files carrying the generated header are removed;
anything you put in that folder yourself is left alone.

The host returns entities associated with a façade, and **the facts its fronds announce**.
An entity that is neither is not in the discovery result — a shape nobody exposed and
nobody declared to leave stays home.

A fact has no operation, so it gets a class and no `Handler` interface beside it:

```ts
// .fougere/remotes/blog/entities/PostPublished.ts — generated
export class PostPublished extends Card.fromDescriptor<{ id: string; title: string; at: Date }>(…).toSchema() {}
```

To have an arriving fact validated, re-export that class into one of your own fronds — the
boot validates against an entity of a **scanned** frond, and `.fougere/remotes/` is a
package, not a frond:

```ts
// fronds/search/entities/PostPublished.ts
export { default } from '../../../.fougere/remotes/blog/entities/PostPublished.js';
```

### The rules

| code | what it means |
|---|---|
| `directory-unreadable`, `handler-parse-failed`, `heritage-unresolved` | what the scan could not do — a rule about an absence is only sound if the analysis attests it looked |
| `operation-unbound` | an operation declares parameters and has no binding plan: it is served, and it receives none of them |
| `cross-frond-import` | a relative import that resolves into another frond |

The last one is a warning, not a refusal — it resolves today and the app runs. What it
states is that a **colocation constraint is holding the app together and nothing declares
it**: `'../../user/entities/User.js'` says these two folders are neighbours, in a string
the scan, the identity card and `remotes:` all ignore. It keeps working right up to the day
that folder is not there, and then it fails as a file path rather than as a model.

`'@fronds/user/entities/User.js'` says the same dependency in terms the model reads, and it
is the form [`fougere sync`](#fougere-sync--consume-a-remote-frond) writes — so it survives
the frond moving out. The name resolves the same way whether the frond is local or synced.

## `fougere build` — write down what a scan found

```bash
fougere build                       # writes .fougere/scan.generated.ts
fougere build --out src/scan.ts
```

The scan reads a filesystem and a TypeScript program. This writes its answer down, so a
deployment reads neither — hand the file to `createApp` as `scan:` and nothing touches a disk
after that.

It is what makes the [edge](/docs/infra/deployment) reachable at all: a Worker has no filesystem
and cannot ship a compiler. It is also why the scan is **optional** — `frond()` declares the same
thing by hand, and `createApp({ fronds })` boots with neither disk nor `tsc`.

A generated file is not a second source. Nothing reads it but the boot, and regenerating it is the
only way to change it.

## `fougere check` — what the scan could not do

```bash
fougere check                 # from a project root; --root points elsewhere
```

It **scans without booting**, so it reports on a project it cannot start. Seven rules
today, each a stable name shared with the scan's own diagnostics:

| finding | means |
|---|---|
| `directory-unreadable`, `handler-parse-failed`, `heritage-unresolved` | what the scan could not do — an unreadable directory, a handler that would not parse, an `extends` it could not follow |
| `operation-unbound` | an operation whose parameters have no binding plan: it is served, and it receives nothing |
| `input-contract-ambiguous` | two parameters could be the input contract, so provenance cannot pick one — refused rather than settled by parameter order |
| `cross-frond-import` | a relative import that resolves into another Frond — a colocation constraint nothing declares, which holds until the day that Frond is not on this disk |
| `frond-holds-several-domains` | past six entities, the same threshold `fougere graph` uses |
| `unknown-adapter` | an entity addressing an adapter no dependency of the project answers to — a typo, or a dependency never added |
| `super-linear-pattern` | a `pattern` whose nested repetition backtracks super-linearly: the regex is fixed at declaration, the string tested against it is the caller's to choose |

Findings are **blocking** or **warning**, and only a blocking one exits non-zero — which is
what makes it usable in CI. An unresolvable base class with no operation is ordinary, and a
check that cries wolf stops being read.

## `fougere explain` — the contract one operation is served under

```bash
fougere explain Post.publish          # from inside a project
fougere explain Post.publish --root ../blog
fougere explain --names operations    # one name per line, what completion reads
fougere explain --json
```

Prints the resolved contract of one operation — the handler and method that run, where each
parameter comes from, which collectors fill it, the surfaces and adapters that serve it, and the
two facts about where it sits:

```
Placement: commande / local
Reach:     stock — 1 hop(s)
```

`placement` says where it ANSWERS, [`reach`](/docs/infra/observability) where its work GOES.
Comment a line out of `remotes:` and the same operation reports `0 hop(s)` — nothing in the
handler changed.

With no operation named, it lists what the project serves at all. `--json` emits a stable key
order, which is the contract an agent reads.

## `fougere graph` — read the model

```bash
fougere graph
```

Two altitudes of one picture. First where the Fronds run and which reaches which, read from
`remotes:` and from what a handler asks for in its constructor — so it answers with nothing
running and nothing booted:

```
  Fronds
    commande  local   → stock
    stock     remote  http://127.0.0.1:4100
```

Then the entities, their references, and the number of incoming ones. Beyond six entities,
the command also suggests clusters calculated from that graph:

```
  Entity Graph
    Post → Author, Category (2 incoming)
    Author
```

A crossing whose far side was never scanned is left out rather than guessed: naming the Frond
behind an address means reading its card, and a card is a discovery. An address is printed as
host and port, never whole.

The [shortest path](/docs/concepts/shortest-path) page covers current and possible future
uses of this graph.

## `fougere load` — the scenario the app already describes

```bash
fougere load                          # writes <root>/load.js
fougere load --door http://127.0.0.1:4200/_fougere/call
fougere load --out ""                 # print it instead
```

Writes a [k6](https://k6.io) scenario covering every operation the default door answers. What it
derives is everything the code already states: the operations, a body for each from the entity's
own fields, and the JSON-RPC envelope from the one function that frames a call.

What it does **not** derive, it marks in the file where it sits — the weights, the stages and the
thresholds are facts about your users, not about your code:

```js
export const options = {
  // Yours: a flat rate draws flat lines and there is nothing to read in them.
  stages: [ … ],
  // Yours: what counts as too slow is a fact about your users.
  thresholds: { … },
};
```

It reads the **scan**, never a boot: booting runs migrations and plants seeds, and a command that
describes a project has no business writing to its database. A named surface is left out — the
load of an app is what its default door answers, and counting a surface would count one operation
twice.

Regenerate rather than patch. A scenario written by hand drifts from the code, and then you are
comparing two scripts instead of two deployments — which is the whole point when the same code
runs [as one process or as several](/docs/infra/gradient).

## `fougere devtools` — what the running apps are dispatching

```bash
fougere devtools                      # every address this project declares
fougere devtools --url http://127.0.0.1:4100
fougere devtools --json               # one page, then stop
```

Reads the call log an app keeps when it mounted [`@fougere/calls`](/docs/infra/observability),
over `/_fougere/call` like any other consumer. **The reader pulls**: no app registers
anywhere, and an app started alone depends on nothing. The price is knowing the addresses,
and the project already states them — `remotes:` says where a call goes, so it also says
where the other half of a call can be watched.

The LOCAL one is the exception: a port belongs to the host and no project states one, so
`http://127.0.0.1:3000` is a convention — where Nuxt, Next and the site all sit. A host that
serves elsewhere says so the way it names a log level:

```bash
FOUGERE_URL=http://127.0.0.1:4100 fougere devtools
```

`--url` still wins over both, and narrows the reading to that one address.

An address that did not answer is reported as a refusal rather than as silence, and the
refusals are not one fact but four: not started, answering but serving no call log
(`Unknown rpc operation 'calls'. It serves discover.`), quiet — and a stranger, `answered
HTTP 404 — not a Fougere receiver?`, which is what something else on that port says for
itself.

## `fougere freeze` — record today's shapes under a name

```bash
fougere freeze v2
fougere freeze v2 --json
```

Writes two artefacts, and both are needed. A **snapshot** alone loses the intent — a field gone
plus a field appeared cannot be told from a rename, and the two produce opposite DDL. A **step**
alone corrupts in silence, with nothing to check it against. Replaying the step over the previous
snapshot must reproduce this one, which is what catches a missing step or a hand-edited file.

**Nothing reaches the disk while a question stands.** When a removal and an addition could be one
rename, the command asks — that intent is the only thing the code does not hold, and it left with
the person who made the change.

## `fougere migrate` — realise the steps the database has not caught up with

```bash
fougere migrate           # print the plan, move nothing
fougere migrate --apply   # run it
```

Reads the frozen versions and the live schema, and reports the gap. Without `--apply` it writes
nothing — the plan is the answer, and reading it is the point.

A fresh table and a migrated one promise the same thing: a `unique()` a live table never carried
is proposed as an index, and the statement fails on rows that already break it. That failure is
the answer, not an accident.

## `fougere keys` — the root a split deployment's grants are signed by

```bash
fougere keys              # once, at deployment time
```

Creates the authority and exits. Nothing stays alive, nothing is joined at boot, and no Frond
reaches anything to prove who it is. A receiver ends up holding **one public key**, so a Frond
granted tomorrow is admitted by a receiver deployed today without its config being touched.

The private key is written and never printed: it signs grants, and a grant is the only thing that
has to travel.

## `fougere grant` — vouch for one Frond

```bash
fougere grant billing
```

Binds a Frond's name to a fresh key, signed by the root. That is what lets a receiver
[establish its caller](/docs/infra/identity) rather than believe a claim — `serve()` refuses to
start beyond loopback with no way to verify, and this is what it verifies against.

## `fougere completion` — shell completion

```bash
fougere completion zsh >> ~/.zshrc
```

`zsh` and `bash`; the shell is auto-detected when the argument is absent. The names it
completes come out of the same entities the commands ride on, so a new command needs no
second list.

## `fougere build-frond` — publish a Frond's entities

```bash
fougere build-frond blog
```

Compiles `fronds/blog/entities/**` to `dist/` with type declarations and configures the
Frond's `package.json`. A consumer in another repository can then install that package.
See [where the code lives](/docs/infra/gradient#where-the-code-lives).
