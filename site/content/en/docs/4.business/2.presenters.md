# Presenters

A presenter adds **computed fields** to what an entity sends out. Each method is one
field: the method name is the field name, and it is handed **every row of the response at
once**, answering one value per row.

```ts
import { Presenter } from '@fougere/core';
import type { EntityOrm } from '@fougere/core';
import Post from '../entities/Post.js';
import Author from '../entities/Author.js';

/** Typed alias — DI resolves by TYPE name, and `AuthorOrm` is the container's key. */
type AuthorOrm = EntityOrm<Author>;

export default class PostPresenter extends Presenter(Post) {
  constructor(private authorOrm: AuthorOrm) { super(); }

  excerpt(posts: Post[]): string[] {
    return posts.map((post) => post.body.slice(0, 200));
  }

  /** One read for the page, not one per row — which is why the page is the argument. */
  async authorName(posts: Post[]): Promise<string[]> {
    const ids = [...new Set(posts.map((p) => p.authorId))];
    const authors = await Promise.all(ids.map((id) => this.authorOrm.findById(id)));
    const byId = new Map(authors.filter(Boolean).map((a) => [a!.id, a!.name]));
    return posts.map((post) => byId.get(post.authorId) ?? 'Anonymous');
  }
}
```

It lives in the Frond's `presenters/` directory, and the scan registers it as `PostPresenter`.
Methods may be sync or async, and the class is DI-injectable like any other — declare
constructor dependencies by type.

## Why it is not a field on the entity

An entity declares **what it owns**. `excerpt` is not owned data — it is derived, every
time, from `body`. Storing it would state the same fact twice, and the second copy would
go stale. `authorName` is worse: it belongs to another entity, so duplicating it means
every author rename silently leaves old rows lying.

The rule is the one [philosophy](/docs/concepts/philosophy) states: a fact is declared
once and everything else derives. A presenter is where the derivation runs when it cannot
be a projection of the shape alone — it needs I/O, or another entity, or both. That is
also why it is a class and not a callback: it takes DI, so it can reach an ORM without a
handler passing one to it.

## Every door, the same answer

A computed field is part of the entity's output, so it rides on **all four** surfaces —
the envelope (`useQuery`, `useCommand`, `invoke`), the REST catch-all, a standalone REST
host, and GraphQL. There is nothing to enable.

```ts
const { items } = await useQuery<Post>(Post, 'list');
items[0].excerpt;      // ← present, exactly as in a GraphQL query
```

> This is recent. The enrichment used to live in the REST and GraphQL projections only,
> each with its own copy, so the same presenter answered on two doors and was silently
> absent from `useQuery`. Two routes to one destination is a framework defect by
> [this project's own standard](/docs/concepts/shortest-path) — it now runs once, at the
> façade.

## Where it stops: a named view

An op that names its output view is **closed** — the author stated exactly what that
audience gets, so a computed field they did not list stays out:

```ts
Crud(Post, { list: PostCard })   // list emits PostCard, and only PostCard
```

Open is the default, and there a computed field is an addition to the entity's output.
Naming an audience is what closes it — the same rule the
[boundary axis](/docs/schema/entities) applies to the entity's own fields.

## What it is not

- **Not a serializer.** What may leave at all is the `boundary` axis; what a given
  audience sees is a [view](/docs/schema/views). A presenter only **adds**.
- **Not a place for business rules.** A computed field is a read. A transition
  (`publish`) is [an operation, not a field
  write](/docs/business/handlers#a-state-changes-through-an-operation-never-through-a-field-write).
- **Not free, but no longer per row.** A method receives the page, so `authorName` above
  issues one query for 200 posts, not 200. The shape makes batching possible; it does not
  force it — `posts.map((p) => this.orm.findById(p.authorId))` inside a computed field is
  still N reads, and nothing says so.
- **Not allowed to fail quietly.** A throwing computed field surfaces as
  `INTERNAL_ERROR` naming the field — the domain produced it, so it is a bug, not a bad
  request.
