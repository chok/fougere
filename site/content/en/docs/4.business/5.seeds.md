# Seeds

A seed is a file in a Frond's `seeds/` directory, run once at boot after migration. It
receives `resolve` and talks to the **same façades** your app uses — seeds go through the
judged operations, not around them.

```ts
// fronds/blog/seeds/Post.seed.ts
type Facade = Record<string, (inv?: Record<string, unknown>) => Promise<any>>;

export default async (resolve: <T>(name: string) => T) => {
  const posts = resolve<Facade>('post');

  // Idempotence is yours to state — here: seed only an empty world.
  const existing = await posts.list();
  if (existing.length > 0) return [];

  const created = await posts.create({
    params: {}, query: {},
    body: { slug: 'hello', title: 'Hello', body: '…' },
    state: { user: { id: 'seed-author' } },   // server-side code owns the invocation
  });

  // The transition goes through the same operation as everyone else's.
  await posts.publish({ params: { id: created.id }, query: {}, body: undefined,
                        state: { user: { id: 'seed-author' } } });

  return [];   // nothing left for the boot loop
};
```

## The contract

- **Export**: `default async (resolve) => rows[]`. Returning `[]` means "done here".
- **`resolve('<entity>')`** returns the entity's façade — each operation takes a full
  invocation `{ params, query, body, state }`.
- **`state` is yours**: seeds run server-side, so they own the invocation — stamping
  `state.user` is how a seed acts *as* someone through judged operations
  (`publish` above still checks author-only, and passes because the seed says who it is).
- **Idempotence** is the seed's responsibility; the guard is one `list()` + early return.

Why through the façade and not the ORM? Because then seeds exercise the same judges,
stamps and errors as production traffic — a seed that works is a proof, not a bypass.
