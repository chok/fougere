# Views

A view is a derived schema class. It is declared **from** the entity, never
reverse-engineered from what a query happens to select:

```ts
/** What an author may write. */
export class PostDraft extends Post.pick('slug', 'title', 'summary', 'body') {}

/** What the public index shows — no body. */
export class PostCard extends Post.pick('id', 'slug', 'title', 'summary', 'publishedAt') {}

/** Input of a custom read operation. */
export class BySlugInput extends Post.pick('slug') {}
```

A view is a full schema class: it has `getFields()`, `validate()`, and is usable as a
TypeScript type. Views chain: `Post.pick(…).partial()`.

## The four derivations

| Derivation | Produces |
|---|---|
| `Post.pick('a', 'b')` | only those fields |
| `Post.omit('a')` | all fields but those |
| `Post.partial()` | every field optional — **validates as a patch**: an absent field means "untouched", never "forged" |
| `Post.extend({ extra: text() })` | entity plus new fields (how `User` extends `AuthUser`) |

The view's mode travels with it: a `partial()` input used as an operation's input validates
in patch mode automatically.

## Where views plug in

- **Handler inputs** — declare the view as the parameter type; the façade validates the
  wire body against it before your code runs ([Handlers](/docs/business/handlers)).
- **Handler outputs** — `Crud(Post, PostPublic)` scopes every read to the view's fields.
- **Forms** — `useFormFor(PostDraft)` derives its fields from the view ([Forms](/docs/client/forms)).

## The io projections

The boundary axis derives two field sets used by every surface:

```ts
inputFields(Post.getFields())    // fields a client may WRITE  — readOnly excluded
outputFields(Post.getFields())   // fields a client may READ   — writeOnly excluded
```

This is why a form built on `Post` never shows `status` or `publishedAt` inputs, without
any per-form configuration — the projection is the single statement.
