# Views

A view is a derived schema class. It is declared **from** the entity, never
reverse-engineered from what a query happens to select:

```ts
/** What an author may write. */
export class PostDraft extends Post.pick('slug', 'title', 'summary', 'body') {}

/** What the public index shows — no body. */
export class PostCard extends Post.pick('id', 'slug', 'title', 'summary', 'publishedAt') {}

/** Input of a custom read operation. */
export class BySlugInput extends Post.pick('slug') {}
```

A view is a full schema class: it has `getFields()`, `validate()`, and is usable as a
TypeScript type. Views chain: `Post.pick(…).partial()`.

## The four derivations

| Derivation | Produces |
|---|---|
| `Post.pick('a', 'b')` | only those fields |
| `Post.omit('a')` | all fields but those |
| `Post.partial()` | every field optional — **validates as a patch**: an absent field means "untouched", never "forged" |
| `Post.extend({ extra: text() })` | entity plus new fields (how `User` extends `AuthUser`) |

The view's mode travels with it: a `partial()` input used as an operation's input validates
in patch mode automatically.

## Where views plug in

- **Handler inputs** — declare the view as the parameter type; the façade validates the
  wire body against it before your code runs ([Handlers](/docs/business/handlers)).
- **Handler outputs** — `Crud(Post, PostPublic)` scopes every read to the view's fields.
- **Forms** — `useFormFor(PostDraft)` derives its fields from the view ([Forms](/docs/client/forms)).

## The io projections

The boundary axis derives two field sets used by every surface:

```ts
inputFields(Post.getFields())    // fields a client may WRITE  — readOnly excluded
outputFields(Post.getFields())   // fields a client may READ   — writeOnly excluded
```

This is why a form built on `Post` never shows `status` or `publishedAt` inputs, without
any per-form configuration — the projection is the single statement.

## Field or view — the partition

`readOnly` / `writeOnly` drop a field from a surface; `pick` / `omit` do too. Two
mechanisms for "drop a field"? No — two **natures**, and knowing which one to reach for is
the whole point.

- **boundary** (on the field) states an **invariant**: "this field never crosses in that
  direction, anywhere." `writeOnly(password)` — the password leaves **no** view, ever.
- **pick / omit** (in a derivation) states a **choice of use**: "for this surface, these
  fields." `Post.pick('id', 'title')` — the public index, not the others.

They are not synonyms: each covers what the other cannot.

- **Putting everything in derivations** breaks on the invariant. Without `writeOnly` on the
  field, you'd need `omit('password')` on *every* output; one miss = a leak. The invariant
  restated at each view is consistency by hand — [what a single declaration
  removes](/docs/concepts/philosophy).
- **Putting everything on the field** breaks on the local choice. A public response (`id`,
  `title`) and an admin response (`+ authorEmail`) can't be marked on the field:
  `authorEmail` is in or out *depending on the view*. Forcing it onto the field would take
  one axis per surface — config, everywhere.

The test, as one question: **true everywhere, or true for this use?**

| The fact is… | It lives… | Example |
|---|---|---|
| true everywhere (invariant) | on the field — `readOnly` / `writeOnly` | a password never leaves |
| true for one use (local) | in a derivation — `pick` / `omit` | this endpoint returns only id + title |

An invariant carried by the field **travels** as a bonus: it rides in the
[card](/docs/schema/card) (`x-fougere.boundary`), so a consumer written in another language
knows too that the password doesn't leave. A view derived in TypeScript does not travel.
